### N1 [中·功能死链] 交期留痕从未被写入，准时率证据恒为空

**08 §7 / 客户口径#5**：*"交期由采购填写，实际交期以仓库验收为准，这肯定要留痕的"*

**根因**：`_recalc_po_delivery()` 只有一个调用点 —— `_bump_line_on_receipt()`（**验收时刻**）。
但那一刻到货单状态还是 `待入库`，而函数里的过滤条件是：

```python
GoodsReceipt.status.in_(("已入库", "现场已验收"))     # ← 待入库被过滤掉 → dates 为空 → 什么都不写
```

`store_receipt` 把到货单置 `已入库` 之后，调了 `_recalc_request_status`，**但没有调 `_recalc_po_delivery`**；
现场清点路径（`site.py` / `services/site.py`）也**完全没有引用**这两个字段。

**实测**：
```sql
select count(*) total, count(actual_arrive_date), count(delay_days) from purchase_order;
  total=14   actual_arrive_date=0   delay_days=0        ← 全库 0/14
```
决定性用例 `PO26014`：承诺交期 `2026-09-23`，实际 `2026-09-28` 验收并入库（**逾期 5 天**）→
`actual_arrive_date=NULL`、`delay_days=NULL`、状态 `执行中`。

**下游连带失效**：`suppliers.py:637` 的准时率计算
```python
if not po.supplier_id or not (po.actual_arrive_date and po.expect_date): continue
```
→ **所有单都被 skip**，`GET /purchase/recommend/{item_no}` 返回的每家供应商都是 `late: false`：
```
乙标准件  score=77 late=False  reasons=[买过2次…, 历史2次成交价 ¥55~¥55, 验收全合格（40件）]
丙钣金    score=77 late=False  reasons=[买过2次…, 历史2次成交价 ¥100~¥100, 验收全合格（10件）]
甲钢材    score=57 late=False  reasons=[…, ★ 验收合格率 80%（有不合格）]
```
**对比**：合格率那一路证据是活的（甲钢材被扣分并给出理由），**准时率那一路是恒真的空证据** ——
所有供应商都"完美准时"，包括逾期 5 天的丙钣金。三期-C「绩效接进推荐」实际只接上了一半。

**修法**：`store_receipt` 与现场清点 `accept_incoming` 两处各补一次 `_recalc_po_delivery(session, po_id)`；
或把过滤条件放宽到 `("待入库","已入库","现场待验收","现场已验收")`（货到了就算实际到货，与"以仓库验收为准"一致）。

### N6 [设计问题] 拆单必须串行，两家供应商 = 两次审批往返

```
第一刀 甲60 → 需求「审批中」
第二刀 乙40 → HTTP 400「当前状态是「审批中」，不能合并下单」     ← merge_order 白名单只有 (待采购, 部分下单)

```

**业务影响**：客户口径#1 说"很有可能会拆给多个供应商"。现在拆 N 家要 **N 次完整审批往返**；
更糟的是**如果总监驳回第一刀，第二刀根本下不了** —— 而"拆给两家"本来应该是**一次决策**。

**★ 关键：放开是安全的。** `assert_no_over_order` 用的 `ordered_qty()` **不看 PO 状态**（只排除已退货/已取消的行）：
```python
select sum(PurchaseOrderLine.qty) where request_id=:i and line.status not in ("已退货","已取消")
```
→ 待审单的量**已经计入**已下单量，超拆防线不受影响。

**修法**：`merge_order` 的状态白名单加 `"审批中"`（一行改动），拆单就能一次提交两张单。

两处过期：① `order_and_receive` 下单后**没有审批步骤**（重构后下单即进待审，需求是「审批中」不能验收）；
② 读的是派生 `status` 而不是 `po_status`（撞上 N7）。

我补了 `approve_po()` 并改读 `po_status` 后才跑通 → **8/8 全绿**。

**★ 隐患**：这是**验证「净需求三项抵扣」修复的唯一强探针**（三个重复进池机制的隔离证明）。
它崩了意味着 `commit 49a7826「e2e 基线入库」`之后，**这条护栏实际上没在跑**。

### N9 [配置隐患] 没有采购经理账号 → 两级审批实际退化成一级

```sql
select username, name, position, org, roles from app_user where org='PURCHASE';
  buyer1             采购组员   组员   PURCHASE  PURCHASE
  purchase_director  采购总监   总监   PURCHASE  PURCHASE_LEAD     ← 角色码是「采购经理」，岗位却是总监
```

**客户口径#17** 明确要求：*"后台你配两个账号就可以了…一个是经理账号，一个是总监账号"*。

实测审批留档：
```
PO26001 | round=1 | level=1 | reviewer=NULL | action=跳过 | note=无采购经理，自动跳级给总监
```

**后果**：
1. 所有采购单都走「经理空缺自动跳级」→ **一级审批（经理审）分支从未被真实数据覆盖**，`lead_for_dept()` 这条路径等于没测过
2. 两级审批在现网配置下**就是一级**（只有总监审），与客户口径#3「采购经理和采购总监进行审批」不符
3. `purchase_director` 的 **角色码 `PURCHASE_LEAD`（名称"采购经理"）与岗位 `总监` 不一致** → 权限与审批链判据分裂（权限看角色码，审批链看 `position`）

**修法**：`services/demo.py` 补一个 `purchase_manager`（PURCHASE / `position=经理` / 角色 `PURCHASE_LEAD`），
并把 `purchase_director` 的角色码改成新的 `PURCHASE_DIRECTOR`（或明确"角色码只管权限、岗位只管审批链"并写进文档）。

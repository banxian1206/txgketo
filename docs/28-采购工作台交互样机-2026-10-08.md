# 采购工作台步骤样机（2026-10-08）

范围：按客户八张参考图优化独立样机，未修改正式业务页面、接口、权限或数据。入口 `/design-lab/proposals/purchase-workbench.html`，附加交互脚本 `purchase-flow.js`。全部状态只存页面内存，刷新复位。

## 页面与交互

- 待采购：左侧品类，右侧详细品牌规格型号；同物料同单位汇总，展开项目–设备与数量；型号筛选、勾选、底部生成单据。
- 生成采购单：供应商、默认收货地及逐行收货地；本次/上次价、小计、总价、逐行预计到货；无价拦截，现场收货必须选项目；草稿或提交审批。
- 采购单：状态筛选、供应商品类、金额、异常、预计到货与详情入口。
- 审批：经理→总监→在途；每行本次价、历史价、涨跌和金额；历史缺失单独显示；未轮到本人不能通过，退回原因必填。
- 叫车：发货指令上下文、车辆与预计到场必填，提交后展示运输安排。
- 催货：按交期展示谁在等、上次催货；沟通结果必填，保留原承诺日期。
- 退换：验收照片占位、原始问题、隔离位置、处理方式、供应商沟通和后续条件；记录处理进展后仍保持异常未关闭。让步接收及退款不能直接完成或入库。
- 项目：沿用项目、客户、交付地、PM、状态、所有角色待办、剩余时间、阶段进展列表；未定义百分比时不展示虚构百分比。
- 仓库手机视角：待验收与验收步骤；实际数量、模拟照片、结果、不合格数量与原因；短缺保持未到，合格进入待入库，不合格转采购。

## 验收顺序

1. 打开样机点任务，选品类、展开明细、筛选型号、勾选型号生成采购单。
2. 保留3030铝型材空价提交，应阻止；填28元后提交，合计9888元。
3. 样机视角切采购经理并通过，再切采购总监并通过，应转在途。
4. 切回采购员，任务中查看叫车、催到货和退换货；观察必填与处理反馈。
5. 切仓库手机端，填实收3、添加模拟照片，提交合格；应显示3台待入库、1台未到。

## 限制

这是交互方向样机，不是生产功能实现。照片是明确标识的占位；待办总数等为示例值，并非全部与内存状态联动。补发再次验收/原货退回、退款金额确认及使用方让步确认尚未提供完整闭环页面，不应把记录处理方式视为关闭异常。项目数量分配、返工及资料缺失仍需进一步定规则。

## 第二轮：摘要 → 明细 → 同页处理

客户希望PC统一先看总，再看细节，减少下沉。新增 `purchase-master-detail.js` 实现样机层覆盖。

| 页面 | 左侧摘要 | 右侧明细与处理 |
|---|---|---|
| 待办 | 上方分类：全部、预警、超时、事件、催单、紧急需求；左侧事项、对象、原因 | 原验收依据与处理方式、催货表单、价格退回依据、紧急采购需求 |
| 待采购 | 品类及型号数、最早需要下单日 | 品牌型号规格、缺口数量、来源展开、勾选下单（保留上一轮形式） |
| 采购单 | 单号、供应商、物料种数、按单位分别统计的数量、金额、状态 | 与生成采购单相同的物料、数量、价格、小计、收货地和来源；只读/编辑按状态区分；同页处理异常或催货 |
| 催到货 | 物料、供应商、未到数量、到货期限 | 等待方、交期依据、最近沟通、直接记录催货 |
| 叫车 | 发货指令、项目、目的地、包数重量、状态 | PM与交付上下文、车辆与到场表单、登记后结果 |
| 退换货 | 原异常摘要 | 沿用验收证据、处理方式及后续关闭条件，不直接完成 |
| 项目 | 项目号名称、客户交付地、PM、剩余时间、待办总数、状态 | 基本上下文、整体阶段、各角色待办与同页采购上下文 |

分类是展示提案，不新增后端待办生成规则：每件事只在主要原因类别出现一次，逾期催货归超时并带催单标签；分类为空时显示空态，不添加虚构事项。数量仅相同单位相加，混合单位分别显示。任务/项目页收起大欢迎区，增加明细可用面积；窄窗口变成摘要横滚、明细下置。

浏览器补验：催货缺沟通结果拦截、填写后同页显示最近记录；采购单切换与右侧明细对应、在途单同页出现催货表单；选择质保项目显示售后待办；叫车后保持选中并显示车辆和时间。浏览器采样无error，JS语法检查通过。截图 `purchase-prototype/summary-orders.png`。

验收：刷新样机 → 首页选择分类和事项 → 任务/采购单点左侧不同单据 → 在途单记录催货或部分到货单处理异常 → 项目切换。主列表选择保持在当前页面。新建采购单及草稿编辑仍使用独立弹窗，这是明确的单据创建边界。

### 第四轮：团团陪伴区与悬浮助手

AI改为右下角悬浮按钮，可展开、收起，支持示例逾期采购单、项目缺料、历史价格、编号查询；回答附对象依据按钮，打开全局搜索预览并可进入原工作页。未知问题明确无对应示例数据。Esc仅收起最上层助手，不关闭底下的业务弹窗。查询使用本地固定示例，不调用模型或业务接口，不执行写操作。

### 第六轮：2.5D角色逐帧动作（替代位图整体运动）

用户授权自行制作所需素材与可爱动作。使用内置imagegen，以原熊猫为形象参考，生成16帧透明图集：眨眼4帧、抬爪吃竹子4帧、招手笑脸4帧、嘴型说话4帧。提示词：同一圆润毛绒大熊猫、2.5D/3D渲染质感、4×4等格、同相机同大小同落脚点、真实改变眼睑嘴型爪子与竹子、完整身体、透明背景、无文字无场景。图集保存于 `frontend/public/design-lab/proposals/assets/panda-actions-v1.png`（1254×1254）；原静态资产保留。

`purchase-companion.js`改用requestAnimationFrame驱动图集取帧，眨眼周期含睁眼停留，吃竹子播放抬爪与咀嚼，开心回应招手与笑脸，短气泡配嘴型。删除整图旋转/翻滚和伪眼睑覆盖层；后台、离屏、搜索/弹窗时暂停新动作，首页自动轮换，点击熊猫回应。沿用透明背景和无常驻文字。对图集实际边距设置源帧位置，避免相邻行的脚部串入画面。

验证：浏览器实际帧编号随自动调度及点击变化（8→0），首页透明角色正常显示，390px根宽390，控制台采样无error，JS语法通过。截图 `purchase-prototype/panda-animated.png`。这一版是16帧预渲染2.5D角色动画，尚非实时3D骨骼模型，四帧单动作的顺滑度仍有精调空间；未接声音与业务接口。验收：刷新后观察吃竹子/眨眼，点击角色看招手笑脸，等待自动轮换时查看嘴型和短气泡。

### 第七轮：连续补帧与稳定落脚点

用户反馈四帧动作跳变、不自然。本轮使用内置imagegen生成三组各16帧，共48帧：`assets/panda-eat-v2.png`、`assets/panda-wave-v2.png`、`assets/panda-idle-v2.png`。提示词约束：沿用原熊猫身份与柔软2.5D质感、每组4×4等格、顺序连续小幅姿势变化、固定镜头/大小/落脚点、无字透明底；吃竹子包含逐渐抬爪→咀嚼→逐渐放下，招手包含逐渐抬爪→轻挥→放下，微表情包含渐闭眼→睁眼→嘴型→闭嘴。保留上轮资产不覆盖。

从图片读取alpha几何信息（不修改源图）计算每帧脚底中心、基线和宽度，Canvas按固定落脚点与体宽绘制，减小生成帧位置/尺寸差异造成的抖动。动作12fps，加入起止停留，按完整周期播放，不在中途强制切到待机。所有图集预加载后才使用。修复requestAnimationFrame时间戳与动作初始化performance.now的小偏差造成负帧索引、停止循环的问题：帧计算时间差钳制到0。

验证：浏览器桌面显示透明角色，点击切wave，等待自动循环后读到idle:0；修复后未出现新增控制台错误（旧日志仍保留修复前05:00:28错误）；390px根宽390无溢出；JS语法与diff检查通过。截图 `purchase-prototype/panda-smooth-v2.png`。这是生成的连续预渲染帧，帧间轮廓仍可能有细微差异，不能等同实时骨骼动画。验收刷新后观察约30秒，再点击看完整抬爪/招手/收爪过程。

### 第八轮：固定结构的2.5D关节动画

用户反馈生成帧头身大小不一致。根因包括不同帧比例漂移、按脚宽逐帧缩放进一步放大差异。本轮放弃整图帧切换，新增原生SVG关节实现 `panda-rig.js`：头/身体/脚的几何尺寸固定，渐变与软阴影提供圆润立体感；眼睛、嘴型、手臂/竹子独立运动。requestAnimationFrame连续采样，smoothstep缓入缓出控制抬爪/招手，眨眼与咀嚼有独立节奏。移除加载图集、逐帧脚宽缩放与canvas帧绘制。外形改为2.5D圆润插画，旧毛绒图集保留。不是实时3D模型或专业骨骼资产。

浏览器对比点击前后：头部width122.70831298828124/height106.08334350585938，两次相同；身体width125.56085205078124/height96.90863037109376，两次相同，位置也相同。手臂transform有独立旋转，头身无动画缩放。390px根宽390，控制台采样无error，两脚本语法及diff检查通过。截图 `purchase-prototype/panda-fixed-rig.png`。验收刷新首页，观察眨眼/吃竹子，再点击看招手；主要检查头和身体是否保持大小、动作是否连续。

## 1. 本轮范围与证据边界

用户要求停止 Pi 协作，先由主 Agent 全面理解系统，再讨论如何改 UI/UX。本轮没有调用 Pi 或子 Agent，没有修改产品代码，没有提交业务单据，没有清库或运行种子/复位脚本。

直接阅读业务主线、编号、角色、设计流转、采购重构及近期业务裁决；核对实际模型、核心服务、路由、工作台与手机入口。浏览器以 buyer1、wh1、site1 本人登录，查看采购及手工申请表、仓库、跨部门项目详情、现场 PC 和手机页面及调试申请表；只查看并取消表单。

以下“实现”指源码证据；“页面确认”限上述实际查看范围。既有测试报告只能说明历史结果，不等于本轮重跑。未把 S0→S11 全部写操作、异常组合、多角色管理范围验证一遍，因此不能宣布所有路径均已理解并实测通过。

## 2. 这个系统到底在管理什么

公司交付的是按客户要求设计制造的非标设备/整线。系统把客户约定、工程设计、实物履历、跨部门交接和款项记录串在同一个项目下。项目能跨多台设备、多专业、多供应商、多批到货、多批发运及多个现场动作。

根对象只有一个 Project：商机出生即发 TX 项目号，订单、合同、项目沿用同号，不是四张独立档案。S0→S11 是业务环节，不是 Project.stage 的十二个值；实际大阶段只有线索、成交待立项、执行中、交付中、质保、已归档、已关闭。

“执行中”覆盖设计、采购、制造、装配的并行活动；首次发运推进交付中，验收通过进入质保，质保过期通过读时扫描归档。不能据大阶段推断所有设备、专业、采购单已同步完成。

依据：docs/00 §1/§3、docs/01 §1、models/project.py、services/project_stage.py、services/shipping.py::depart、services/acceptance.py::confirm。

## 3. 对象之间的关系

| 对象 | 核心含义 | 与其他对象的关系 |
|---|---|---|
| 客户/联系人/资料包 | 谁提出要求，以什么约定做事 | 项目关联客户、联系人和版本资料；冻结技术协议是设计/验收依据 |
| 项目 | 一次客户交付的组织与合同上下文 | 设备、团队、节点、款项和所有业务记录的根 |
| 设备 | 同一项目里可单独设计、制造和发运的单元 | 01A/02A 等；01B 可为同型第二台 |
| 图纸树/图号件 | 非标设备的结构与零件 | 项目专属；图号即物料号；版本变更不换图号 |
| 标准库型号 | 公司共用的标准件/原材料规格 | 类别→品类→型号；无项目号，各项目引用 |
| 设计 BOM/材料 BOM | 设计需要什么，与制造用什么原料 | 同设备结构下两种用途，不是两个互不相关的项目 |
| 任务/子任务 | 指派到人的设计工作 | 经理主任务、组员子任务；项目对接人不等于任务 owner |
| 评审单/轮次/发布批次 | 谁交了哪些内容，谁审过，哪版有效 | 一个任务一张评审单，可多轮；审核发布形成冻结快照 |
| 采购需求 | 上游缺什么、要多少、归哪项目/设备 | 发布、长周期、手工、补采等来源；不能被拆单覆盖原需求量 |
| 采购单/单行/到货单 | 买给谁、买多少、哪批真的到了 | 一条需求可拆多家，单行必须保留归属，验收到具体行 |
| 库存/流水/领料单 | 在哪库位、可用多少、交出了多少 | 领料需求量/已备量/已领量分开；备料占用不等于已出库 |
| 排产单/验收/转运 | 零件做出来并到装配区的事实 | 自制件按已发布图纸产生；没有工序级报工审批 |
| 装配记录/未装清单 | 装到什么状态，还有什么散件 | 发运结构可折成组装体+未装散件 |
| 发运指令/车辆/清单/现场清点 | 哪天发哪些设备，实际发什么，现场收什么 | 一条指令跨 PM、采购、发运、现场；收发用同一份清单 |
| 现场问题/改版申请 | 哪个设备/零件出了什么问题，如何处理 | 问题可关联具体件；冻结对象改动走改版而非直接编辑 |
| 客户验收/质保/服务工单 | 客户接受交付，之后如何保障 | 验收通过算质保；报修、派工、处理、签字关闭 |
| 回款节点/采购付款记录 | 客户付给公司、公司付给供应商 | 两种相反方向的款项，不能混为同一“付款”状态 |

## 4. S0→S11 的主线与交接

| 环节 | 主要责任 | 处理的对象与依据 | 交给下游什么 |
|---|---|---|---|
| S0 商机与成交 | 销售/商务；销售经理指定 PM | 客户需求、联系人、技术约定、合同周期/金额/回款节点 | 成交待立项项目及明确 PM；成交不是自动立项 |
| S1 立项 | PM组织，团队对接 | 设备范围、团队、节点、长周期件 | 设备×专业主任务给专业经理，采购相关需求给采购 |
| S2 工程设计 | 机械/电气/程序并行，工艺后接；经理/工程总监审核 | 图纸、设计 BOM、原材料 BOM、来源判定、程序版本 | 分批有效版本；产生采购净需求；机械首次发布解锁工艺 |
| S3 采购 | 采购员执行，采购经理/总监审价格 | 多项目需求池、供应商、规格/冻结图纸、历史价格、交期 | 已批准采购单及确定的单行归属；公司仓或直发现场 |
| S4 仓库 | 仓管；车间专职人员领料 | 到货单、采购单行、规格/图纸、库位、领料单 | 合格入库与实际发料事实；不合格交采购协商 |
| S5 制造 | 车间系统专员/领料员/质量职能 | 已发布图纸、原材料、排产与外协记录 | 合格零件转运装配区；返工留在原记录链上 |
| S6 装配/厂内调试 | 装配与调试职能 | 齐套事实、有效图纸/程序、装配记录 | 装配完成、厂内调试结果、未装清单；不设100%齐套开工门槛 |
| S7 发货与发运 | PM定指令；采购叫车；发运装车/发出 | 设备装配状态、客户沟通、计划日期、实际清单、照片 | 一批实际已发项及物流状态；现场按同清单接收 |
| S8 现场安装 | 现场负责人/安装队 | 勘测、收货清点、直发件、日报、具体件问题 | 安装事实、缺损处理、需派调试人员的申请 |
| S9 现场调试 | 现场协调与被派调试工程师 | 调试申请、到场、单机/联调日报、问题记录 | 调试完成事实，作为申请客户验收前置 |
| S10 客户验收 | PM/现场系统执行；客户实际签认 | 技术约定、资料包、调试完成记录、签字人 | 验收结果；通过后质保起止与商务收款提醒 |
| S11 售后与归档 | 售后执行；商务/财务跟踪款项 | 质保范围、工单、备件、设备历史、客户签字 | 维修闭环与历史；项目到期归档，非“所有款项自动结清” |

S10 的“项目组织责任”和“谁在系统里有操作权限”必须分开：代码给 PM 和 SITE acceptance:edit，现场手机页有客户验收入口。未据此推断现场替代 PM 的组织责任。

## 5. 角色体系：四种维度不能混用

1. 系统角色：决定功能能力与工作台可见。实际 seed 有 ADMIN/GM/SALES/SCHEME/DESIGN/DESIGN_AUDIT/CRAFT/PM/PURCHASE/PURCHASE_LEAD/WAREHOUSE/MFG/ASSY/QC/DELIVERY/SITE/SERVICE/FIN 共18种。
2. 部门/组：描述人在哪里，经理管哪组、总监管哪部门。部分代码仍用 profession 判断专业组，尚未全面迁到组织树。
3. 岗位：组员/经理/总监，决定执行、分工/本级审核、部门协调/终审的职责差异。拥有“采购经理”角色码与 position=经理是不同字段。
4. 项目角色：同一个人在某个项目的对接职责；如机械负责人、现场负责人。不是自动授予系统功能，也不是设计审评经理。

| 人员职责 | 工作的核心 | 必要上下文 |
|---|---|---|
| 销售/商务 | 客户跟进、成交约定、回款 | 工程/交付节点用于客户沟通与款项触发 |
| 销售经理 | 商务协调、未分配成交项目、指定 PM | 部门商机与接手状态；此新确认规则入口尚未实施 |
| PM | 设备范围、团队、节点、卡点、交付与验收组织 | 跨专业及实物流转；不是所有专业的默认操作者 |
| 设计组员 | 指派的设计范围、本人产出、提交与退回 | 有效技术依据、相关设备结构、前置状态 |
| 专业经理 | 接主任务、自己做/拆分/转派、本级审核 | 本专业人员与设备工作、退回卡点 |
| 工程总监 | 工程终审与部门协调 | 有效版本、审核依据、部门进度；不能看组员提交页就当本人核心工作 |
| 工艺 | 原料 BOM、自制/外协/定制判定 | 机械首次发布的结构和图纸 |
| 采购员 | 合并/拆单、选供方、提审、交期、不合格协商、叫车、付款记录 | 需求来源、图纸规格、历史价与供应商往来 |
| 采购经理/总监 | 当前本级价格审批与采购协调 | 含税口径、历史价、供应商交期与质量；不以金额阈值免审 |
| 仓库 | 验收、库位入库、备料交料、库存事实 | 单据和项目追溯、图纸规格；不需要合同金额 |
| 制造/质量/装配 | 下发、验收、返工、转运、装配与厂内调试 | 有效版本、料件到位、照片交接；不是逐工人报工系统 |
| 发运 | 实际发出项、装车、发运履历 | PM指令日期、已叫车辆、组装体与散件 |
| 现场 | 清点、安装记录、问题、申请调试、现场签认 | 项目与设备、同份清单、冻结图纸与客户要求 |
| 售后 | 工单、派工、处理、备件、客户签字 | 设备全历史、质保范围、维修依据 |
| 财务 | 客户回款与供应商付款记录核对 | 项目金额、采购价格、应付已付；当前与GM共用驾驶舱 |
| GM | 交付、卡点、经营与质量总体情况 | 全项目汇总；当前成本毛利未建，不能按有完整成本系统理解 |
| 管理员 | 用户、组织、角色、编号与集成配置 | 系统维护；超管绕过权限，不能用来验证业务角色 |

## 6. 不能忽略的分支与异常

- 分批设计：不等整设备全部发布才采购；评审退回在原任务/评审单里进入下一轮。
- 机械、电气、程序并行，工艺等待机械首次发布；程序发布不产生采购需求。
- 经理自行提交与缺审核人的处理不是同一种情形；工程/采购具体规则以各服务实现分别核对。
- 总装图首次需随批发布或已发布；图纸/程序附件必需；草稿、审核中、冻结版动作不同。
- 冻结后改版：挂具体冻结版本、裁决、下发、重审、新版生效；已有采购影响提示并人工处理。
- 同型设备复制：发布/新增同型设备时复制设计并形成自身需求；母机 ECN 自动传播尚未实现。
- 長周期件早于常规设计采购节点，不能假设所有采购都等 S2 完成。
- 手工申请可以归项目/辅料/办公用品/其他，免设计审核入池；采购单价格审批仍是另一道流程。
- 一条采购需求多供应商拆单、多批到货、部分合格；需求量、已下单量、单行已收量各有含义。
- 验收不合格：采购协商换货/退货重采，不能把合格部分也丢回池。
- 直发现场绕过公司入库；缺件/破损形成补采来源，需保存原单据追溯。
- 库存优先与净需求抵扣：可用库存、在跑需求覆盖、已领到车间都参与，不能同一件反复进池。
- 部分备料/部分领料可继续补差额，已备库存锁定不等于实际发出。
- 制造按已发布非总装图的自制件生成；外协任务另一路；不合格返工，合格后拍照转运。
- 齐套率是事实展示，装配可以提前做；装配完成后的未装散件还需随货发出。
- 发运不是整个项目一次发完；PM按设备发指令，采购叫车，发运勾实际已发、装车、发出。
- 现场只清点实际发出的项；组装体不再展开为内部80个零件，收发单位保持一致。
- 客户回款节点由物流/验收事件提醒，不阻塞实物流；供应商付款截图/标记不等于银行转账功能。
- 现场调试申请有未完成记录时复用；验收已通过不可重复覆盖质保起算日。
- 项目归档是质保过期的读时扫描，不是后台定时任务，也不代表自动关闭所有服务工单。

## 7. 跨域的共同机制

数量以 services/bom_math.py 为公共口径：组件2×零件3=整机6，BOM行还要乘父级累计倍数。采购、领料、排产、齐套、发运不是各自解释一个 qty。

库存由库位库存与流水维护；结构件具有项目归属，标准库型号跨项目共用。项目齐套用于PM看全局，单据用于采购/仓库办事，两种视角需要能互相追溯。

金额是独立权限：project:amount 与 purchase:price 等；协作只读可见不等于能看所有钱，更不等于可以改或提交其他人的内容。

消息是提醒渠道，不是接单/责任确认的完整替代。当前有精确发给负责人，也有按角色群发；点通知/搜索/编号后的具体落点是理解交接的一部分。

件档案、设备档案、全局检索与活动流是只读聚合入口，不是另建一份业务事实。标准库、供应商和历史价是采购基础；ERP仅导入数据，内部 legacy_code 不做展示编号。

PC更适合设计/BOM、采购与管理；仓库、车间专职录入人员、现场、售后主要手机。手机页不是仅把PC缩窄；同一核心服务有不同作业页面。

OCR实际只做可选的库位标签识别、结果人工确认。旧终端文档中的广泛本地OCR和AI助手能力不能直接当成已上线；本轮主路由未发现AI聊天接口，查询档案不等于自然语言AI助手。

## 9. 本轮页面观察与限制

- buyer1：默认采购池；PC列出审批/叫车/需求池/单据/到货/不合格/退换/入库/价格/供应商，个人执行与部门数据在同台。打开手工申请读取归属、项目、设备、标准库物料、数量、需用日和用途，取消未提交。
- wh1：默认待验收；库内作业区分验收、入库、领料、库存、流水、库位。可打开协作项目TX26001，金额不出现在列表，详情仍是近似统一生命周期与“进入设计面”。列表显示新建商机入口，未点击/未验证写权限。
- site1：PC默认来货清点；手机能选项目进入来货、日报、问题、调试、验收、勘测。调试申请是dispatch_to文本，计划到场日期另填。取消未提交。
- 当前五个测试项目主要为线索/成交待立项/执行中，查看的采购与现场队列为空；不能据空态验证多单、拆单、退回、发运清点或服务工单操作。
- 本轮没有按所有账号穷举所有操作，也没有新造全链数据。后续业务理解需要验证上述分支的真实交接；但应先讲清责任与事实口径，不能边测边随意改页面。

## 10. 已确认且保持的用户口径

销售经理负责指定PM与未分配成交项目；首页聚焦本人职责，相关项目链接仍可协作查看。停止Pi分工，由主 Agent继续理解。暂不推进此前指定PM入口和任务上下文的实现建议，先形成完整理解并讨论一致后再决定改造。

本文件用于向用户核对业务理解，不把尚未验证的细节包装成既定规则，也不预先把现有页面或四角色样稿当最终正确结构。


## 11. 后续真实角色验证对整体理解的补充

以上§1/§9是最初只读走查范围；后续按用户“继续”完成专用测试业务写链，证据统一放docs/22 §7–10，不覆盖历史范围说明。当前TX26001的一台设备标准件路径已实际经历设计退回重提/发布、拆单采购/换货、入库/领料、装配/厂内调试、PM指令/采购叫车/发运、现场清点/调试、客户测试验收和售后工单闭环。自制制造等支路与手机体验仍待验证，不宣布全路径验收。

这轮理解带来的重点是：页面不应只按数据模块排功能，而应从“谁接到了哪项交接、凭什么处理、完成后给谁”组织。

| 责任方 | 已证实的主要接手依据 | 目前需要澄清/补齐的体验 |
|---|---|---|
| 专业经理 / 工程总监 | 本级评审单与版本，退回重提保留同单多轮 | 本人审核与部门量分开；多人设计对象范围待用户实际口径 |
| 采购员 | 需求、批准采购单、真实单行、不合格批次；PM发货日形成待叫车 | 拆单质量履历不能混归；叫车与物料采购是两种待办 |
| 仓管 / 车间领料人员 | 到货批次、实际供方、库位、领料累计数量 | 验收/入库/已备/已交分别表达，剩余未完交接不能被状态隐藏 |
| 装配 / 调试人员 | 实时齐套与开工快照、有效图纸、未装清单 | 可以部分齐套开工；工程师赴现场后需完整工作入口 |
| 发运 / 现场负责人 | 同一份本批实发清单，叫车事实，到/缺/损与日报 | 签收不等于异常解决；公司发运缺件与供应商直发缺件路径不同 |
| PM | 项目设备范围、跨部门卡点、调试完成、验收资料与客户确认 | 项目阶段推进与未解决异常并存；需要可追踪的异常责任交接 |
| 商务 | 验收等节点触发的应收款项提醒 | 与PM验收组织责任区分，不把提醒等同实际到账 |
| 售后 | 设备/项目质保、报修工单、处理与客户签字 | 派工为文字且无本人队列；备件台账目前独立于仓库库存 |

因此后续改造需要同时设计三个层面：角色首页的待办与需知事项；项目/设备/件的协作上下文；退回、缺损、变更等异常由谁接手直到解决。只重排卡片、换标签或换配色无法补齐后两者。此处是理解结论，尚不是已批准实施方案。


## 12. 制造与改版支路对整体理解的补充

详docs/22 §11。制造/外协采用13项内存服务分支验证，不等同真实排产全链；现场工程改版有14步真实API证据。

系统中要分清：发布的是设计依据，制造验收记合格事实，转运记实物交接。自制合格仍需转运才被齐套认可；外协实现目前合格即到位，无单独转运步骤。工艺来源判定是经工程评审发布后决定下游去向，不是自由标签。

现场人员提同一工程图改版，现有实现按申请人部门路由：site1属GM，实际交给gm，工程总监裁决403。测试申请CR26001已带方案否决，现场问题另行关闭，原V1保留。此责任路由应在UI/UX改造前校正；不能靠分角色排菜单掩盖。

后续整体设计应先明确每项工作对象、依据、当前责任人、下游接手人，以及异常闭环条件，再分配角色首页和协作详情；视觉精调建立在这份业务规格上。


## 13. 整体收敛：角色体验规格与分段改造顺序（2026-10-07）

### 13.1 本轮结论与使用方式

本节是基于docs/22证据的设计建议，供整体评估；不是已经批准或落地的产品改动。继续暂停Pi和产品实施。本轮只整理文档，没有新增业务数据。

系统不适合把S0→S11当作人人都逐页走完的一套流程。PM需要了解全项目，专业人员处理具体任务，仓库/车间面对共享作业队列，经理与总监负责分工和本级决定。阶段反映项目位置，单据反映执行事实，异常反映仍需解决的问题；三者应同时可追溯。

既有功能大量可保留：引擎编号、对象档案、分批发布与两级评审、采购单行、累计领料、实发清单、验收与质保、防重复操作。改造不是先重写全部业务，而是校正少数错误事实与责任路由，然后按职责重新组织入口、内容与动作。新页面结构和文案可以调整，不把现有卡片或四角色样稿当既定答案。

### 13.2 每个角色登录后应该先看到什么

下表是拟议首页规格，不是新增权限或数据硬隔离。共同遵守用户确认：首页聚焦职责，相关链接可协作查看；敏感金额和写操作仍按权限。共享队列不伪称已分配给本人。

| 职责 | 首页优先事项 | 首要动作 / 工作入口 | 需要保留的协作上下文 |
|---|---|---|---|
| 销售执行 | 本人商机跟进、成交资料交接、回款节点 | 进入具体商机或款项节点 | 客户要求、PM接手与项目交付进展 |
| 销售经理 | 未指定PM的成交项目、部门需要协调的商务事项 | 为具体项目指定PM；入口待实施 | 成交约定、候选PM与管理范围 |
| PM | 本人负责项目的启动缺口、节点风险、未解决交接 | 组织立项、协调责任人、发货/验收安排 | 设备×专业工作、采购实物、现场问题；成员项目另作参与项 |
| 专业经理 | 专业主任务、轮到本人的本级审核、人员阻塞 | 自己承担/拆分/转派；审核具体单 | 本组产出、有效依据、下游需求 |
| 设计组员 | 本人任务、退回修改、前置等待、提交反馈 | 进入任务工作范围、编辑与提交 | 对应设备结构、冻结约定、相关对象；范围规则待确认 |
| 工程总监 | 实际待终审、工程改版待裁决、跨专业风险 | 终审/裁决具体单 | 版本、审评意见、影响面；改版路由需先修正 |
| 工艺经理/组员 | 机械前置是否已满足、本人任务、材料BOM与来源判定 | 进入工艺任务，提交材料/判定评审 | 已发布机械结构、零件制造去向；经理分工与组员执行分开 |
| 采购执行 | 待下单需求、交期、退换协商、待叫车 | 处理采购单/单行/异常批次或发运车辆 | 需求来源、库存覆盖、供方价格、计划日期 |
| 采购经理/总监 | 轮到本人这一级的价格审批、供方风险 | 审核具体采购单 | 价格与历史依据、交期质量；部门采购池可跟踪，不作本人审批量 |
| 仓管 | 共享队列的待验收、待入库、已备待交、缺料 | 扫/选具体批次或领料单，记录实物 | 真实供方与单行、库位、图纸规格、接收班组 |
| 车间专员/质检 | 待下发、返工、验收记录、合格待转运 | 下发材料图纸、验件、拍照转运 | 有效版本、周期、原验收履历；不新增生产审评或工序报工 |
| 装配/厂内调试 | 责任设备、缺口数量、装配/调试记录 | 开工、记录未装清单、完工与厂内调试 | 实时齐套与开工快照；当前无精确责任绑定处标共享队列 |
| 发运 | PM本批指令、车辆就绪、清单确认/装车/发出 | 进入具体批次登记实发与照片 | 设备组装体/散件、发货日、车数、现场反馈 |
| 现场负责人 | 本现场来货、安装日报、需协调问题、调试申请 | 清点、日报、关联问题、派调试 | 同份实发清单、直发批次、现场条件、有效设计 |
| 被派调试工程师 | 被派现场、到场计划、调试工作与反馈 | 到场/调试记录；日报能力待补齐 | 单机/联调依据与问题、申请验收所需事实 |
| 售后 | 待受理/待派工与本人维修任务分别呈现 | 进入具体工单处理、记录与签字关单 | 设备历史、质保、备件；管理/执行实际分岗待核实 |
| 财务 | 客户应收/实收、供应商应付/已付核对 | 进入真实款项记录 | 合同与采购金额；支付登记不等于执行银行转账 |
| GM | 交付风险、责任缺口、质量异常与经营概况 | 定位具体项目协调 | 全项目汇总；未实现成本毛利明确说明 |
| 管理员 | 账号、组织、权限与配置异常 | 系统管理 | 配置/日志；不以admin视角验收业务 |

多角色用户如何确定首个落点仍需设计；不自动新增身份切换或恢复“我的工作台”。共享作业责任、销售/商务、售后派工人员实际分岗未确认部分不擅自固化。

### 13.3 同一事项必须说清六件事

1. **是什么**：项目/设备、任务或单据、版本/批次。名称和编号可追溯，不能只写“3个待办”。
2. **为什么到这里**：上游是谁、发生了什么；如经理退回、采购已叫车、现场实到不足。
3. **现在轮到谁**：本人、共享作业队列、别人处理需我跟踪，清楚标范围。
4. **凭什么办**：有效技术约定、冻结图纸、价格依据、实物清单、照片与数量。
5. **下一步是什么**：提供当前有权限且业务条件允许的动作；不能把可查看事项称为待本人审批。
6. **完成后给谁**：显示实际接收人/队列与结果；没有指派或闭环模型时不虚构“已交接”。

例：仓库不是显示“采购需求10件/部分到货”就结束，而是定位A采购单行6件、当前到货批次3件合格待入库、余量另列；现场不是显示“已签收”就结束，而是同时给出应发2、实到1、缺1和异常处理进展。设计退回进入原任务与对应对象，消息直接定位单据，不再让用户从部门首页重新查。

### 13.4 优先级：哪些必须先处理，哪些先设计再落地

| 优先级 | 项目 | 已有证据 / 边界 | 完成判据（建议） |
|---|---|---|---|
| 优先纠正事实 | 拆单到货供方、单行质量履历、已验收/已入库 | docs/22 §7，真实API | A批不标B；B单不含A不合格；未入库不称已入库 |
| 优先纠正入口 | 部分到货同时有待入库时剩余验收入口 | §7–8，真实API | 前批待入库不隐藏后批可验收入口；数量仍按单行上限 |
| 优先纠正责任 | 工程对象改版按单据归属找裁决人 | §11，真实API，符合AGENTS§6.13 | 现场发起工程对象也交工程裁决；配置缺人明确报错，不全局兜底 |
| 定向补验后修 | 有图号采购件部分到货被算齐套 | §3.4，隔离复现；标准件链正常 | 部分实物不能当整项齐套；保留已领覆盖，按种数展示齐套率 |
| 首段体验 | 销售经理指定PM、PM启动、经理分工、组员执行/退回、总监发布 | 用户确认+§2/8；多人对象范围待答复 | 成交有明确接手责任；各角色首屏和动作符合职责；未决范围不先加限制 |
| 交付体验 | 调试本人日报、发运缺损责任与解决进展 | §9–10，真实API | 被派人工作入口完整；签收与异常解决分别表达；处理归属需确认 |
| 收尾体验 | 任务/通知深链、文案数量、手机照片操作 | 源码+部分页面；浏览器补验待恢复 | 数字、队列、消息、详情对应同一对象和范围；现场手机完成主要动作 |
| 后续扩展 | 财务与GM分工、外协采购/实物关联、多设备/多人、工艺改判/改版V2 | 以源码为主或未续验 | 先补真实场景证据，再决定重构，不宣称当前已正确 |

这里“优先”表示改造依赖和风险排序，不是本轮开工授权。发运缺件是否阻断验收、丢失/漏装/损坏由谁接手仍未裁决，不能直接添加验收拦截或自动补采。

### 13.5 按交接链分段实施，不按页面数量分段

| 顺序 | 一段完整交付 | 实施范围与退出条件 |
|---|---|---|
| 第0段 | 统一事实和责任基础 | 修已复现的单行追溯/队列/裁决路由，补必要护栏；关键数据及权限正确后再据此显示 |
| 第1段 | 登录→销售成交交接→PM立项→工程分工/评审发布 | 登录状态/落点与各角色首页、任务工作页、协作详情、退回文字一起完成；沿既有测试项目验正常与退回，保护原有发布机制 |
| 第2段 | 发布/长周期需求→采购→仓库→车间/装配 | 同步改善采购单行、批次、领料数量与去向；补真实自制/外协、工艺路径；手机是主要验收终端 |
| 第3段 | PM发货→叫车→发运→现场→调试→验收/售后 | 同一实发清单、本人派工、异常处理与质保上下文；明确处理责任后补闭环 |
| 第4段 | 全站一致性与经营/财务职责收尾 | 统一文字、间距、控件、空态、错误/保存反馈与金额范围；FIN/GM依据实际已建能力分别组织，不补虚构指标 |

各段内部先定“事项与交接规格”，再做代表页面，连同查询/深链一起落地；视觉细节随段完成，最后全站复核。登录可作为第1段第一个可见页面，但不让登录美化替代角色落点与业务交接设计。没有通过该段的真实角色与手机验收，不扩到下一段。

### 13.6 每段都用四类场景验收

- 正常：上游完成后，下游正确账号/共享队列看到正确对象与依据，并能处理。
- 退回：回到原任务、对象和意见，跨区/刷新保留数据，再提交后履历连续。
- 部分完成：部分发布/到货/备料/领料/实发，剩余量与入口可用，不要求一次做完。
- 异常：缺人、缺料、不合格、缺损、改版，区分告知与待办，明确责任及未解决状态。

同时验证首页计数→列表→详情一致，消息/搜索/直接链接可定位，非本级审批拒绝，协作可读，敏感金额遵循权限。依据本段变化跑必要测试与build/tsc，功能行为回档；不为了UI验收清空ERP库。本轮只改文档，未运行产品构建或回归，不将既有证据当新页面验收。

### 13.7 下一步的具体成果

先把第1段六种职责（销售执行、销售经理、PM、专业经理、组员、工程总监）的首页事项、工作页和正常/退回交接画清楚，沿用本节规格及docs/19已确认部分，替换不准确内容。经理多人设计范围需用户口径后才能固化提交边界；其余信息架构可继续细化。产品实施前提供完整可评估的一段，避免继续零散改页面。

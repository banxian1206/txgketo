## P0 · 会造成数据错误或资损

### P0-1 ★ 直发现场的件完成后会**永久重复进采购池**

**位置**：`services/bom_demand.py:32` + `_open_qty()` + `_cover()`

```python
OPEN_STATUS = ("待采购", "在途", "已下单", "待入库", "部分到货", "不合格")
#              ★ 缺「现场待验收」「现场已验收」
```

`_cover` 的抵扣只有两个来源：**库存** + **OPEN_STATUS 里的在跑需求**。
但直发客户现场的货**从不进 `StockItem`**（`store_receipt` 明确拦：`"直发客户现场的货由现场验收，不走公司入库"`）。

**复现推演**：
```
1. 定制件 TX26001-01A-01-00-00-00 × 10 发布进池 → request A（待采购）
2. 采购下单，deliver_to=直发客户现场 → status=在途，建「现场待验收」到货单
3. 现场清点「齐」→ routes/site.py:421 调 _recalc_request_status
   → goods_receipt.status = 现场已验收，request A.status = 现场已验收
4. 任何人点设备面「生成采购需求（进池）」：
   · _open_qty：现场已验收 ∉ OPEN_STATUS → request A 被跳过，贡献 0
   · _stock_available：直发件从不入库 → 0
   · cover = 0 → 净需求 = 10 → ★ 又建一条 request B（待采购）
5. 再点一次 → 又建 request C …… 每点一次多一条
```

**影响**：AGENTS §8.1 承诺的*"幂等，重复点不会重复进池"*对直发件**不成立**。采购池里会堆积重复需求，采购员看不出哪条是真的 → 重复下单资损。
**关联**：`REQUEST_DONE = ("已入库", "现场已验收")` 把「现场已验收」当"采购不用再管"，但净需求计算没把它当"已覆盖" —— **两处口径打架**。

### P0-2 ★ `equipment_demand` 把定制件/外协件数量**算成平方**

**位置**：`services/bom_demand.py` `_cumulative_qty()` 与 `equipment_demand()`

```python
# _cumulative_qty：cum[X] = X.qty × cum[parent]  ← ★ 已含自身 qty
q = float(d.qty or 1)
if parent and parent in by_no:
    q *= calc(parent, seen | {no})
cache[no] = q

# equipment_demand 图纸分支（定制件/外协件）：
need[key] += float(d.qty or 0) * cum.get(d.drawing_no, 1.0)
#            ↑ 又乘了一次自身 qty  →  d.qty² × cum[parent]
```

**四处口径对比**（同一个"零件在设备上要几个"）：

| 位置 | 算法 | 对不对 |
|---|---|---|
| `bom_demand.equipment_demand` **BOM 行分支** | `b.qty × cum[parent_ref]` | ✅ 对（BOM 行数量 × 父级累计） |
| `bom_demand.equipment_demand` **图纸分支** | `d.qty × cum[d.drawing_no]` | ❌ **平方** |
| `bom_demand.release_demand` ②③ | `cum[d.drawing_no]` | ✅ 对 |
| `manufacturing.generate_orders:113` | `mult.get(d.drawing_no, 1)` | ✅ 对 |

**复现推演**：定制件图纸 `qty=3`，挂在 `qty=2` 的组件下，组件挂在总装（qty=1）下。
- `cum[定制件] = 3 × (2 × 1) = 6` ← 正确需求
- **发布自动进池** → 6 个 ✅
- **手动点「生成采购需求」→ 3 × 6 = 18 个** ❌ 多买 12 个

**为什么没被发现**：绝大多数图纸 `qty=1`，`1² = 1`，完全看不出。**任何 qty>1 的定制件/外协件都会被超采。**
**附带**：同一条需求走"发布"和走"手动补跑"结果不同 → 两条通道互相矛盾。

### P0-3 「待入库」窗口期会重复进池（幂等性失效）

**位置**：`_open_qty()` 用 `qty_received`，而 `_recalc_request_status` 把**未入库的 pending 也算进了 `qty_received`**

```python
# _recalc_request_status (initiation.py:1028-1031)
stored  = Σ qty where status == "已入库"
site    = Σ qty where status == "现场已验收"
pending = Σ qty where status in ("待入库", "现场待验收")
row.qty_received = stored + site + pending      # ★ pending 也算"实收"

# _open_qty (bom_demand.py)
remaining = max(0.0, qty - qty_received)         # ★ 于是 pending 部分 remaining=0
```

`pending` 的货：**既不在库存里（还没入库），又不算在跑量（被 qty_received 抵掉了）→ 两头都不覆盖。**

**复现推演**：
```
1. 设备 01A 的 BOM 需方通 100（已冻结）→ 发布进池 request A(qty=100)
2. 下单 → 在途；到货 100 验收合格 → goods_receipt=待入库
   _recalc：qty_received = 0(stored) + 100(pending) = 100，status=待入库
3. 此时点「生成采购需求（进池）」：
   · _open_qty：待入库 ∈ OPEN_STATUS ✓，但 remaining = 100 − 100 = 0
   · _stock_available：还没入库 → 0
   · cover = 0 → ★ 新建 request B(qty=100, 待采购)
4. 仓库把 A 的货入库 → 库存 100
5. 采购在池里看到 B → 下单 → 多买 100
```

**影响**：违反 AGENTS §8.1 的幂等承诺。**"验收合格但未入库"是仓库最常见的中间态**（分批到货时长期存在），窗口不小。
**修法方向**：`_open_qty` 的 remaining 应只扣**真正进了库存的**（`已入库 + 现场已验收`），pending 仍算在跑。

### P1-5 齐套率**不乘父级累计倍数** → 虚高

**位置**：`services/kitting.py:113`（图纸件）、`:146`（BOM 行）

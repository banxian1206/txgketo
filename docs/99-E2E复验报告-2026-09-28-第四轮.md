## 4. 本轮新发现（3 个，均非本次重构引入）

### N14 [P2] 审批价格快照留档是"半截活"——永不落库、也不回传

08 §3.3 设计的是：审批留档记 `price_flags`（审核人**当时看到**的历史价快照），这样事后能回答"你批准时参考的是什么价"。

现状链条：

| 环节 | 状态 |
|---|---|
| 模型列 `purchase_approval.price_flags` | ✅ 在（`models/purchase_order.py:165`） |
| 服务层参数 `price_snapshot` + 写入 | ✅ 在（`purchase_order.py:151, 190`） |
| **路由是否传** | ❌ `approve_purchase_order:2299` 调用只传 `(session, po, current, body.action, body.note)`，**从不传 price_snapshot** |
| **`/approvals` 是否返回** | ❌ 实测返回字段只有 `{round_no, level, reviewer_id, reviewer_name, action, note, acted_at}`，**无 `price_flags`** |
| 前端 | 审批弹窗 `PoApproveModal` 的 `HistoryCell` **当场展示**上次价/均价/区间/笔数（做得很好），但不持久化 |

**实测**（V6-1）：故意用 ¥99 下单（历史成交 ¥8，`avg_price=54.67 / min=8 / max=113 / deal_count=9`），审批"通过"后：
```
审批留档 price_flags = []          ← 空
```
**后果**：`price_flags` 这一列永远是 NULL。事后审计问"这张 ¥99 的单批准时，审核人看到的参考价是多少"——**系统答不出来**；前端展示的参考价也**无法回溯**（下次价格库变了就变）。

**修法**（约 5 行）：`approve_purchase_order` 里对单内每行调 `price-reference` 取 `stats` 组成 `price_snapshot` 传给 `approve_order`；`/approvals` 的 dict 里回传 `price_flags`。

### N15 [P3] `late` 字段语义与"实际逾期绩效"是两码事，且缺结构化字段

实测（V6-2 / V7-C）：一家**实际逾期 8 天**（`PO26021 承诺09-20 实际09-28 delay_days=8`）的供应商：
```
丙钣金  score=65  late=False  reasons=[…, ★ 经常逾期：2/2 批晚到, 验收全合格（22 件）]
```

- ✅ **扣分生效**（score 65 vs 他人 77）—— N1 那条链真的通了
- ✅ reasons 文案里有"经常逾期 2/2 批晚到"
- ❌ 但结构化字段 `late=False`

根因：`suppliers.py:767` 的 `late` 是**前瞻语义**（`supplier_catalog.lead_days + 今天 > need_date` → 声称的交期赶不上），且**不传 `need_date` 时恒为 false**；而三期-C 接进来的**回顾语义**（实际批次逾期）只落在 `reasons` 文本里，没有独立字段。

**后果**：前端若按 `late` 渲染警示标记，**逾期供应商不会显示任何警示**（虽然排序已被压低）；文案里的逾期信息也无法被前端结构化利用。

**修法**：加一个不与 `late` 混淆的字段，例如 `on_time_rate` / `late_batches`（或直接复用已算好的 `2/2`），前端按它打"历史逾期"旗标。

### N16 [P2] 现场清点「缺件」不回流采购侧——缺口无补采出口

实测（V8）：直发件 方通×40，现场清点 `result=缺件`、`shortage_detail=[{item, qty:15, reason:少发15}]`、`remark=实到25缺15`：

```
HTTP 200 ✅  通知已发：{type: site, title: "现场来货缺件：TX26001 GR26012"} ✅
需求：qty=40  qty_received=40.000  qty_ordered=40  status=现场待验收
到货单：qty=40  qty_ok=40.000  status=现场待验收        ← qty_ok 仍是全量，无处记"实到 25"
新增「待采购」需求：0 条
```

交叉验证（`grep shortage_detail` / `site_incoming`）：
- `shortage_detail` **只存在于 site / shipping 两个域**
- `initiation.py` / `workbench.py` / `warehouse.py` 对 `SiteIncoming`、`shortage_detail` **零引用**

→ **缺的 15 个既没进采购池、也没进「验收不合格」，采购台完全看不到**。对比仓库侧：不合格有完整闭环（`不合格 → negotiate → 换货 / 退货重采新建需求回池`）；现场侧只有通知，没有回流。**这是一个不对称的闭环缺口**，风险是设备到现场装配时才发现少 15 个方通。

缓和因素（所以我只给 P2 不给 P1）：
- ✅ 通知已发（项目团队知道）
- ✅ 到货单停在 `现场待验收`、单子一直不结清 → 采购台会看到它长期"在途"（弱信号）
- ✅ 补发到达后可再次清点，不是死单

**修法**：清点结论为 `缺件/破损` 时，除通知外，把缺口落成采购侧可见的事实 —— 与仓库侧同构：到货单记 `qty_ok=实到 / qty_rejected=缺口`，并按需新建一条 `source='现场缺件'` 的「待采购」需求（`origin_request_id` 指回），这样采购池/到货跟踪都能看见。

## 5. 一处我自己的判断被证伪（记下来免得下次再猜）

我怀疑"直发件下单即建的现场待验收单会让 `qty_received` 在货还没到现场时就被虚记成订购量"（若成立则是 P1）。
**V7-A 实测证伪**：刚下单、审批通过、货在路上 → `qty_received=NULL`、`arrived_at=NULL`、`status=在途` ✅。
原因是 `qty_received` 只在 `_recalc_request_status` 被调用时才重算，而下单/激活路径没触发它。
（也正因此，N16 里"清点缺件后 qty_received=40 全量"才是真实现象——它是**清点动作触发 recalc** 时把 pending 计入了实收。）

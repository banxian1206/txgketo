# 18 · 业务交接与角色体验重构

2026-10-06初稿，2026-10-07补充收敛。当前整体角色规格与分段优先级以docs/21 §13为准，真实证据见docs/22；docs/19样稿是早期四角色提案，尚非正式实施方案。

## 1. 重新定义设计的起点

用户最新口径：不同角色登录后看到属于自己职责的内容；各角色职责不同，展示内容应不同。不能只沿已有页面布局修补。

系统核心是项目型制造的交接：客户需求变成项目约定，项目约定变成专业设计任务，已发布图纸 / BOM 变成需求与实物任务，实物经过采购、仓库、制造、装配、发运、现场，最终验收与售后。各环节交接的是具体对象、版本、数量、时间和责任，不是一个大阶段百分比。

职责范围不能只按角色名称决定。需区分：部门与小组（归属）、岗位（承担哪层责任）、权限角色（允许哪些动作）、项目角色（在某项目承担什么）、单据 / 任务指派（此刻轮到谁）。同一个人可有多个角色，但不能因此把所有台的所有事项都当成他的待办。

## 2. 职责与交接地图（供核对）

以下依据当前业务主线与已确认限制整理，不增设业务审批。范围仍需与实际人员组织核对，不能直接据表改后端授权。

|---|---|---|---|---|
| 销售 / 商务执行 | 哪些商机要跟、合同约定是否完整、哪笔款该跟进 | 客户需求、线下合同与资料 | PM 接手的项目范围 / 周期 / 付款约定 | 本人负责的商机、到期跟进和商务事项 |
| 商务管理 | 哪些商机 / 回款需要协调与决策 | 部门业务和异常 | 明确的跟进责任与处理结论 | 管理范围内的例外和待决事项，不能机械用组员列表 |
| PM | 项目是否能启动、哪里卡交付、该找谁处理 | 合同 / 技术基线、各专业与实物状态 | 设备范围、团队、节点、任务、发货与验收安排 | 所负责项目的交接缺口、节点风险、需要协调的事项 |

| 制造执行 / 领料专员 | 下发哪份图和材料、到期零件是否合格、下一站在哪 | 有效图纸、材料与制造任务 | 实物验收、返工 / 外协 / 转运结果 | 责任任务的下发与验件事项；不做工序报工或生产审评 |
| 装配 / 厂内调试 | 哪台设备可以开始、缺哪些件、问题是否影响完成 | 到位实物、有效设计与任务 | 装配 / 调试记录及可交付设备状态 | 责任设备、缺件与问题、记录动作；齐套率不设开装硬门槛 |

| 现场负责人 / 安装 | 收到哪些实物、今天完成哪些、缺什么、是否能派调试 | 发运 / 直发物料、现场条件与任务 | 清点、日报、问题、调试申请 | 本人负责现场的来货、今日记录、问题和交接 |
| 现场调试 | 单机 / 联调做到哪、什么阻碍验收 | 安装与派人交接、有效技术要求 | 调试记录、问题处理、验收申请 | 被派现场的调试工作与验收准备；当前与 SITE 的映射需进一步核对 |
| PM / 验收责任人 | 是否具备验收依据、客户确认后发生什么 | 资料包、调试与问题状态、客户签字依据 | 客户验收确认与质保起点 | 待准备 / 待确认事项与缺失依据，避免泛化为所有人可确认 |
| 售后 | 哪台设备出了什么故障、在保吗、谁处理 | 设备历史、质保与报修 | 服务工单闭环、备件与处理记录 | 本人 / 服务范围工单、下一动作和必要设备历史 |
| 财务 / 经营 | 财务：账款与成本怎样核对；经营：哪里要做决策 | 付款、成本、合同及项目风险 | 财务记录 / 管理决策 | 两者不能只因都能看驾驶舱就当同一首页 |
| 系统管理员 | 账号和系统配置是否正确 | 组织、权限与运行记录 | 可用的账号与配置 | 管理事项，不以超管业务画面定义其他角色体验 |

## 3. 四层范围必须分开

1. **待本人处理**：真实指派 / 审批链轮到本人，能执行具体下一步。
2. **本人负责范围**：未轮到本人处理也可能需要跟踪，例如 PM 的整个项目、经理的本组任务。
3. **必要协作上下文**：完成任务所需的设备、版本、上下游状态；可只读，但不因此暴露整份合同或所有其他项目。
4. **无关 / 敏感信息**：不提供无关浏览或写入口；金额仍按对应权限区分。

这只是设计框架。已补读 docs/05：历史口径明确是默认筛选且可协作打开链接。用户已于2026-10-06确认：首页聚焦本人职责，相关项目链接仍可协作查看；四层范围用于首页组织，不新增数据硬隔离。

特别需要核对：仓库 / 制造 / 发运的部分任务是共享队列，不能直接复制 Task.owner_id=本人；负责人为空也不等于无人负责。管理范围还要区分专业组、部门、仓库、项目与现场。

## 5. 接下来如何重构

先逐角色确认：触发事项 → 所需依据 → 允许动作 → 输出 → 接收人 → 失败 / 退回 → 完成后反馈。每个角色拿同一测试项目核对，不以“台能打开”替代职责验证。

产出角色体验规格：登录落点、首屏结论、事项排序、可见对象与字段、主要动作、必要上下文、无关内容、状态与文案。再形成登录到 S1 的分角色原型，其中销售交给 PM、PM 交给专业经理、经理派给组员是重点。原型可以重排现有结构，不受当前台头 / 指标条 / 页签骨架约束；但不恢复已明确取消的“我的工作台”聚合入口。

业务有歧义列具体场景让用户核对；页面组织与文字由设计主动给出。原型确认后才改路由、公共壳、查询范围及授权；范围规则落后端统一出口，前端消费一致结果，不能只藏按钮。

验收同时检查正向与反向：本人事项可办、必要上下文可看、无关内容不充当本人首页待办、非本人审批不可处理、经理 / 总监数据与组织相符、列表 / 深链 / 搜索 / 消息入口结果一致。之前的明确修复保留，其布局与文案仍可推翻。

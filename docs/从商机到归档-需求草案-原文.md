# 从商机到归档 — 系统需求梳理（原始草案）
本文档整理自内部讨论，目前仍是讨论阶段草案，后续会随实际情况调整、细化。

## 一、全局流程总览
商机 → 立项 → 工程设计 → 长周期件识别 → 采购 → 仓库 → 生产 → 装配 → 装箱发运 → 现场安装 → 调试 → 验收 → 售后 → 归档
核心原则：以设计BOM为主线贯穿全流程，各部门在同一份BOM上标记各自的状态，而不是各建各的清单。

## 二、各节点详细说明
1. 商机建档（商务部）
跟进过程本身很复杂，但不需要在系统里还原这个复杂过程，只需要一个"项目资料包"上传功能，把客户资料、合同、中标通知等所有资料上传进去即可
商机建立时生成一个订单号，作为贯穿全流程的主键——后续合同、立项、设计、采购、生产、发运、安装、售后都挂在这个订单号下；订单号一旦生成不再复用，即使商机作废也保留空置，不会被后续商机占用
系统操作只有两个结果：成交（自动进入立项，签订的合同作为附件挂在商机资料包里，不是单独的流程节点）或关闭商机（不做后续处理）
2. 立项启动
商机成交（即签订合同）后立项
立项不是"冻结版本"节点，而是"从粗到细"的切换点：前期方案是粗颗粒度（用于客户沟通），立项后才精细化
成立项目经理，项目经理与各部门负责人共同制定项目推进计划（时间节点、各部门产出）
3. 工程设计
按设备/子系统分组，组内并行工作，任务可再细分到个人
每人完成后提交BOM设计，需逐级审批（到总监）后才发布生效
工艺部门决定零件自制/外购；自制需报原材料需求
工艺部门汇总的整机BOM（如零件BOM+原料BOM汇总成一台设备的完整BOM）也需要总监审批
原材料需求审核通过后，先用仓库库存抵扣，缺口部分才生成采购需求（例：需10个方通，库存2个，采购需求=8个）
设计分批出图，不是一次性完成
长周期（长交期）物料：立项这个节点基本就能识别出来（不是100%准确，凭经验大概98%能确定），不需要等详细图纸
4. 采购
采购对象不只是原材料，还包括"商选件"（如马达、机器人、变频器等标准功能部件），这些也是设计BOM的一部分；商选件里只有一部分属于长周期件（例：一台设备20个商选件里可能只有1个机器人是长周期件，需提前预定，其余大多数商选件周期可控，走常规采购即可）
同一供应商可能同时供应多个项目的物料，系统需支持按供应商合并下单
同时需支持按项目/订单查看齐套率（哪些已到/在途/未下单），因为同时有多个订单在跑
需要系统辅助推荐/匹配物料对应供应商，减少人工逐项寻源
下单时收货地点需支持多选：可能是项目现场，也可能是某个仓库（公司有多个仓库）
下单前价格需要审批，不是采购专员单独决定，审批通过后才能下给供应商（工程BOM、整机BOM、采购价格分别由各自部门的总监审批——工程总监、采购总监、生产总监是不同人，不存在单点瓶颈）
需要多项目汇总看板：比如同时20个订单在走，总共要采购多少东西，按类型分类清楚（原材料多少、标准件多少、外协件多少、采购服务多少、辅材耗材多少），以及各类的状态分布（已下单/在途/待验收/已入库）
5. 仓库入库
验收有明确依据：原材料对照规格是否符合，定制件对照图纸是否正确；操作仍保持简单——合格直接拍照确认；不合格则点选问题类型，退给采购去跟供应商沟通
入库时拍照识别库位并记录
入库后通知生产可领料排产
6. 生产排产
生产任务是一个清单：某个工位/工序当天要处理的一批活，清单里的每一项可能来自不同订单，但每一项都清楚知道属于哪个订单/设备
任务安排后，把图纸+材料交接给第一道工序的人时需要拍照确认交接
每个零件有固定排产周期（如2天）；图纸+材料随工序流转，各工序负责人按周期交接
零件转运到装配区需拍照确认到位
系统需要能一目了然看到：今天的任务量是多少、整体生产情况如何
7. 装配
生产（零件加工）与装配是两道独立工序
装配人员可实时看到设备的零件到齐率（%）
装配完成后拍照记录实际已装配/未装配的零件（未装部分仍归属该设备）
需要多项目汇总看板：比如同时8个项目、30台设备在装配，每个项目多少台、各自齐套率如何，管理者据此安排人力
8. 装箱发运
装配（全部或部分）完成后打包，移至发运区
发运的装配完整度因工期/运输条件而异：工期紧或超长超重时可能以散件发出；条件允许时尽量在厂内先装配，减少现场难度
项目经理与客户确认进场时间，下达发货指令；叫车由采购负责
以"包"为单位打包（一个设备的零件可能分多包），逐包拍照生成发货清单
目前现场对账靠纸质单据，需改为系统化
9. 现场安装
现场收货逐包拍照验收
安装人员每天发送进度（照片/视频）
安装完成后需申请调试——调试是另一批人（工程师），不是安装的同一批人
10. 调试
公司工程师到现场调试，与安装是完全不同的人员
调试期间同样每天发送进度（照片/视频）
调试完成后需申请验收
11. 验收
项目经理带着调试的工程师一起到现场，与客户共同验收
验收后需要上传一个资料包，包含客户签名的验收通知书等资料
12. 售后
验收通过后进入质保期
客户发现问题发起工单，核实后派工程师处理
13. 归档
质保期结束后项目归档

## 三、贯穿全局的通用设计模式
状态确认统一组件：验收、入库、到装配区、装配完成、打包、收货、现场进度、调试进度——都是"拍照/视频+时间戳+人员+关联对象"的同一种动作，建议做成公共组件复用。
齐套率计算引擎：原材料齐套（库存抵扣算采购缺口）、订单采购齐套、设备装配齐套，算法一致（应到 vs 实到），不同层级复用同一套逻辑。
采购单的双重视角：供应商维度合并下单（效率）vs 项目维度查询齐套（可追溯），要求采购单明细行必须能关联到具体项目/BOM项。除采购和仓库外，其他所有人只关心项目维度的齐套率，不关心具体某张采购单——只有采购和仓库需要按单据(PO)操作，因为要按单验收、按单下给不同供应商。
发运的最小单位是"包"：装箱单管理的是包（可能含多个零件），现场对账按包进行，需要一层"包↔BOM项"的映射关系。
款项节点与物流节点联动：预收款、发货款、到货款、验收款、质保金，应设计为由对应的物流/进度节点触发的财务事件。
全程操作留痕：所有人在设计BOM下的每一个动作（什么时间、什么人、做了什么、附带的照片/视频）都要被系统记录，形成可追溯的操作日志。
BOM变更管理：设计BOM需要支持版本变更（会有多种原因触发变更），变更记录及影响范围需要清晰可查。
问题反馈关联BOM：所有人工作中遇到的问题需要能反馈和跟踪解决，但不是脱离项目的通用意见箱，而是关联到具体项目/BOM项——本质上是"发现问题→关联BOM→可能触发变更"这条链路的入口。

## 四、系统设计核心原则：极简操作
如果系统做不到让每个环节的人操作简单、一目了然，这个系统就白开发了。 具体要求：
每个人的操作和交互都要尽量简单，不做成复杂的大型系统
优先用"拍照/勾选/二选一"代替复杂表单和填写（如仓库验收：合格拍照，不合格点问题类型即可，不需要填一堆字段）
每个角色打开系统，应该能立刻看清"我今天要做什么、做了多少、还剩多少"，而不需要额外解读

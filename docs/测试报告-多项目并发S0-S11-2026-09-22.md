# 多项目并发 S0→S11 全链路真实走查报告

> 被测系统：同兴高科项目管理系统（txgketo）
> 测试日期：2026-09-22　|　测试类型：真实 HTTP 接口端到端 + 多项目并发 + 深度功能点
> 测试原则：**只走查记录、不修改任何应用代码**；驱动脚本见 `backend/scripts/multiproj_walkthrough.py`

## 一、测试目标与方法

**目标**：在"多个项目同时进行、每个项目都很复杂"的真实条件下，验证 S0 商机 → S11 售后的完整业务链、跨项目协作、并发健壮性与权限边界。

**方法**：

- **真实 HTTP**：对运行中的后端 `http://127.0.0.1:8208` 发起真实请求（非进程内 TestClient），真实 JWT、真实 multipart 文件上传、真实 PostgreSQL。
- **4 项目锁步推进**：4 个复杂度各异的项目按阶段同步前进，始终有多个项目在流水线不同环节共存。
- **每个动作 GET 回读校验**：写完立刻读回，核对状态/阶段/结论，异常一律登记，不中断其它项目。
- **并发专项**：多线程并行建项目、并行下单、并行合并同一需求、并发读接口。
- **深度覆盖**：主链之外再走约 80 个读写接口（发号、草稿/改版、采购动作、库位、资料下载、通知、代登录、改版 ECN 等）。
- **数据一致性核查**：直接查库核对编号唯一性、状态收口、库存非负、跨表引用。

## 五、关键场景验证（通过项）

### 5.1 主链与业务规则

- **发号**：商机 `TX{YY}{NNN}` 自动发号；立项即为每台设备自动生成总装图 `TX26009-01A-00-00-00-00`；同型第二台自动编 `01B`。
- **评审发布 = 冻结 + 采购触发**：经理提交直达「待总监审」→ 总监通过 →「已发布」；发布后按 BOM 自动进采购池，且**净需求**扣减在途/库存（长周期件已在途不重复买）。
- **物料三分与判定**：外协件、定制件（工艺改判）、标准件、原材料分别正确进池；采购池 8 条预期全部命中。
- **采购合并单**：合并下单多行共用一张 `po_no`；**跨项目**把 P1、P2 的轴承合并为同一张 PO26005。
- **分批到货**：轴承 4 件按 2+2 到货，首到后状态「部分到货」→ 齐后「已入库」。
- **验收不合格处理**：
  - 换货：方通不合格 → 采购协商「换货」→ 供应商补发 → 重验 → 入库。
  - 退货重采：板材不合格 →「退货」→ 自动新建 `退货重采` 需求回池 → **换供应商**（远东型材）重新下单 → 入库。
- **直发客户现场**：外协件直发 → 仓库验收生成「现场待验收」→ 现场按清单清点 →「现场已验收」，需求状态闭环。
- **制造（只管两头）**：按已发布图纸展开排产（总装图不排产）；机架不合格→返工→合格→转运；外协发出→回厂→验收合格。
- **装配与齐套率**：齐套率 = 100%（01A/02A/03A 及 P2/P3/P4），仅展示不设门槛；装配→厂内调试合格。
- **发运**：按设备结构自动生成发运清单；逐项勾「已发」+拍照；重复下发货指令被 400 拦；漏项清点被 400 拦；缺件签收留明细；发运后项目阶段自动「交付中」。
- **现场**：勘测、每日汇报（照片/视频）、现场问题立 ECN、申请调试→到现场→开始→联调日报→调试完成。
- **验收与质保**：资料包上传/签收 → 客户确认 → **自动进入质保期**（验收日 + 质保月数）；P4 回溯验收日 → 售后判定**过保**（`in_warranty=false`）。
- **售后**：备件建账/领出扣库存；工单 报修→派工→到场→处理（工时/照片）→客户签字关单。

### 5.2 权限与金额分档

## 六、发现的问题

### 问题 1（严重·数据丢失）· `PATCH /api/v1/suppliers/{id}` 会把未传字段清空

- **现象 1**：只想改一个字段（如 `rating`）会返回 **422**：
  `{"detail":[{"type":"missing","loc":["body","name"],"msg":"Field required"}]}`
- **现象 2（更严重）**：带上 `name` 再传（`{"name":"测试供应商-临时","rating":5}`）虽然返回 200，但**没有传的字段会被静默清空**：
  主营类别「标准件」→ 空、联系人「测试」→ 空、电话「13900000000」→ 空（审计日志如实记录为 `标准件 → —`）。
- **根因**：该路由用完整模型 `SupplierIn`（而非 `SupplierPatch` 类部分更新模型），并对 `body.model_dump()` 的**每一个字段**无条件 `setattr`；可选字段默认 `None`，于是没传的就写成空。
  对比：图纸/项目/组织/采购需求等 PATCH 均为部分更新（只改传入字段）。
- **影响**：前台只要漏传任何一个字段，就把已有资料（联系人、电话、账期、税率…）抹掉，且无二次确认；与系统其它 PATCH 行为不一致。
- **建议**：新增 `SupplierPatch`（字段全可选），仅对 `model_fields_set` 中出现的字段做更新（或 `exclude_unset=True`）。
- **证据**：走查「供应商改资料（只传 rating）」→ 422；带 `name` 提交 → 200，随后查库：`kind/contact_name/phone/remark` 均为 `None`；同一条 `audit_log` 记录了这三项被改成「—」。

### 问题 2（控制点存疑）· 设计产物（图纸 / 程序）无任何附件即可评审发布

- **现象**：新建 PLC 程序后**不上传任何文件**，直接提交评审 → 总监通过 → 状态「已发布」；此时 `GET /api/v1/programs/{id}/file` 返回 **404**（"还没上传程序文件"）。
- **范围**：代码核对后确认**图纸与程序同样**——提交评审（`review_flow` 的 `ITEM_DRAWING` / `ITEM_PROGRAM` 分支）只校验「当前是草稿」，不校验附件；发布环节也不校验。本次走查图纸恰好都先传了文件，所以只从程序上暴露出来。
- **影响**：可能存在"已发布但没有内容"的设计产物，下游（车间烧录/外协/售后）取不到文件。
- **建议**：评审提交或发布环节校验版本是否已上传文件；未上传则不允许发布（或在评审单标注"无附件"）。
- **证据**：走查「无文件程序发布后取文件」→ 404；代码 `app/services/review_flow.py` 提交/发布分支均无文件校验。

### 问题 3（数量控制）· 超额验收未被拦截或提示

- **现象**：采购需求订购 2 件，仓库验收时填 5 件 → **200 成功**，生成到货单 qty=5、状态「待入库」，采购需求进入「待入库」，系统无任何超额提示或封顶。
- **影响**：供应商超量到货、或误填数量时，系统照单全收（入库后库存按 5 计），缺少业务确认环节。
- **建议**：验收数量 > 未到数量时，要么拦截，要么要求填写超额原因/供应商确认，并留痕。
- **证据**：`purchase_request #40` qty=2 → `goods_receipt GR26029` qty=5（status 待入库）。

### 问题 4（测试工具过期）· 端到端脚本未跟上 S7 发运重构

- `backend/scripts/seed_s0_s1.py`：TRUNCATE 列表仍含已被删除的 `packing_list` 表 → 直接 `UndefinedTable` **无法运行**。
- `backend/scripts/e2e_full_test.py`：S7 仍调用已废弃的 `POST /shipping/{id}/pack`（重构后为 `/items/generate` + `/items/ship`），该脚本已无法跑通。
- **建议**：同步更新这两个脚本的表清单与发运接口调用。

## 七、观察与待确认（产品/口径）

1. **同型设备（01B）不继承设计**：`same_as` 生成的 01B 没有 01A 的图纸/BOM，因此**不排产、不装配、齐套率 0%、不参与发运**。若业务上同型设备需要各自交付，需明确"同型是否自动克隆设计"。
2. **合并单 `po_no` 多行共用属设计使然**（非缺陷）：`purchase_request.po_no` 一单多行，按 `po_no` 去重/求和时需按"单"而非"行"理解。
3. **总装图归属与发布**：每台设备立项即生成总装图（默认草稿），需被勾选进设计评审才会发布；本次已将总装图纳入机械评审，发布成功。建议在流程说明中明确"总装图必须随批发布"。

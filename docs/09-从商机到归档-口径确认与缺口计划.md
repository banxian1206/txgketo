## 0. 一句话结论

草案的**骨架**与现状一致 —— **以设计BOM为主线贯穿全流程**（各部门在同一份BOM上标各自状态）、**极简操作**（拍照/勾选/二选一）。
差异集中在三块：

1. **发运单元**：草案说"以**包**为单位"，裁决 = **按组件勾选**（现状），但**新增**"装配结果决定清单结构"（组装体）；
2. **发货指令**：裁决 = **一条跨部门指令**（PM 下指令 → 采购叫车 → 发运装车交付）+ **必须带时间**；
3. **6 个未实现缺口**（见 §3），其中 5 个要补、1 个否决。

## 1. 口径裁决（以现状为准 · 不再改动）

| # | 草案原文 | 裁决 | 现状实现 |
|---|---|---|---|
| 1 | 成交后**自动进入立项** | ❌ 不自动。**成交登记后停在「成交待立项」，需人工点击立项** | `PROJECT_STAGES` 含「成交待立项」；立项是独立动作 |

## 2. 新增 / 变更需求（客户新提，草案里没有或讲得不够）

### 2.1 装配结果决定发运清单的结构（组装体）

**客户原话**：

> 装配的时候，比如一个设备有 100 个零件，但我只装配了 80 个，那么发货时怎么发？那肯定是发这个装了 80 件的**组装体**，勾选这个就可以了。
> 装配完之后，清单其实就变成了**一个组装体 + 20 个零件**。发货的时候，就可以选择这个组装体和 20 个零件，勾选拍照进行发货。

**要点**：发运清单不能在装配完成后还按"100 个零件"平铺，要变成
**1 × 组装体（已装的 80 件，作为一个可勾选单元）+ 20 × 零件（未装的，仍单列）**。

| 项 | 内容 |
|---|---|
| 现状 | `shipment_item` 按结构自动生成（组件→子组件→零件 + 标准件/原材料），数量按结构连乘；勾组件 = 整棵子树 |
| 缺口 | **清单不感知"装配到哪一步了"** —— 装了 80 件之后，那 80 件仍然是散列的零件行 |
| 方案要点 | 装配完成（`assembly_record` finish）时，把**已装进组装体的零件子树折叠成一个「组装体」项**；未装部分保持单列。清单 = 组装体 + 剩余零件 |
| 裁决 | ✅ **已定（客户 2026-09-28）**：① **不纠结组装体的构成** —— 组装体就是清单里的**一项**，不必知道它由 80 个零件组成；② **现场清点不拆** —— 发的是「组装体 + 20 个零件」，收的也是「组装体 + 20 个零件」；③ **数量守恒**：设计 100 个零件全要采回来，装配后变成「1 组装体 + 20 零件」，合计仍是 100 |
| 落地要点 | ① 装配完成时登记**未装清单**（哪些零件还没装上，可拍照）—— 这是唯一需要新增的输入；② 发运清单生成时，把**已装部分折成 1 项「组装体」**，未装零件保持单列；③ 组装体**不展开**子件（清单里就一行） |

### 2.2 发货指令 = 跨部门指令 + 时间约束

**客户原话**：

> PM 发出指令需要**叫车服务**，**采购**就去采购车辆回来，**发运**就开始装车并进行交付。这相当于是一条指令，但是**指挥了两个部门**的人在干事情。
> 同时，这个指令也是需要有**时间**的，比如明确**什么时候发、什么清单的内容**。

**要点**：一条指令 → **两个部门的待办**（**以“发货日”为轴**）：

```
PM 定一个【发货时间：某一天】（依据：项目进度 + 装配进度 + 与客户沟通的进度）
        │
        ├─→ 采购待办：**当天**把车叫回来（按这个日期安排）
        │
        └─→ 发运/装货：当天需要装几车货，心里有数 → 装车 → 发运交付
```

| 项 | 内容 |
|---|---|
| 现状 | `POST /shipping/instructions` 下指令 → 生成批次 → 逐项勾「已发」→ 装车 → 发运。**没有"叫车"环节**，也没有"计划发运时间"字段 |
| 缺口 | ① 无车辆/承运商环节（采购不在链上）；② 指令无时间要求 |
| 方案要点 | 指令增 `plan_ship_at`（**计划发货日期，精确到天**）；下指令后**同时给采购与发运派待办**（各自工作台可见"今天要干嘛"）；采购登记车辆 → 发运才可装车 |
| 裁决② | ✅ **已定 · 时间颗粒度 = “天”**（客户 2026-09-28）：<br>① PM 根据**项目进度 / 装配进度 / 客户沟通进度**定一个**发货时间（如定在十几号）**；<br>② 采购**按这个时间，在当天把车辆采购回来**；<br>③ **装货的人据此知道当天需要装几车货** |
| 裁决① | ✅ **已定**：**车辆服务不进价格库，只填本次价格**（地方不同、车型不同、时间不同 → 价格必然不同，入价格库无意义）；只需知道“这次服务花了多少钱” |
| 待定 | 到点未叫车 / 未装车要不要提醒（可复用 §8.3 的超期扫描）—— **暂缓**；状态机怎么加（在 `SHIP_STATUS` 里加「待叫车」还是独立字段）—— 实现时定 |

## 3. 确认要补的缺口（5 补 + 1 否决）

### G1 ✅ 要补 · 项目归档

> **客户**："肯定是需要补的。质保期过了，那不就归档了嘛。"

- **现状**：`PROJECT_STAGES = ("线索","成交待立项","执行中","交付中","质保","已关闭")` —— **没有「已归档」**（只有改版单 ECN 有 `archived_at`）。
- **方案要点**：加终态「已归档」；质保期（`warranty_end`）到达 → 归档；归档后项目**只读**（要改先走变更/解归档）。
- **裁决** ✅ **已定 · 自动归档**（客户 2026-09-28）："归档是**自动**的。我们不是有一个质保期嘛，**质保期过了就自动归档**。"→ 复用 §8.3 已列的**超期扫描**（同一扫描器顺手把过期质保的项目置归档）。
- **待定**：① 是否要 `project:archive` 权限码（自动归档下可能只需人工**提前**归档的入口）；② 归档后还能不能看（能看，不能改）。

### G2 ✅ 要补 · 款项节点与物流节点对齐

> **客户**："这些节点要跟物流能够对上。因为我发了之后，就必须要**催商务部**的人去把这个款给拿下来。"

- **现状**：`PaymentTerm(node_name, amount, received_amount, received_date)` —— **纯手工登记回款**，不跟任何业务节点挂钩。
- **方案要点**：把付款节点**绑到业务节点**（发货 / 到货 / 验收 / 质保期），节点达成 → **自动提醒商务部**去收款（通知，不自动记账；回款仍人工登记，保持账实一致）。
- **裁决** ✅ **已定**：**只提醒商务，不卡流程** —— "我们已经发货了，你要收款了" / "我们已经验收了，你要收款了"，**挂在那就行**（提示还有多少未收款，提醒去收）。
- ✅ **已定（客户口径 2026-09-29）**：**预收款 → 立项**（"预收款的提醒是立项，立项之后就开始提醒"）；
  发货款 → 发货 · 到货款 → 到货 · 验收款 → 验收 · 质保金 → 质保。
  `PAYMENT_TRIGGERS = (立项, 发货, 到货, 验收, 质保)`；存量预收/预付已由迁移 `a3b5c7d91e02` 回填为「立项」。

### G3 ✅ 要补 · 问题反馈关联到 BOM 项

> **客户**："这是肯定的、必须的。他在装这个设备的时候，发现零件有问题，那他肯定是反映**这个零件**，或者是反映**这个设备的某个零件**，它是有归属的嘛。"

- **现状**：`SiteIssue(project_no, equip_no)` —— **只到设备级**，挂不到具体零件。
- **方案要点**：`SiteIssue` 增 `drawing_no`（图号=物料号）/ `item_no` / BOM 行引用；建问题时可选"是哪台设备的哪个零件"；现有「**问题 → 改版(ECN)**」链路自然接上（`link-change`）。
- **待定**：① 是否**车间/装配端**也要能建问题（不止现场）；② 页面从哪进（现场问题页 / 设备设计面）。

### G4 ✅ 已澄清 · 「商选件」= 标准件

> **客户**："这个商选件，它就是我们的**标准件**。"

- **结论**：**不新增类别**。马达/机器人/变频器等就是标准件；草案里"商选件里只有一部分是长周期件"→ 对应我们"标准件里长周期件在立项时登记"。
- **动作**：文档记一句口径即可，**无代码改动**。
  > ⚠ **2026-10-07 更新**：长周期件**不再「立项即下单」**，改为**进采购池、由采购下单**（客户实测 TX26005；见 `AGENTS.md §8.1/§8.2`）。本条其余结论（不新增类别）仍只适用。

### G5 ✅ 要补 · 多项目采购齐套率（**多视角**）

> **客户**："肯定是按照文档里面的。多个项目会同时运行，采购池里面会看到多个项目的东西…可能会**合并成一个采购单**给到一个供应商去采购。
> 但系统需要能**清清楚楚地展示**以下信息，因为**其他人就是看这些数据的**：
> 1. 这个项目**买了多少东西回来了，已经验收入库了多少**；
> 2. **还有多少在途**；
> 3. **还有哪些是没买的**。
> 比如我是一个 PM，我就看这个项目**买了多少、在途多少、入库多少、生产领料了多少、已经装配了多少**。所以这是一个**多视角**的展示。"

**客户追问（2026-09-28）**："**其他人基本上都是按照项目去看齐套情况的**。比如整个项目我要买 200 个零件：是还没有买，还是在途，还是验收已入库，还是说**已经做成了成品（即组装件）**？
其实**只有采购和仓库**这两个人，他们是**看采购单，按照单**去看这个物件。他们可以不用看项目的视角，但是**如果有，那肯定是最好的** —— 因为也有人会问你这个项目的这个件有没有验收、有没有入库、有没有被领走，他们也是需要查的。"

- **现状**：采购池是**单项目**口径；齐套率有（`assembly/kitting`），但**没有跨项目汇总**，也**没有"单据视角"的对照**。
- **方案要点**（两个视角，**项目视角为主**）：
  - **项目视角（主）**：单项目 200 个零件的齐套状态分布 —— **未买 / 在途 / 验收已入库 / 已领料 / 已做成成品（组装件）**；
  - **单据视角（采购 / 仓库的日常工作台）**：按**采购单（PO）**看物件（因为要按单验收、按单下给不同供应商）；**同时保留项目筛选**（别人来问"这个项目的这个件验收/入库/领走没有"时能查）。
  - **跨项目汇总**：采购池会同时看到多个项目的东西，可能**合并成一张单**给同一供应商。
- **裁决** ✅ **已定**（客户 2026-09-28）：**项目视角为主、单据视角为采购/仓库专用，两者都要**；齐套状态**必须含「已做成成品（组装件）」**这一态（接 §2.1）。
- **待定**（实现细节）：口径以**数量**还是**项数**为主（倾向两者都给）；是否按供应商归拢（配合"合并下单"）。

### G6 ✅ 要补 · 入库拍照识别库位（OCR）

> **客户**："我们肯定是要**拍照识别**啊。上面明明有编号，明明有那些东西，为什么不能直接拍照识别，非得要手选呢？"

- **现状**：入库**手选库位**（03 卷有 OCR 能力，但这条链路没接）。
- **方案要点**：对**库位码**（如 `A-03-12`）拍照 → **大模型识别** → 出候选 → **人工确认后写入**（铁律 7：OCR 永远只作候选）。
- **裁决** ✅ **已定 · 不做固定版式**（客户 2026-09-28）："其实它是要靠**大模型**去识别的。**没有固定的版式，大模型用 OCR 可以直接识别**。"→ 不要求现场库位牌定版式，直接交给多模态模型。
- **待定**（实现细节）：识别不到时的兜底（仍可手选）+ 是否"记住上次"（同库位连续入库）。

### G7 ❌ 否决 · 整机BOM 由"生产总监"审批

> **客户**："没有生产总监没有关系，因为我们生产不需要审评，也没有审评这个概念，所以就没有必要去审评。也就是说，**目前为止，审评只有在工程和采购这里有**。"

- **结论**：**不补**。审评口只有**两处**：
  - **工程**：设计评审（图纸 / 设计BOM / 材料BOM / 程序），二级到**工程总监**；
  - **采购**：采购下单前的**价格审批**，二级到**采购总监**。
- **动作**：**写入铁律级口径**（防止以后有人照草案去加"生产总监"）。草案 §4 那句"工程/整机/采购价分别由工程总监、生产总监、采购总监审批"**作废**。

| 批次 | 内容 | 理由 |

### 7.3 流程会改成什么样子

#### ① 发货（S7）—— 变化最大

**现在**
```
项目经理在发运台：勾清单项「已发」 → 一次装车（填车牌/司机） → 发运 → 到货 → 现场清点
                （采购不参与；没有"叫车"；没有计划发货日）
```
**改后**
```
PM 定【发货日：某一天】（看项目进度 + 装配进度 + 客户沟通）
      ↓ 下达发货指令（含：发哪些清单内容 + 发货日）
      ├─→ 【采购】待办：当天把车叫回来（登记车辆数 / 承运商 / 本次运费）
      └─→ 【发运/装货】待办：知道"当天要装几车" → 装车 → 发运 → 到货 → 现场清点
```
- 新增状态：指令后 = **待叫车**（或独立字段）→ 车辆就绪 → 已装车 → 在途 …
- 采购工作台**多一个待办**；发运台的"装车"前置条件从"有已发项"变成"有已发项 **且** 车辆就绪"

#### ② 发运清单（S6→S7）

**现在**
```
BOM 结构 → 清单：组件 / 子组件 / 零件 / 标准件 / 原材料（数量按结构连乘）
装配完成 → 只影响"哪些设备可发"，清单结构不变
```
**改后**
```
装配完成时登记【未装清单】（哪些零件还没装上，可拍照）
      ↓
发运清单 = 【1 个组装体】 + 【未装的 N 个零件】
      ↓
发货勾选：✔ 组装体  ✔ 20 个零件  → 拍照
现场清点：同样只点「组装体 + 20 个零件」（不拆）
```

#### ③ 齐套率 / 看板（S3–S6）

**现在**
```
GET /assembly/kitting?project_no=xxx   （project_no 必填，单项目）
状态：已入库 / 已到货 / 已下单在途 / 未采购（+ 自制件 已转运 / 未排产）
采购池：能看到多个项目的东西，但没有项目筛选、没有按项目汇总
```
**改后**
```
【项目视角（主）】整个项目 200 个零件 →
   未买 / 在途 / 验收已入库 / 已领料 / 已做成成品（组装件）
【单据视角（采购·仓库）】按采购单看物件（他们日常工作），但保留项目筛选（别人来问也能查）
【跨项目汇总】同时 5 个项目在跑 → 按项目 × 类型汇总数量与状态分布
```

#### ④ 入库（S4）

**现在**：仓库入库 → **手选库位** → 记库存 + 流水
**改后**：仓库入库 → **拍照（大模型识别库位码）** → 出候选 → **人工确认** → 记库存 + 流水

#### ⑤ 问题反馈（S8/S5）

**现在**：现场问题 = `项目 + 设备`（设备级）→ 可关联改版单（ECN）
**改后**：现场问题 = `项目 + 设备 + 具体零件（图号/物料号）` → 关联改版单（链路不变，粒度变细）

#### ⑥ 收款（S10/S11）

**现在**：付款节点只在成交登记时录入；回款**手工登记**；**没有任何提醒**
**改后**：付款节点绑业务节点 → **发货了 → 提醒商务"该收发货款了"** / **验收了 → 提醒"该收验收款了"**（**只提醒，不卡流程**）

#### ⑦ 归档（S11）

**现在**：项目阶段止于「已关闭」；质保期到了**什么都不发生**
**改后**：质保期过 → **自动归档**（阶段 = 已归档，只读）
> ⚠ 架构点：本系统**不许用 Redis / 消息队列 / K8s**（技术栈铁律），目前**也没有调度器**（`main.py` 只有 startup hook）。
> 所以"自动归档"要么做成**惰性扫描**（读项目/登录时顺手判定），要么加一个**进程内定时线程** —— **实现时要定**（现状：超期都是读时算的）。

### 7.4 一句话总结

**没有"方向性冲突"** —— 草案的骨架（BOM 为主线、极简操作）与现状一致，§1 的 5 条裁决还把草案里最矛盾的地方（按包、多选收货地、自动立项、工序报工、生产总监）都按**以现状为准**钉死了。
真正的改动集中在三块：**S7 发货（加采购叫车 + 发货日，动状态机）**、**发运清单（组装体）**、**齐套率（加"已做成成品" + 多视角）**；
其余 4 项（归档、款项提醒、问题关联零件、库位 OCR）都是**加字段/挂钩子**，不动主干。

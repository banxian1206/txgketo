## 0. 一句话

把「采购单」从一个**用 `po_no` 字符串 GROUP BY 凑出来的视图**，改成**真正的实体表**，
从而修掉 3 个会丢数据/丢语义的洞，并挂上审批、付款、交期留痕三块新能力。

## 1. 客户口径（2026-09-24 确认，★ 需求唯一来源）

| # | 问题 | 客户答复 |
|---|---|---|
| 1 | 一条需求会不会拆给多家供应商？ | **很有可能会拆给多个供应商** |
| 2 | 供应商付款要不要管？ | **付款流程可以不管，但付款记录必须有** —— 跟供应商的交易往来明细要能查 |
| 3 | 采购要不要审批？ | **要，采购经理 + 采购总监两级审批** |
| 4 | 整单运费/税点要不要？ | **肯定要有** |
| 5 | 供应商要不要有账号？ | **不给供应商开权限**。采购下单后**默认供应商即接单**；交期由采购填，**实际交期以仓库验收为准，必须留痕** |
| 6 | 审批是全部还是按金额阈值？ | **审批是必须的，不管金额多少都要走**。金额异常只是**辅助审核的信息**，不是门槛 |
| 7 | 金额异常怎么判？ | **不设系统阈值，由历史采购价格决定**：把「平均价 / 上次购买价 / 历史区间」显示出来，让审核人自己看清楚判断（例：本次填 10 元，历史 8~9 元 → 一眼看出偏高） |
| 8 | 审批期间需求算什么状态？ | **「审批中」** |
| 9 | 超拆（下单总量 > 需求量）拦不拦？ | **必须硬拦** |
| 10 | 单价含税口径谁定？ | **由采购员选定，而且必选**（填价格时必须声明这个价是含税还是不含税） |
| 11 | 财务付款怎么走？ | 财务**按采购单**付款（20 张单可能只付其中 10 张）→ 财务通知采购 → 采购通知供应商确认到账 → **采购在后台把这 10 张单标记「已付款」+ 上传付款截图** |
| 12 | 一单会不会分多次付？ | **基本不会，一个单付一次** |
| 13 | 付款要能查什么？ | 假设某供应商 100 张单、付了 80 张：必须能清楚知道 **① 哪 20 张没付 ② 哪 80 张付了、什么时候付的** |
| 14 | 审批退回怎么办？ | **回草稿，改了重提**，不作废重下。★ 理由：*"采购单不是采购部决定的，是上游部门决定的，我们只负责采买"* |
| 15 | 分批到货怎么算？ | 两种情况都要支持：**①** 送 100、验收合格只有 80 → 收 80，20 退回重送；**②** 只有 80 货，第一批送 80、第二批送 20，分批验收。**采购单上要有拆分记录** |
| 16 | 采购单能不能作废？ | **能作废、能关闭** —— "确实不跟你合作了，整批退给你" |
| 17 | 审批人账号 | 后台配两个演示账号：**采购经理 + 采购总监**（现在都是演示数据，没有真实数据） |

## 2. 现状的三个洞（重构的必要性证据）

### 洞 ①：拆单会**丢需求**（最严重）★ 已实测

**实测**（`/tmp/txgk_e2e.py` 探针 B1）：新建板材需求 `qty=100` → 下第一张单给甲钢材 60 个：
```
第一张单后：qty=60.0  status=在途  po_no=PO26004      ← ★ 需求数量被改成 60
第二张单（乙标准件 40）→ HTTP 400
   {"detail":"YL-BC-0001 当前状态是「在途」，不能合并下单"}
最终：qty=60.0，落在 1 张单上（{'PO26004'}）        ← ★ 剩下 40 个蒸发
```

```python
# api/routes/initiation.py:1942  merge_order()
if ln.qty:
    row.qty = ln.qty          # ★ 直接覆盖需求数量
row.status = "在途"
```

现有绕法只有「退货重采」异常路径或手工新建需求，都不是正常业务该有的样子。
**客户口径 #1 明确「很有可能会拆给多个供应商」→ 这是必修项，不是优化项。**

### 洞 ②：部分合格**表达不了**

```python
# AcceptanceIn (initiation.py:1127)
result: str = Field(..., description="合格 / 不合格")   # ★ 整批二选一，无「合格数量」
```

送 100、合格只有 80（客户口径 #15 情况①）：
- `qty=100, result=合格` → 100 全进待入库（**错，20 个是废的**）
- `qty=100, result=不合格` → 100 全退回（**错，80 个是好的**）
- 绕法：验两次（80合格 + 20不合格）→ 能过超额硬拦，但**两条到货单互不关联**，看不出是同批 100 个里挑出 20 个不合格，且 `arrived_at` 被第二次覆盖

### 洞 ③：三处「代码在替数据库兜底」

| 位置 | 代码 | 问题 |
|---|---|---|
| `_order_summary` | `supplier_id: first.supplier_id if len(suppliers)<=1 else None`<br>`supplier_name: … else f"{len(suppliers)} 家供应商"` | 一张单**业务上不可能有两个供应商**，但数据库允许，代码发现后用 UI 圆过去 → **数据不一致被合法化** |
| `_order_summary` | `deliver_to: first.deliver_to` | `first = active[0]`，**任取一行**。行不一致时静默取错 → 直发现场的货可能被显示成进仓库 |
| `_order_rows` | `if key.startswith("R") and key[1:].isdigit():` | API 主键是合成 key（`po_no` 或 `R{行id}`），**没有实体却当实体用** |
| `_order_summary` | `max(ordered_at)` / `min(expected_date)` | 发明出来的聚合语义 |

对照 `AGENTS.md` 铁律 3 的思路（*"这条 CHECK 约束是防串项的核心，不要绕过"*）：**能用约束挡的，不要用代码挡**。现在正好反了。

### 附带：现在**根本没地方放**的东西

供应商付款记录 · 整单审批 · 运费/折扣/税率 · 采购订单附件 · 供应商确认/交期留痕 · `goods_receipt.po_id`（02 卷原本设计了，实现时挂的是 `request_id`，导致每次都要 `_receipt_qty_map` 反查聚合）

### 附带：性能

`list_purchase_orders` 每次把 `PurchaseRequest` + `Item` + `Project` + `Equipment` **全表拉进内存**做 Python group by。30 人规模暂时没事，但这是 O(全表)/每次翻页。

## 3. 目标数据模型

```
purchase_order（单头）1 ──┬── N purchase_order_line（单行）N ── 1 purchase_request（需求）
                          │        ★ 一条需求可拆到多张单的多行
                          ├── N purchase_approval（审批留档，多轮多级）
                          └── N goods_receipt（到货单，挂 po_id + line_id）

purchase_request 1 ── N goods_receipt（保留，行级到货）
supplier         1 ── N purchase_order（★ 一单一供应商，FK 天然保证）
```

**换算规则**（`tax_incl` 决定方向）：
```
tax_incl=True  → amount_tax_incl = qty × unit_price
                 amount_tax_excl = amount_tax_incl / (1 + tax_rate/100)
tax_incl=False → amount_tax_excl = qty × unit_price
                 amount_tax_incl = amount_tax_excl × (1 + tax_rate/100)
单头 total_* = Σ 行 amount_*  − discount + freight
```

#### ⚠ `expected_date` 为什么必须留在需求上（我第一版方案写错了，已修正）

它现在撑着三件事，删了会连带坏掉：

| 用处 | 位置 |
|---|---|
| **到货跟踪的排序键** | `warehouse.py:569` `.order_by(PurchaseRequest.expected_date)` |
| **超期风险判定** | `initiation.py:1596` `overdue = expected_date > need_date`（预计到货晚于需要日期 = 红） |
| ★ **换货时被重算** | `initiation.py:2423` `r.expected_date = _resolve_expected(body.expected_date, None, r.lead_days, base=today)` |

第三条是关键：**换货是「需求行级」动作，不是「整单级」**。一条需求拆到甲60/乙40，只有甲那 20 个不合格要换货 —— 重算的是甲这一行的预计到货，跟乙无关，也跟整单承诺交期无关。

**所以三层都要有，语义不同**：

```
purchase_order.expect_date      = 跟供应商约定的【整单承诺交期】（审批时看的、算 delay_days 用的）
purchase_order_line.expect_date = 【本行预计到货】，可被换货重算覆盖
purchase_request.expected_date  = 【派生】= min(该需求所有有效 po_line.expect_date)
                                  ↑ 到货跟踪排序、overdue 判定继续用它，前端不用改
```

`need_date`（需要到货日期，上游定的）继续留在需求上不动 —— 它是需求侧的事实，不属于采购单。
| **加** | `qty_ordered` num(14,3) | 已下单数 = Σ 有效 `po_line.qty`（**派生，落库便于查询**） |
| **加** | `qty_rejected` num(14,3) | 累计不合格数 |
| **保** | `qty` | ★ **恢复为纯净需求数量，任何下单动作都不许改它**（修洞①） |
| **保** | `qty_received` · `arrived_at` · `status` · `need_date` · `lead_days` · `attribution` · `requester_id` · `part_no` · `source` · `source_release_id` · `origin_request_id` | |

### 3.6 `supplier_quote` 改动（★ 容易漏，但必须同步）

| 动作 | 字段 | 理由 |
|---|---|---|
| **加** | ★ `tax_incl` bool | 否则历史价格库口径混乱，审批页的「历史均价」会把含税价和不含税价混在一起算 → **凭空报出 13% 的涨幅**，审核人被误导 |

> 存量 `supplier_quote` 迁移：`tax_incl` 默认回填 `true`。★ **客户 2026-09 确认：现存均为测试数据，直接标「含税」，无需人工过一遍。**

## 4. 状态机

### 4.1 采购单 `purchase_order.status`

```
草稿 ─提交─► 待经理审 ─通过─► 待总监审 ─通过─► 已批准 ──► 执行中 ──► 已完成
  ▲            │                  │              (★视为供应商接单)   │
  │            └─退回(必填说明)────┘                                  │
  └──────── 已退回（回草稿，改了重提，round+1，全部留档）              │
                                                                      │
草稿/已退回 ─撤销─► 已作废（★ 所有需求行回「待采购」回池）              │
已批准/执行中 ─整批退货─► 已关闭（★ 到货单全转「已退货」，需求回池重采）┘
```

| 状态 | 含义 | 可做的动作 |
|---|---|---|
| `草稿` | 采购员在填，还没提交 | 编辑全部字段、提交、作废 |
| `待经理审` | 一级审批中 | 经理通过/退回；提交人撤回 |
| `待总监审` | 二级审批中 | 总监通过/退回；提交人撤回 |
| `已退回` | 被驳回，回草稿态 | 编辑、重提（`round+1`）、作废 |
| `已批准` | ★ **两级通过 = 供应商接单**（客户口径 #5，供应商无账号） | 开始执行；整批退货关闭 |
| `执行中` | 已有到货 | 收货验收；整批退货关闭 |
| `已完成` | 全部到货入库完毕（派生） | 只读；标记付款 |
| `已作废` | 未执行就取消 | 只读（需求已回池） |
| `已关闭` | 整批退货、不再合作（客户口径 #16） | 只读 |

★ **清单锁死线**：`已批准` 之后单头的供应商/收货地/交期不可改（要改走「更改供应商」动作或作废重下）；行的价格任何时候不可改（改了审批就白审了）。

### 4.2 ★「审批通过才发生」的三件事（现在都是下单瞬间发生，必须往后挪）

| # | 事件 | 现在 | 改为 |
|---|---|---|---|
| 1 | 需求状态 `待采购` → `在途` | `merge_order` 里立刻置 | **总监通过后** |
| 2 | 直发客户现场 → 建「现场待验收」到货单 | `_ensure_site_pending_receipt` 下单即建 | **总监通过后** |
| 3 | 成交价落价格库（`supplier_quote price_type='成交'`） | 下单即写 | **总监通过后**（未批准的价不是成交价，会污染历史均价） |

### 4.3 采购需求 `REQUEST_STATUS` 改动（★ 枚举即契约）

```
现在：待采购 · 在途 · 现场待验收 · 待入库 · 部分到货 · 已入库 · 现场已验收 · 不合格 · 已退货 · 已取消
新增：★ 审批中 · ★ 部分下单
```

```
待采购 ─下单(建PO草稿并提交)─► 审批中 ─两级通过─► 在途 ──► 部分到货 ──► 已入库
                                  │                                      现场待验收 → 现场已验收
                                  ├─退回─► 待采购（PO 回草稿，需求解锁可改下别家）
                                  ├─作废─► 待采购（★ 需求回池，绝不能死）

```

| 新状态 | 判据 | 说明 |
|---|---|---|
| `审批中` | 有 PO 处于 `待经理审`/`待总监审`/`已批准(未生效)` | 客户口径 #8 |
| `部分下单` | `0 < qty_ordered < qty` | ★ 拆单后必须有，否则剩下的量没人管 |

⚠ 改这两个状态必须同步 `tests/test_status_contract.py`（AGENTS §8.1：*"状态枚举 = 契约，否则就是实现跑出了契约里没有的状态"*）。

### 4.4 到货单 `RECEIPT_STATUS`

**枚举不变**（`现场待验收 · 待入库 · 已入库 · 现场已验收 · 不合格 · 已换货 · 已退货`），

### 5.3 审批人能看到什么（★ 客户口径 #7 的核心）

审批页每一行**直接内嵌**价格参考（数据源 = 现有 `GET /purchase/price-reference/{item_no}`，**无需新算法**）：

```
┌────────────────────────────────────────────────────────────────────────────┐
│ 方通 Q235 40×40×2.0 (YL-FT-0001)     本次 60 个 @ ¥10.00 含税              │
│                                                                            │
│  历史成交（同口径·含税）： 上次 ¥9.00（2026-08 · 甲钢材 · 买 5000 个）      │
│                           平均 ¥8.50   区间 ¥8.00 ~ ¥9.00   样本 6 笔      │
│                           明细：8.00(5000个·甲·03月) 9.00(200个·乙·08月) …  │
│  各家最新报价：           甲 ¥9.20 · 乙 ¥8.80 · 丙 ¥10.50                  │
│  ⚠ 本次 ¥10.00 高于历史最高 ¥9.00                                          │
└────────────────────────────────────────────────────────────────────────────┘
单头汇总：本单 12 行，其中 3 行超出历史区间 · 2 行无历史参考（新物料）
```

**设计原则（客户口径 #7）**：
- ❌ **不设系统阈值、不做红黄分级评分、不做配置表** —— 客户明确说"先不用系统去设定阈值"
- ✅ **只摆事实**：上次价 / 平均价 / 历史区间 / 样本数 / 每笔成交的数量与供应商 / 各家报价
- ✅ 让审核人自己判断（与本项目「齐套率只展示不设门槛」「OCR 只作候选」「AI 助手只读」同一哲学）

**★ 同口径分列（客户 2026-09 确认，替代原「过滤」）**：含税价与不含税价**不能混在一起算**。比价区**分两组并排摆**：
- **含税组**：上次 ¥X（含税）· 平均 ¥A · 区间 ¥min~¥max · 样本 N 笔
- **不含税组**：上次 ¥X（不含税）· 平均 ¥A · 区间 ¥min~¥max · 样本 N 笔
- **本次报价**标明自己的口径，**只跟同口径那一组**比；某组样本不足 2 笔时明确写「历史样本不足」，不硬凑。
- **「上次价格」任何地方出现都必须带口径**，如「上次 ¥9.00（不含税，2026-08·甲钢材·买 5000 个）」。

> `tax_incl` 在录入时**必选**（见 §3.6），历史新数据都带标记，所以分列是可靠的。

**已知局限（先接受，不解决）**：不按数量档位分段统计。缓解方式 = **每笔历史成交都显示数量**（`supplier_quote.qty`，见 §3.6），审核人看到「8.00 元（买 5000 个）」自然知道跟本次 60 个不可直接比。这比引入分段算法更符合"摆事实"路线。

`⚠ 本次高于历史最高` 这类提示属于**待点头项**（§14）：它是客观事实对比（10 > 9），不是人为阈值，但确实带了"判断"色彩。

### 5.4 审批页可改什么（★ 客户口径 #14 的深层含义）

客户原话：*"采购单不是由我们采购部门决定的，而是由上游部门决定的，我们只负责采买"*

| 草稿/已退回时可改 | ★ 任何时候都不可改 |
|---|---|
| 供应商 · 单价 · 含税口径 · 税率 · 承诺交期 · 收货地点/地址 · 运费/折扣 · 备注 · **行的数量拆分** · 增删行 | **物料（item_no）** · **需求总量（request.qty）** · 零件归属（part_no） |

采购若发现**需求本身有问题**（物料选错、数量算错）→ 不是采购改，而是**退回上游走改版 ECN**（`change_request`），符合铁律 4「一切改动都是变更，必须走审批」。
→ 审批页需要一个「需求有误，退回上游」的出口（提 ECN 或退回需求），这是**待点头项**（§14）。

## 8. ★★ 第 0 期地基：数量口径与净需求（V2.0 新增，实测驱动）

> 这一节是 V2.0 相对 V1.0 最大的改动。实测证明：**不先修这里，建表也没用** ——
> 单行 `purchase_order_line.qty` 的值本身就是错的。

### 8.1 ★ 同一个「要几个」，六个通道六种答案（实测）

测试用 BOM 树（刻意构造 `qty>1`）：总装(qty=1) → body 组件(qty=2) → 定制底板(qty=3) / 外协罩壳(qty=1) / BOM标准件轴承(qty=4) / BOM原材料方通(qty=5)

| 物料 | 真实需求 | ①发布进池<br>`release_demand` | ②手动补跑<br>`equipment_demand` | ③排产<br>`manufacturing` | ④齐套率<br>`kitting` | ⑤领料<br>`generate_issue` |
|---|---|---|---|---|---|---|
| 定制底板（图纸·定制件） | **6** | 6 ✅ | **18** ❌ 平方 | — | **3** ❌ | — |
| 外协罩壳（图纸·外协件） | **2** | 2 ✅ | 2（但重复进池）❌ | — | **1** ❌ | — |
| 轴承（BOM 标准件） | **8** | 8 ✅ | 8 ✅ | — | **4** ❌ | **4** ❌ |
| 方通（BOM 原材料） | **10** | 10 ✅ | 10 ✅ | — | **5** ❌ | 10 ✅ |
| body 主体组件（自制件） | **2** | — | — | 2 ✅ | 2 ✅ | — |

> **★ 第 6 个通道（2026-09 补测发现，本文初稿漏了）**：`shipping.generate_items`（发运清单）也用 `cum`。
> 它的 **BOM 行正确**（`b.qty × cum[parent_ref]`），但 **图纸件用的是原始 `d.qty`**（不是累计）——
> 与它自己的注释「数量 = 结构连乘」相矛盾（同一棵树里 body 下三级零件只显示 3 而不是 6）。已一并接入 `bom_math`。

**五个不同的错法（含第 6 通道）：**

| 通道 | 代码 | 错在哪 | 修法（已落地 `bom_math`） |
|---|---|---|---|
| ② `equipment_demand` **图纸分支** | `float(d.qty) * cum.get(d.drawing_no, 1.0)` | `cum[X]` 已经 = `X.qty × cum[parent]`（含自身），**又乘一次 → qty²** | `drawing_demand(d, cum)`（= `cum[d]`，不再乘自身） |
| ④ `kitting` | `need = _qty(d.qty) or 1`（图纸）、`_qty(b.qty) or 1`（BOM行） | **完全不乘父级累计** → 一律少一半 | 图纸 `drawing_demand`；BOM 行 `bom_line_demand` |
| ⑤ `generate_issue` **标准件分支** | `need[child] += _qty(b.qty)` | **完全不乘** | 与原材料分支合并，统一 `bom_line_demand(b, cum)` |
| ⑤ `generate_issue` **原材料分支** | `qty = b.qty * parent.qty` | **只乘直接父件一层** → 三级以上必少领（本例两级树恰好对） | 同上 |
| ⑥ `shipping` **图纸件分支** | `"qty": float(d.qty or 1)` | **不乘父级累计**（其 BOM 行分支本来就对） | `drawing_demand(d, cum)` |

> ★ **为什么潜伏至今**：`qty=1` 时 `1²=1`、`1×任何数=任何数`，四个错法全部隐身。
> 现实里绝大多数图纸 qty=1；一旦出现 `qty>1` 的组件（非标设备里很常见：一套 2 个工位、4 个夹爪），
> **采购超买 3 倍 / 齐套率虚高 / 车间少领一半料** 同时发生。
>
> ★ **齐套率虚高实测**：`kitting` 返回 `rate=1.0, arrived=5/5, qty 15/15`，而真实总量应为 `2+6+2+8+10 = 28`。
> **显示 100% 齐套，实际只到了一半多** → 装配按它开工会停线。

**结论：必须抽出单一口径模块**（本期核心交付物，★ **已落地**）：

```
services/bom_math.py（新）
  cumulative_qty(drawings) -> dict[drawing_no, float]   # 唯一的累计倍数算法
  drawing_demand(drawing, cum) -> float                  # 图纸件 → 真实需求（cum[d]，别再乘自身）
  bom_line_demand(bom_row, cum) -> float                 # BOM 行 → 行数量 × 父件累计
  scaled_qty(qty, parent_ref, cum) -> float              # 发布批次条目（dict）用
  is_ready(have, need) -> bool                           # 通用「到位」判定（stock+issued ≥ need）
```

**六个通道全部改为调用它**：`bom_demand`（①②）、`manufacturing`（③）、`kitting`（④）、`warehouse.generate_issue`（⑤）、`shipping`（⑥）。
配单测（纯函数，不需要库）：`tests/test_bom_math.py`（12 项）、`tests/test_bom_demand.py`（净需求抵扣 10 项）。

### 8.2 ★★ 净需求缺一项抵扣 → 四种场景重复进池（实测）

**根因（一句话）**：`_cover` 的抵扣只有两项 —— **当前库存** + **`OPEN_STATUS` 里的在跑需求**。
**完全没有「已完成的采购需求量」这一项。**

```python
OPEN_STATUS = ("待采购", "在途", "已下单", "待入库", "部分到货", "不合格")
#              ↑ 不含 现场待验收 / 现场已验收 / 已入库
cover = max(stock, 0.0) + open_qty
```

于是**货一旦离开库存，系统就认为「从来没买过」**。离开库存有三条路，三条都已实证：

| 场景 | 隔离项目 | 实测数据 | 后果 |
|---|---|---|---|
| **A 直发件完成后** | TX26001 | 发布进池 6（正确）→ 下单直发 → 现场清点「齐」→ 需求 `现场已验收`、库存 `0`（直发从不入库）→ 手动补跑 `need_qty=18, covered_qty=0, created=1`，**新增 qty=18** | 一次多买 18（真实 6，已买 6 → 共 24，**4 倍**）；★ 同时命中 qty² |
| **B 验收合格未入库** | TX26002 | 发布进池 8（正确）→ 下单 → 验收合格**不入库** → 需求 `待入库`、`qty_received=8`、库存 `0` → 补跑 `need_qty=8, covered_qty=0`，**新增 qty=8** | 完全重复一倍。<br>机制：`qty_received` 含 pending → `_open_qty` 的 `remaining = 8−8 = 0`；货又没入库 → **两头都不覆盖** |
| **C 已入库+已领走** | TX26003 | 发布进池 10（正确）→ 入库（库存 10）→ 领料领走 5 → 库存剩 5 → 补跑 `need_qty=10, covered_qty=5`，**新增 qty=5** | 共买 15，真实只需 10 |
| **D 综合** | TX26001 | 发布进池后**立刻**手动补跑，一次新增 **4 条**：定制底板×12、外协罩壳×2、方通×10、轴承×4 | 违反 AGENTS §8.1「幂等，重复点不会重复进池」 |

**幂等承诺为什么失效**：AGENTS §8.1 写的是「已冻结 BOM 展开 − 库存 − 在跑需求（幂等）」。
幂等成立的**隐含前提**是「货要么在库存里，要么在跑」—— 这个前提在上述三种情况下都不成立。
**即：幂等只在「刚发布、还没开始执行」时成立；一旦进入执行期，每点一次就多买一批。**

**修法（本期核心）**：`_cover` 把「已处理掉的量」算全。

> ★ **V2.0 初稿的公式写反了，已核对代码并订正**：初稿写 `− Σ(qty − qty_ordered)`，
> 但「整条在途」时 `qty == qty_ordered` → 该式恒为 **0 覆盖**，会把现在唯一正确的那条通道也修坏。
> 正确口径应是「按**已承诺/已计划量**抵扣」，不是「未下单量」。

```
净需求 = BOM 展开(真实数量)
       − 可用库存               max(qty_on_hand − qty_locked, 0)   （全局，物理共享）
       − 本项目已领到车间量      领料单「已领走」的 qty_issued          （已消耗，不在库存）
       − Σ 已承诺/已计划量        status ∈ OPEN_STATUS 的整条 qty        （在途/待入库/…/待采购都算）
       − Σ 已直发到现场量         status =「现场已验收」的 qty          （没进过库存，场景 A）
```

- **`已入库` 不单列**：它的量已被「可用库存」+「已领到车间量」覆盖，再列就双算。
- **`不合格`/`已退货`/`已取消` 不计覆盖**：退回的量不算已完成，否则退货重采被抵扣 → 漏采。
- ★ 对 OPEN 用**整条 `qty`**（当前系统「一条需求只属于一张单」，`qty` = 已承诺量）；等一期拆单落地后，`在途/部分到货` 改用 `qty_ordered`、`部分下单` 只覆盖 `qty_ordered`。**所以 `qty_ordered` 列属于一期，第 0 期不建**（避免空列）。

| 要点 | 说明 |
|---|---|
| `DONE_STATUS` | `已入库` / `现场已验收`（= 现有 `REQUEST_DONE`）。★ **直发件必须算进来**，否则场景 A 永远重复 |
| `qty_ordered` 而非 `qty`（★ **一期起**） | 拆单后一条需求可能只下了一部分（`部分下单`），必须按**已下单量**算，不能整条排除也不能整条计入。**第 0 期系统还不支持拆单，先用整条 `qty`**（见上方订正公式） |
| 退货要减回去 | `已退货` / 换货退回的量不能算「已完成」，否则退货重采会被抵扣掉 → 漏采 |
| `_open_qty` 的 `remaining` | ★ **不再用 `qty − qty_received`**（场景 B 的根因：`qty_received` 含 pending）。改为按上方订正口径统计「已承诺/已计划/已直发」的量；`qty_received` 保留作展示字段 |
| `OPEN_STATUS` 扩枚举 | 加 `审批中`（§4.3）和 `部分下单`；同步 `tests/test_status_contract.py` |
| 领料口径 | `generate_issue` 改用同一套 `bom_math.net_demand`（AGENTS §8.3#3 待办一并解决） |

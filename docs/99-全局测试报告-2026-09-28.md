## N22 [P1·最严重] `PATCH /projects/{project_no}` 无权限校验，可篡改 9 个敏感字段

**攻击者**：`site1`（现场服务，只应有 `project:view` / `site:edit` / `acceptance:edit`）

```
PATCH /api/v1/projects/TX26001   HTTP 200
改前: stage=质保  amount=3,000,000  est_amount=3,000,000  pm_id=18  sales_id=11
      deadline=2026-10-28  period_end=2027-01-26  warranty_months=12  tech_agreement_frozen=True
改后: stage=已关闭 amount=1.00      est_amount=1.00       pm_id=None sales_id=None
      deadline=2020-01-01 period_end=2020-01-01  warranty_months=1   tech_agreement_frozen=False
★ 被改动的敏感字段: stage / amount / est_amount / pm_id / sales_id / deadline /
                    period_end / warranty_months / tech_agreement_frozen
```

**为什么最严重**：这不是"点了不该点的按钮"，而是能一次性
① 把**合同金额改成 1 元**；② 把项目**直接关闭**；③ **清空 pm_id / sales_id**（归属丢失）；
④ **解冻技术协议**（`tech_agreement_frozen=False`）—— 而技术协议是**设计基线与验收裁判**（00 卷 §3.1①）。

**连带危害已实证**（不只是理论）：
清空 `pm_id` 后，**所有"通知项目经理"的分支静默失效** —— 前端 `e2e:api` 的
`RCPT-售后报修→项目经理 pm1 未收到（工单 SV26002）` 随即 FAIL；执行基线复位后立刻恢复。
这正是 `AGENTS §8.1` 记录过的坑（"修复前从未赋值 → 通知静默丢失"）。

**同批实测越权成功的其它写接口**（同一根因：只校验登录、未校验权限码）：

| 接口 | 攻击者 | 实测 | 后果 |
|---|---|---|---|
| `POST /projects/{no}/close` | site1 | **200** | 关闭任意项目 |
| `POST /projects/{no}/generate-tasks` | site1 | **200** | 给设计/采购**派活**（实测一次产生 31 条任务、指派 5 人） |
| `POST /projects/{no}/milestones` | site1 | **201** | 改项目节点计划 |
| `POST /projects/{no}/contacts` | site1 | **201** | 改客户联系人 |
| `POST /suppliers` | site1 | **201** | 建供应商主数据（采购下单时可被选中） |
| `PATCH /tasks/{id}` | site1 | **200** | 改任务标题；**含 `owner_id` 时 403** ⇒ 字段级防护不完整 |

> 说明：`site:survey` / `site:issues` / `purchase/manual-request` / `notifications/read-all` 也是 2xx，
> 但属**设计允许**（site1 有 site:edit；05 卷 §6 明确手工申请任何部门可提；通知是本人数据），不计入。

**覆盖度数据**：129 个写接口中，**62 个挂了 `require_permission`，67 个没挂**（其中 57 个源码里也查不到内联/服务层防护标记）。
之前修的 AZ-01/AZ-02（采购需求登记/删除）确实已加内联校验（现返回 403「没有权限：purchase:edit/project:edit」），
但**同一类缺口在项目域/供应商域/任务域仍然成片存在**。

**修法方向**：项目域写接口统一挂 `project:edit`（关闭→`project:close`）、供应商域挂 `purchase:edit`/`std:edit`、
任务域挂 `project:edit`；`PATCH /projects/{no}` 还要做**字段级白名单**（金额/阶段/pm_id/tech_agreement_frozen 不应走通用 PATCH）。

## N23 [P2] 金额分档覆盖不全 —— 3 个接口把采购价给了无 `purchase:price` 的用户

用 `wh1`（仓库，无 `purchase:price`）逐个打读接口，找「价格类字段非空」：

| 接口 | wh1 | 价格字段 |
|---|---|---|
| `GET /suppliers` | 200 | ❌ **11 处非空**：`tax_rate=13.0` + `catalog[].price=10.0` ×3 |
| `GET /suppliers/{id}/catalog` | 200 | ❌ **3 处非空**：`price=10.0` |
| `GET /purchase/recommend/{item_no}` | 200 | ❌ **2 处非空**：`price_hint=80.0 / 100.0` |
| `GET /suppliers/{id}/quotes` | 200 | ✅ 0 处（已脱敏） |
| `GET /purchase/price-reference/{item}` | **403** | ✅ 整接口拒绝 |
| `GET /purchase/orders` · `/purchase/pool` · `/library/items` | 200 | ✅ 0 处 |

**影响**：仓管/现场/车间都能看到供应商的**品类常规价**与**推荐价提示**，而 `purchase:price` 的设计意图正是遮住"我们买多少钱"。
**修法**：把这 3 个接口的 `price` / `price_hint` / `tax_rate` 纳入 `scrub_money`（或整接口要求 `purchase:price`）。

## N24 [P2] 缺料的领料单**没有出口** → 永久卡在「待备料」

实测（把某物料库存造成 5，设备 BOM 需求 10）：

```
generate-issue → 201   领料行: YL-FT-0001 需 10.0 shortage=True 库位=深圳仓 A-01-01
pick           → 400   {"detail":"YL-FT-0001 在库位可用 5，不够备料 10（先补货或调整数量）"}
                       ★ 库存/占用 = (5, 0)（守恒正确，未超锁、未变负）
hand-over      → 400   {"detail":"要先备料才能领走"}
```

**问题**：报错说"**先补货或调整数量**"，但领料单的可用动作只有
`generate-issue / pick / hand-over` —— **没有调整数量、没有取消、没有部分备料**。
→ 整张单**永久卡在「待备料」**，同一张单里**本来能满足的行也被连坐卡住**。
→ 而"部分有货"（0 < 库存 < 需求）是车间最**常见**的状态。

**性质**：与 AGENTS §8.1 记录的教训同族 —— *"没有批次取消/作废口 → 造出永久死单据"*。
（本轮修好"静默跳过"后，原本的隐式绕过被换成了硬拦，但**没配出口**，是这次修复留下的尾巴。）

**修法方向**：`pick` 支持**按行部分备料**（备可用量，余量留待补货）或给领料单一个「调整数量 / 作废」入口。

## N25 [P2] 客户验收可**重复申请**，并**覆盖质保起算日**（无留痕）

```
对【已验收通过】的项目再次 POST /acceptance/apply  → HTTP 201（第 3 张验收单）
再 POST /acceptance/{id}/confirm {result:通过, accepted_at:2026-11-11} → HTTP 200
  project.warranty_start: 2026-09-28 → ★ 2026-11-11（被覆盖）
  project.warranty_end:   2027-09-28 → ★ 2027-11-11（同步漂移）
  该项目累计验收单 3 张
```

**影响**：质保起算日=**60 天到期提醒、质保金回收、售后在保/过保判定**的唯一依据，
现在可被**任意重复验收改写且无历史留痕** —— 直接违反铁律④「一切改动都是变更，必须走审批」。
叠加"任何人可 `PATCH /projects` 改 `warranty_months`"（N22）⇒ **质保期完全不可信**。

**修法方向**：已通过验收的项目禁止再次 `apply`（或必须走变更/重开流程）；`confirm` 对已确认的单幂等拒绝。

## N21 [P2] 无部门提交人 → 审批链跳到**错误部门**的总监 → 单据卡死

`reviewers.py` 两个函数策略不对称：
```python
def lead_for_dept(...):   # 无部门 → 返回 None（不兜底，记为"跳级"）
def director_for(...):    # 无部门 → ★ 全局兜底到「第一个总监」
```
实测（`admin` 无 `org_id` 提交的采购单 PO26029）：
```
round=1 level=1 action=跳过 note=「无采购经理，自动跳级给总监」   ← note 也是误报
  跳到的"总监" = director_for 全局兜底 = eng_director（工程总监，id=2）
  purchase_director 审 → 403「只有本部门采购总监能审这一级」
  eng_director     审 → 403「没有权限：purchase:edit」（角色 DESIGN_AUDIT 无该权限）
  ⇨ 没人能审，单据永久卡在「待总监审」
```
**连带影响已实证**：前端 `e2e:ui` 的 `P-02` 就是被它卡住的 —— UI 用 admin 下单 → 单停「待总监审」→
需求停在「审批中」→ 仓库**不出现验收按钮**（`找不到 PO26029 验收按钮`）。这不是前端 bug，是 N21 的下游。

**逃生口**：提交人可 `withdraw` → 草稿 → 作废 → 需求回池（不是绝对死单，但总监审这条路走不通）。
**修法方向**：`director_for` 无部门时**不要全局兜底**（改为报错提示"该用户未配部门，请先配置"），
或兜底到"该用户角色所属域"的总监；并修正那句 `跳过` note。

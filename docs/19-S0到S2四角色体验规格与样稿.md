# 19 · S0 到 S2：角色体验规格与样稿

日期：2026-10-06初稿，2026-10-07补六角色规格（§10）。状态：方案内容样稿，不是完整业务操作原型；正式数据、权限与页面未实施。§1–9保留早期四角色设计和历史验证，最新范围以§10为准。

## 1. 本次交付与范围

梳理销售 / 商务 → 项目经理 → 专业经理 → 设计组员的交接，先回答每个人该处理什么、看什么依据、交给谁，再决定首页与工作页面怎么组织。

样稿：`frontend/public/design-lab/roles/index.html`；开发服务器地址 `/design-lab/roles/index.html`。角色选择只用于对照设计方案，不是正式系统的身份代看功能；示意数据不代表测试项目当前状态，不连接业务 API、不提交业务操作。

样稿覆盖：四个职责首页、事项与依据、交接内容、角色相关导航、桌面与手机布局。它不模拟完整编辑表单、后台授权或真实审批；用来审视信息架构，不能作为全流程业务验收。

## 2. 最重要的业务区别

| 概念 | 在本业务中指什么 | 不能混淆成什么 |
|---|---|---|
| 销售负责人 | 商机归属与商务跟进，创建人未必是此人 | 创建人自动拥有所有后续工作 |
| 项目经理 | 组织设备范围、团队、节点与跨专业交接，跟踪交付 | 因有 design:edit 就以编辑图纸为核心职责 |
| 项目机械 / 电气等负责人 | 此项目里的对接人 | 自动等于对应专业审核经理 |
| 专业经理 | 承接专业主任务，决定本人做 / 拆分 / 转派，并处理本级评审 | 部门所有终审事项都待本人处理 |
| 设计组员 | 本人子任务和本人负责的图纸、BOM、程序内容 | 以整台设备为单位替所有人一键提交 |
| 工程总监 | 本部门最终审核、改版裁决与部门协调 | 仅凭“总监”岗位就管理其他部门事项 |
| 生成设计任务 | 设备 × 专业的主任务派到专业经理 | 组员已经接手或所有内容已经分工 |
| 提交评审 | 勾选本人负责的对象，进入同一任务评审单的一轮提交 | 创建无关联的多张评审单或整机完成 |
| 经理通过 | 本级通过，继续到工程总监 | 发布冻结 |
| 发布冻结 | 有效版本形成，可供下游使用；按所提交对象发布 | 必须等整台设备全部 BOM 完成才触发采购 |

业务依据：docs/05 §0、0.1、2、3；AGENTS 审评归属部门规则。机械 / 电气 / 程序并行，工艺等待机械首次发布；程序发布不产生采购需求。经理自己提交时总监直审。组织审核角色与项目对接角色分开。

## 3. 交接契约

### H1 · 销售 / 商务交给 PM

输入：已成交约定、客户联系人、资料包、合同周期 / 金额 / 付款约定、技术要求。输出：让 PM 能组织立项的业务依据。

首页：销售仍能跟踪本人商机与商务事项，但不会把工程设计、仓库验收等写成自己的待办。未成交以客户跟进为主；已成交以交接与后续商务节点为主。合同金额与付款操作遵循已有金额和动作权限。

关键缺口：当前 PM 未被指派时，成交项目不在 PM 本人台中；通用项目列表又能打开。用户已确认由销售经理任命PM并处理未分配项目，入口待实施，不能用“成交后自动出现在PM台”掩盖。样稿仅提示缺接收人，未新增“接单确认”或审批。

### H2 · PM 组织立项并交给专业经理

输入：项目约定与技术依据。输出：设备范围、项目对接人、节点时间、专业主任务与负责人；长周期件需要及时下单。

立项应围绕四个问题组织：做哪些设备 → 谁负责对接 → 什么时候交付 / 各节点怎么安排 → 专业工作交给谁。资料和长周期件贯穿准备，不能为了凑步骤让用户以为填过页签就是完成交接。

拟议工作页面：同一项目上下文中展示准备事项、可查的依据和生成任务预览。仍沿用当前必备条件，不自行要求所有项目角色都任命、所有节点都有负责人、所有附件都齐全。标准节点生成日期明确是待确认计划，不伪称已开会确认。

已有执行中项目：呈现已立项结果与任务去向；原路由保留，不能继续诱导再次确认立项。阶段适配作为后续实现项；本轮不改状态机。

### H3 · 专业经理交给设计组员

输入：本人专业主任务、设备范围、技术资料、时间要求。输出：明确范围 / 负责人 / 日期的子任务，或将主任务转派，或由经理本人完成。

“拆分”与“转派”分开表达，不能把添加人员当成分工完成。经理首页优先呈现需要安排的责任和轮到自己的本级评审，本组进度作为跟踪上下文。

待分工是体验提示，不是本轮新增数据库状态。当前“主任务还没有子任务”不足以认定经理尚未安排，因为经理可能自己做。实现前需要明确如何区分本人承担与准备分派，或使用可证实的“尚无子任务”文案。

### H4 · 组员提交给专业经理，再到总监

输入：本人任务、负责对象、有效技术依据、前置条件与退回意见。输出：本人负责的图纸 / BOM / 程序的一轮提交。

任务工作页面拟议结构：工作范围与时间 → 有效依据 → 本人产出 → 本次提交 → 审核记录。其他相关对象可供协作理解，写 / 提交范围由对象归属与业务条件决定。不能因为同属一个设备就允许替人提交。

退回不是泛红的项目风险：要直接显示涉及哪个对象、哪个版本、谁给了什么修改意见。经理通过后显示“待工程总监审核”，不是“已发布”。发布后主动作转为查看有效版本或申请改版，不再显示直接修改冻结内容。

## 4. 四角色首页规格

| 项目 | 销售 / 商务 | PM | 专业经理 | 设计组员 |
|---|---|---|---|---|
| 默认焦点 | 本人业务跟进 | 本人负责项目的启动 / 协调 | 本组分工与本人本级评审 | 本人设计与退回修改 |
| 核心对象 | 商机、客户、商务节点 | 项目、设备范围、节点与交接 | 专业主任务、子任务、本级评审 | 本人任务、图纸 / BOM / 程序 |
| 首页必须说清 | 这次需要跟什么，缺什么约定 | 哪个条件 / 责任没落实，应协调谁 | 哪项要分工，哪张单轮到我审 | 做哪部分、用什么依据、提交给谁 |
| 主要动作 | 跟进、补资料、成交登记、商务处理 | 准备立项、查看交接、协调事项 | 拆分 / 转派 / 本人做、本级审核 | 进入本人工作范围、修改退回、提交 |
| 必要上下文 | 客户资料、合同与交付进展 | 全项目专业与实物链状态 | 本专业设备 / 版本、项目技术要求 | 对应设备与前置状态、有效版本 |
| 不作为首页主角 | 零设备 / 零批次与工程审批数 | 各专业编辑按钮、无关全量项目 | 全部门终审数和他人个人待办 | 采购、合同价格与部门审批数 |
| 结果反馈 | 明确项目阶段与交接接收人 | 任务生成到谁，后续状态可追溯 | 子任务到谁，本级审核流转到谁 | 本轮提交、审核进度、退回与发布 |
| 空态说明 | 本人暂无需处理的商务事项 | 暂无已指派给我的项目；未分配项目由销售经理安排 | 暂无本级审核事项，可查看本组任务 | 暂无指派给我的任务；分工由专业经理安排 |

菜单在样稿中按核心工作重新组织，未绑定正式路由；不是简单复制九个台。保留已拍板取消“我的工作台”聚合入口的决定。本轮只讨论四种职责，经理 / 总监其他部门范围、多角色用户默认优先身份另行设计。

## 5. 当前实现到新体验的差距

| 差距 | 现有证据 | 需要的落地条件 |
|---|---|---|
| 同一项目详情给不同角色近似相同的全生命周期摘要 | DetailPage 统一 SummaryBar 与按阶段 nextAction | 角色需要的字段 / 动作规格明确，金额及写权限同源 |
| PM 的编辑能力容易被当作专业职责 | seed.PM 含 design:edit；立项总装图 owner=current.id | 核对 PM 创建根节点与设计负责人后续归属，避免只改按钮文案 |
| 经理分工能力藏在任务页，工作台多为汇总 | workbench/EngWorkbench 与 workbench/Page 的拆分 / 转派 | 工作台事项直接进入具体主任务与分工，保留深链 |
| 组员进入设备设计面时对象范围不突出 | 任务链接导航到 project/equip，没有任务上下文参数 | 任务上下文与对象归属一致，避免设备全树作为唯一工作入口 |
| 工程台结论混用本人、本组和部门量 | EngWorkbench metrics 使用 eng_board 的待总监数 | 按岗位与实际审核人派生结论，数字可点击后对应同一集合 |
| 商务与 PM 接手存在入口空档 | sales_board 的 sales_id 与 pm_board 的 pm_id / members 筛选 | 明确 PM 任命流程和未分配项目责任 |

这里只列业务与体验差距，不把接口“全量”自动认定为应禁止。协作、历史复用与数据隐私需要明确口径。

## 6. 已发现的历史口径冲突与待明确事项

1. **“自己的东西”是否硬限制**：docs/05 §0#11 / §2.2 明确默认筛选、链接可协作打开；最新用户强调只看到自己的。用户 2026-10-06 已确认：首页聚焦本人职责，相关项目链接仍可协作查看。保留协作可见，不新增数据硬隔离。
2. **PM 谁指派、何时指派**：用户 2026-10-06 已确认：销售经理负责指定 PM，并处理尚未指定 PM 的成交项目。不新增接单或审批机制。
3. **任务归属与对象归属**：立项根图由 PM 创建，专业任务由专业经理承接；拆分以后组员对应哪些对象，需要核对实际创建 / 转派 / 提交链。不能仅靠任务 owner 推断全部图纸 owner。
4. **销售与商务是否实际分岗**：当前 SALES 合并权限；样稿保留共同业务范围，若实际人员分工不同，应按职责再细分而非只换岗位名。
5. **组织与 profession**：docs/06 提出组由组织决定，当前部分查询仍靠 profession；业务边界需统一，不能仅靠前端筛选补救。

这些事项分别影响规则、范围与实现。可以继续检查与做样稿，依赖未决规则的生产改动暂不执行。

## 7. 下一步实现与验收

先审视样稿的四种身份：内容是否符合职责、遗漏了什么交接、哪项不是这人该办的、文字是否符合公司习惯。确定角色规格，再决定首页与对象工作页的正式结构，不以当前组件壳为正确答案。

实施时先打通一个正常链与一个退回链：销售成交与 PM 接手 → PM 准备与任务生成 → 经理分工 → 组员做本人内容并提交 → 经理审评 → 总监发布；退回能回到同一任务与具体对象。用责任角色本人账号，不用 admin，保留 ERP 主数据。

验收入口包括首页、任务、项目详情、搜索、站内消息、直接链接与刷新；验证看到的状态、计数、对象、动作与后台一致。权限口径确认后补正反向数据范围测试。没有完成真实路径验证，不宣布角色体验重构完成。

## 10. 第1段六角色页面与交接规格（2026-10-07）

### 10.1 本次成果与边界

现有`/design-lab/roles/index.html`已更新为销售执行、销售经理、PM、专业经理、设计组员、工程总监六角色内容样稿。角色按钮和责任链均可切换；每个角色有独立事项分区，主按钮展开工作页应包含的内容。全部示意，不调用API，不指定真实PM、不派工、不审批、不改变业务状态。正常链/退回链是下面的设计规格，样稿暂不模拟整段状态推进，也不是正式登录/完整编辑表单原型。

本次修正旧样稿：未指定PM交销售经理；“待分工”改为可证明的“尚无子任务”；组员不假装已有子任务对象隔离；默认先看退回；待总监审与已发布分开；回款日期待定不称到期；加入工程总监终审与现存改版路由缺陷说明。

### 10.2 登录与落点规格（尚未画登录表单）

登录只承担账号验证和进入本人工作，不让用户先选择部门来获得身份。成功后由已有账号角色/岗位决定职责落点；已登录打开具体任务链接，验证权限后进入该对象，不统一送回首页再找。多角色首落点未定，先保留当前规则，不新增身份代看。

| 情况 | 应给用户的反馈 |
|---|---|
| 登录中 | 按钮显示正在登录，保留输入，防重复提交 |
| 账号/密码错误 | 表单就地明确失败，可修正再试，不跳无关页面 |
| 服务暂不可达 | 说明连接失败并可重试，与凭据错误区分 |
| 成功但无业务角色 | 显示账号缺工作入口并引导联系管理员，不展示假空业务队列 |
| 会话失效 | 登录后尽量回原对象；未保存内容不假装已经保存 |
| 首页无事项 | 说明本人当前无待处理工作，提供职责范围内记录/协作入口，不自动切到别人的任务 |

现有登录已做部分基础改善。本节不宣布全部状态/落点能力已实现；尤其深链与失效恢复须实现时验证。

### 10.3 六个首页：内容顺序与动作

| 首页 | 首屏主内容 | 跟踪/协作内容 | 直接进入的工作 |
|---|---|---|---|
| 销售执行 | 本人客户跟进与成交资料 | PM是否指定、回款计划 | 具体商机/项目的客户依据与成交交接 |
| 销售经理 | 未指定PM的成交项目 | 已指定后的启动跟踪、商务协调 | 指定具体项目PM |
| PM | 本人项目立项准备与协调缺口 | 专业任务去向、有效发布、相关异常 | 当前项目立项工作页 |
| 专业经理 | 专业主任务安排、本级待审核分别列 | 本组工作和前置等待 | 具体主任务安排或具体评审单 |
| 设计组员 | 退回修改、本人进行中任务 | 我的提交与当前审核人 | 带任务上下文的产出/提交工作页 |
| 工程总监 | 实际轮到自己的终审 | 工程改版、跨专业与部门进展 | 本轮终审工作页或工程改版依据 |

首页从当前职责讲起，不把S0→S11所有阶段均作为菜单主角。无重复计数；若数字可点，必须进入同范围的列表。项目、设备和件档案可协作访问；各角色不复制一套业务事实。

事项排序建议：需修改/明确异常→轮到本人决定→当前执行→仅需跟踪。具体先后结合实际期限，不用“没有预计日期”推断逾期。待本人、共享队列、需我跟踪明确区分。

### 10.4 六类工作页

1. **销售成交交接页**：客户/联系人、技术依据、设备需求、合同周期、回款约定、项目经理现状。显示缺项和下一接手责任；销售继续补资料，不代销售经理任命PM。
2. **销售经理指定PM页**：项目与成交范围先可查，再选择合法PM候选；提交后显示实际PM和对应项目，未分配队列更新。沿用已有任命机制，不新增审批或接单确认；授权/管理范围需后端实现核对。
3. **PM立项页**：常驻项目约定和启动缺项；设备、项目团队、节点、长周期件、任务去向分区。预览主任务派到谁，沿用必备校验；执行中展示启动结果，避免重复确认。表单keepMounted、错误跳区、刷新状态、保存失败反馈保留。
4. **经理任务安排页**：主任务依据/日期、本人产出与子任务、安排动作、实际接收人。本人承担、转派、拆分分开；没有子任务不等于必须分派。多人对象划分待用户口径，当前样稿不把选择姓名包装成完整范围分工。
5. **组员任务工作页**：任务与计划→技术依据/前置→可编辑产出→本次提交预览→审核履历。任务上下文在深链/刷新/返回中保留；提交预览列真实对象和版本。冻结后不直接编辑；协作可读与可提交边界分开。
6. **审核工作页**：当前轮次与审核责任常驻；本轮对象及附件/BOM、上轮意见及修改、历史动作、通过/退回。经理通过后说明交工程总监；总监通过后展示本批发布及实际下游结果。审核页不把整机设计进度替代本轮依据。

### 10.5 一条正常链的用户反馈

| 完成动作 | 当前操作者看到 | 下一责任方看到 |
|---|---|---|
| 销售登记成交 | 成交约定已登记；尚无PM则显示销售经理安排 | 销售经理未指定PM队列 |
| 销售经理指定PM | 显示实际PM，项目移出未指定队列 | PM本人项目启动事项 |
| PM确认立项/生成任务 | 设备×专业任务与实际责任经理，工艺前置明确 | 经理主任务；工艺等待首次机械发布 |
| 经理拆分/转派 | 具体任务与接收人；主/子任务关系保留 | 执行者本人任务及现有内容说明 |
| 组员提交一轮 | 本轮对象、轮次、实际待审核人 | 经理本人本级审核单 |
| 经理通过 | 待工程总监审，尚未发布 | 总监实际终审队列 |
| 总监通过 | 本批有效冻结版本与发布记录 | 相应采购需求、工艺解锁及通知；以实际产出为准 |

经理本人提交是另一正常分支：跳过本级，总监直审，界面明确说明原因；不添加本人审核步骤。分批发布是允许路径，单批成功不宣称设备全部设计完成。

### 10.6 退回链与部分完成

经理或总监退回时，意见定位本轮对象，回原提交任务和原评审单。组员工作页优先显示谁在第几轮因何退回，编辑允许修改的产出；重提进入同单下一轮，旧意见和附件依据留档。经理/总监不再保留已经退回的单为本人待审。

尚未发布的其他内容可以后续再提交；不能把已发布部分全部解冻。待审核显示当前责任而非“没完成”；只有实际服务允许才提供撤回。用户跨分区/刷新/返回后仍能识别原任务与当前轮次。

未决边界：多人同设备任务按图纸/组件还是工作内容分工；同设备同专业草稿可提交集合与个人归属如何对应。现有源码不等于最终正确规则，本轮未新增对象隔离或代提交权限。

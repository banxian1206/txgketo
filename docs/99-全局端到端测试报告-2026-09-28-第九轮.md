## 4. 本轮新发现（都是 P3 / 观察项，无阻断）

### Q-1 [P3·最值得处理] **基线里的"评审授权负控"在空转**
```
--- C2 评审审核的授权码 ---
    · 审核中的评审单 0 张
```
S2 在 Part A 就把评审单全发布了，Part C 的负控拿不到"审核中"的单 → 这段等于没跑。
而 `ALLOW` 里正是用**"走 review_flow —— 服务层校验只有本专业经理/工程部总监能审这一级"**给 `POST /review-tickets/{id}/review` 免挂了权限码。
我试着实测它：`review_flow.review_ticket` 是**先判单据状态、后判审核人身份**（第 454 行 vs 466 行），所以用「已发布」的单只能拿到 `400「不在审核中」`，**永远走不到身份判断** → **目前没有任何活数据能证明这条声称成立**。
> 建议：照他们刚修好的 `api.mjs` 的办法，把这条负控改成**自建靶**（自己提一轮评审 → 用错账号去审 → 断言 403 → 撤回清理），别再"找现成的单，没有就跳过"。同一段里的 `c_authz_codes`（改版裁决）我手工造靶实测是拦住的（见 §1），可以照同样方式固化。

### Q-2 [P3] 收款提醒发给**整个 SALES 角色**，不是项目自己的销售负责人
`payment.py:81` 用 `notify_role("SALES", …)` → 现在 sales1 与 sales_director **两人都收到同一条催款**。项目是各自负责的（`project.sales_id`），销售多于 2 人时，每个人都会被别人项目的催款打扰。
对照：到期扫描（`deadline.py`）是**精确定位**到任务负责人 + 同专业经理 / `pm_id + sales_id` 的。两处口径不一致。
> 建议：改为 `[project.sales_id] (+ 销售总监)`，与 `deadline.py` 对齐。

### Q-3 [P3] 收款提醒**没有 `dedup_key`**
到期扫描每件事每天最多提醒一次；但 `remind()` 没传 `dedup_key` → 一个项目**分批发运**时每趟 `depart` 都会为同一笔「发货款」再催一次（未收额相同时看起来就是刷屏）。
> 建议：`_key("payment-remind", project_no + node, day)` 同口径补上。

### Q-4 [P3] 三个新功能只有 **pytest 层**护栏，没有 e2e / 前端断言
覆盖普查（grep 护栏文件）：

| 功能 | 单测 | e2e_baseline | 前端 static/api/ui |
|---|---|---|---|
| 叫车（跨部门） | ✅ | ✅ | ✅ |
| 组装体发运清单 | ✅ | — | ✅ |
| 到期扫描 | ✅ | — | — |
| 离线队列 | ✅ | — | ✅（横幅） |
| **项目自动归档** | ✅ | — | — |
| **Excel 历史采购导入** | ✅ | — | — |
| **付款节点→催款提醒** | ✅ | — | — |

后三行是缺口：本轮基线 126 条断言里**没有一条**验证"归档发生"、"导入后价格可用"、"节点达成产生催款"。这三条恰恰是"只有跑通全链路才会暴露"的那类（第八轮 M-04 就是这么溜进来的）。
> 建议：归档 + 催款提醒直接补进 `e2e_baseline`（S10 之后加 2 条断言即可）；导入补 1 条 e2e（造 CSV→导入→`price-reference` 可查）。

### 7.2 Q-5 ❌ 需要更正（数量与定性都错）

原文：*"`payment_term.trigger_node` 存量 **4 条**为 `NULL`，迁移没回填历史节点。影响：老项目的**预付款永远不会触发催款**。"*

**干净基线后实测**：

```
TX26001 1 预付款  NULL   900000    ← NULL
TX26001 2 发货款  '发货' 900000    ← 绑对
TX26001 3 验收款  '验收' 900000    ← 绑对
TX26001 4 质保金  '质保' 300000    ← 绑对
```

1. **迁移确实回填了** —— 发货款/验收款/质保金三条都绑上（迁移里就是
   `UPDATE payment_term SET trigger_node=... WHERE trigger_node IS NULL AND node_name LIKE '%发货%'` 这类）。
   "没回填"**不成立**。
2. **`NULL` 的全是「预付款」**，这是**设计如此**：`infer_trigger("预付款") → None`。
   客户口径是"这些节点要跟**物流**能够对上"，而**预付款在发货之前、没有物流节点可对**。
   原文那条"影响"描述的其实是**预期行为**。

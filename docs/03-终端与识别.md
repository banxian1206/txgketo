## 0. 七条结论（先说结果）

| # | 结论 |
|---|---|
| 1 | **一套代码，三个终端**：PC 浏览器 + Android APK + iOS。不写两套原生 |
| 2 | **现场访问靠内网穿透**（客户已确认可做）：服务器留在公司内网，只把**手机端接口**透出去 |
| 3 | **30 人规模 → 单机部署足够**：不需要集群、不需要微服务。一台普通服务器（8 核 32G）跑全部 |
| 4 | **Android 发 APK**；**iOS 用电脑 sideload（刷 ipa）** 或 PWA 加到主屏 —— 两条路都行 |
| 5 | **不做二维码体系**（客户确认没必要）：系统里本来就有清单，**勾选就够了** —— 这是最省事也最正确的选择 |
| 6 | **OCR 用 PaddleOCR 本地部署**，识别**外来单据**（送货单、图纸标题栏、标准件标签、设备铭牌）；识别结果**永远人工确认** |
| 7 | ★ **新增 AI 助手**：用大白话查系统数据（查件、查采购、查设备统计与成本）。**只读、继承权限、可追溯** |

## 2. 终端方案

### 2.1 技术路线：一套代码三端

```
React + TypeScript + Vite   ← 一套代码
        │
        ├── PC 浏览器（管理、设计、采购、财务）
        ├── 手机浏览器 / PWA（现场、仓库、车间）—— 零安装
        └── Capacitor 打包 → Android APK + iOS ipa
```

**为什么用 Capacitor 而不是 RN / Flutter / 原生：**

| 理由 | 说明 |
|---|---|
| 一套代码 | PC 与手机同一份代码，改一处三端生效 |
| **AI 友好** | 不需要学两套原生 SDK；就算打包失败，纯 H5 照样能用，**不会卡住项目** |
| 原生能力够用 | 相机、录像、文件、离线存储都有成熟插件 |
| 私有部署友好 | App 只是外壳，连公司内网的 API，不依赖任何云服务 |

### 2.2 三端能力对比

| 能力 | PC 浏览器 | 手机浏览器 / PWA | 打包 App |
|---|---|---|---|
| 勾选清单、审批、报表 | ✅✅ | ✅ | ✅ |
| 拍照 / 录像上传 | — | ✅ | ✅✅ 体验更好 |
| **弱网/无网暂存** | — | ⚠️ 有限 | ✅ **可靠**（本地队列 + 后台重传） |
| 消息推送 | — | ⚠️ iOS 差 | ✅ |
| 更新 | ✅ 刷新即最新 | ✅ 刷新即最新 | ⚠️ 需重装（可做检查更新） |

> ★ **`弱网/无网暂存` 是现场最大的体验风险** —— 客户工厂地下室没信号、车间屏蔽严重。
> 现场拍完照片视频必须**先存本地、再后台慢慢传**，不能"点一下等它传完"。

### 2.3 分发方式（已按客户答复定案）

| 平台 | 方案 | 说明 |
|---|---|---|
| **Android** | **直接发 APK**（内网下载 / U 盘拷） | 0 元、无审核、**最省事** |
| **iOS** | **电脑 sideload 刷 ipa**（客户确认可行） | 需要签名；个人签名 7 天有效期，到期需重签（或用企业证书长期有效） |
| iOS（备选） | PWA 加到主屏 | 0 元、无需签名、**不怕过期** —— 建议同时保留这条路 |

> 被排除：微信小程序 / 企微 / 钉钉 —— 需公网域名 + 平台审核 + 数据过第三方，与"纯私有"冲突。

## 3. 现场访问：内网穿透（已定案）

**架构：服务器留在公司内网，只把手机端需要的接口透出去。**

```
公司内网                                   外网（现场/家里）
┌─────────────────────────┐                ┌──────────────┐
│  PostgreSQL + 主系统      │                │  手机端 App   │
│  ├ PC 端（完整功能）      │◀── 内网穿透 ───│  / 手机浏览器 │
│  └ 手机端 API（透出这一块）│    HTTPS       └──────────────┘
└─────────────────────────┘
```

### 安全加固清单（穿透必须配套）

| # | 措施 |
|---|---|
| 1 | 只透出**手机端所需接口**；**成本、报表、管理接口绝不开公网** |
| 2 | HTTPS 证书（域名 + 证书，不能用裸 HTTP） |
| 3 | 强密码策略 + **登录设备绑定** + **异常登录告警** |
| 4 | 接口限流 + 上传大小限制（视频大，要单独限） |
| 5 | 全量操作日志（谁、何时、从哪个 IP、做了什么） |
| 6 | 穿透通道本身设访问白名单（只允许手机端路径） |

### 穿透方式建议

| 方式 | 成本 | 说明 |
|---|---|---|
| **frp 自建**（一台最便宜的云服务器做中转） | ~¥100/年 | 最可控、最便宜，需要一点运维 |
| 商业穿透服务（花生壳/贝锐等） | ¥200–500/年 | 省心，带证书，适合不想折腾 |
| ZeroTier / Tailscale 组网 | 免费起 | 更安全（不暴露公网端口），但每台手机要装客户端，30 人推广有成本 |

**建议**：**先 frp 自建**（便宜可控）；如果运维嫌麻烦就换商业服务。

### 离线兜底（仍要做）

现场有网 ≠ 永远有网（地下室、屏蔽、流量用尽）。所以 App 端保留**离线队列**：
没网时照片/勾选先存手机 → 一有网自动上传。**这是花小钱防大坑。**

## 4. OCR 与识别

### 4.1 首要原则：**清单驱动，勾选为主，OCR 兜底**

客户已明确**不打印二维码** —— 这个判断是对的。因为：

```
系统里本来就有清单：
  仓库到货   → 系统已知道"今天该到哪些货" → 逐条勾选 + 拍照
  车间领料   → 系统自动生成领料单       → 按单备料 + 勾选
  现场到货   → 系统带出**发运清单**（应到明细）  → 逐项勾「到/缺/损」+ 拍照
```

**不需要扫码 —— 清单 + 勾选 + 拍照就够了。** 这比让人对着标签扫码快得多。

**OCR 只用来对付"外来的、没有我们数据的"东西。**

### 4.2 OCR 应用清单（按价值排序）

| # | 场景 | 识别什么 | 价值 |
|---|---|---|---|
| 1 | ★ **供应商送货单** | 物料名称、规格、数量 | 自动生成到货清单 → 仓库逐条勾选验收（替代手工录入） |
| 2 | ★ **图纸标题栏** | 图号 / 名称 / 版本 / 材料 | **最大**：图纸一扫，BOM 条目自动冒出来，不用手敲图号 |
| 3 | ★ **标准件包装标签** | 品牌、型号、规格 | 自动匹配标准库，避免重复建码 |
| 4 | **设备铭牌** | 型号、序列号、厂家、功率 | 自动建设备档案（进场、售后换件时用） |
| 5 | 手写单据 | 领料单、验收单手写字 | ⚠️ 手写准确率低，**仅作辅助，必须人工确认** |
| 6 | 图纸里的尺寸/材料标注 | 各种标注文字 | ❌ **不做** —— 版面复杂、错误代价高 |

### 4.3 技术选型：**PaddleOCR，本地部署**

| 项 | 选择 | 理由 |
|---|---|---|
| 引擎 | **PaddleOCR**（PP-OCRv4/v5） | 中文识别效果最好；开源免费；**内网可跑**；CPU 就够（约 1–2 秒/张） |
| 服务形式 | FastAPI 包一层 `POST /ocr` → 文字 + 坐标 | 与主系统同一套技术栈、同一台服务器 |
| 结构化提取 | **模板 + 正则**（按单据类型配置模板） | 比大模型可控、可离线、可解释；错了能改规则 |
| 不用云 OCR | — | 数据要出内网，与"纯私有"冲突 |

### 4.4 铁律：**OCR 只给候选，永远不自动写入**

```
拍照 → OCR 识别 → 显示"识别结果 + 原图对照" → 人工确认/修改 → 才写入系统
```

**原因**：错一个图号 = 一批料做错 / 一个件装不上。OCR 只用来"少打字"，不用来"替人做决定"。

## 5. ★ AI 助手（概览）

> **详细设计见 [`04-AI助手与物料状态链.md`](./04-AI助手与物料状态链.md)**：物料状态链（22 个状态 + 判定依据）、
> 点查与分析两套能力、查询目录、指标字典。本节只讲它在终端侧怎么呈现。

### 5.1 目标：用大白话查系统里的数据

客户原话：*"我想做一个 AI 助手。通过这个助手，我可以查询到系统里面的数据。"*

**典型问题：**

| # | 问题 | 背后要答什么 |
|---|---|---|
| 1 | 某个订单的某个件现在怎么样了？ | 这个零件**一生**的当前状态与责任人 |
| 2 | 采购的某个件到了没有？ | 采购单 + 到货记录 + 预计到货时间 |
| 3 | `01A` 这台设备有多少个件？外购/自制/外协各多少？成本是多少？ | BOM 按来源分类统计 + 成本归集 |

### 5.2 三条铁律

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **只读** | AI 只能查，不能改/删。要改数据请去对应页面 —— **防止 AI 误操作** |
| 2 | **权限继承** | AI 能看到的数据 = **这个人本来就有权看到的**。不能因为"问了 AI"就看到合同金额和成本 |
| 3 | **可追溯** | 每个回答下面显示**数据来源与时间**，并给出**可点击的实体卡片**（点图号 → 进零件档案看详情） |

### 5.3 架构：三层，预置查询优先

```
① 听懂问题
   自然语言 → 意图 + 参数（图号 / 订单号 / 设备号 / 时间范围）
        ↓
② 映射查询
   优先命中【预置查询目录】（30~50 个标准查询）
   命中不了 → 生成 SQL（Text-to-SQL，兜底）
        ↓
③ 执行与呈现
   权限过滤 → 查库 → 表格 / 卡片 / 图表 + 一句话结论
   → 给出可点进去的实体链接
```

**为什么"预置查询优先"，不全靠 Text-to-SQL：**

| 理由 | 说明 |
|---|---|
| **准** | 业务口径提前定义好（比如"在途"怎么算），不会每次算出不同结果 |
| **快** | 不用等模型生成 SQL |
| **可控** | 权限与性能都有保障 |

### 5.4 第一批预置查询目录

| 类别 | 问题示例 |
|---|---|
| 零件 | 这个件现在到哪一步了？谁在负责？ |
| 采购 | 这个件到了没？什么时候到？ |
| 设备 | `01A` 有多少个件？自制/外购/外协各多少？齐套率多少？ |
| 进度 | 这个项目现在在哪个阶段？哪些节点超期了？ |
| 成本 | `01A` 花了多少钱？材料/外协/人工各多少？ |
| 交付 | 这个项目发了几个批次？现场装到哪了？ |
| 售后 | 这台设备修过几次？ |
| 回款 | 这个项目还有多少款没收回？ |

### 5.5 模型部署（★ 需要拍板）

| 方案 | 硬件 | 效果 | 数据安全 |
|---|---|---|---|
| **A. 本地小模型**（Qwen2.5-7B/14B，Ollama 部署） | CPU 可跑（慢，5–15 秒/次）；一张消费级显卡更快（2–5 秒） | 够用 | ✅ **数据不出内网** |
| B. 云端 API（DeepSeek / 通义等） | 无 | 最好 | ❌ 问题与数据会出内网 |

**建议 A**：订单、成本、客户信息属于敏感数据，**不建议出门**。30 人规模，一张消费级显卡就够；
先用纯 CPU 跑 7B 试效果，不够再加卡。

### 5.6 落地路径：三步走（★ 顺序不能反）

```
第 1 步  实体档案页  —— "零件的一生" / 设备档案 / 项目全景
                      （AI 回答的落点，本身就是极高价值功能）
第 2 步  结构化快查  —— 输入图号 / 订单号 / 设备号 → 直接出结果（不用 AI，最快最准）
第 3 步  AI 助手     —— 自然语言入口，把前两步的能力用大白话串起来
```

**没有第 1、2 步的底子，直接做第 3 步就是个玩具。**

## 6. 部署与规模（30 人规模定案）

| 项 | 结论 |
|---|---|
| 服务器 | **一台**（8 核 / 32G / 1TB SSD 起），或公司现有虚拟化平台上开一台 |
| 部署方式 | Docker Compose 单机（Nginx + API + PostgreSQL + OCR 服务 [+ AI 模型]） |
| 并发 | 30 人、峰值十几人 → **毫无压力** |
| 不需要 | 集群、微服务、Redis、消息队列、K8s —— **一律不上**（上了只是增加维护负担） |
| 备份 | 每日 `pg_dump` + 附件目录增量备份到 NAS/移动盘 |
| 显卡（可选） | 若要本地 AI 助手体验好，加一张消费级显卡；否则先纯 CPU |


**您只需确认看得见的东西**：页面能不能用、拍照顺不顺手、勾选快不快、有没有多余的填写项。
技术细节不用管 —— 但**业务规则错了必须当场说**，越往后改越贵。

# 12 · 页面分型与 UI/UX 重构方案（2026-09-29）

> 全部结论来自实测：13 个 PC 页 + 2 个移动页**逐一截图并量了首屏可见性/密度**（截图与脚本在 `/tmp/uiaudit/`、`/tmp/uiaudit.mjs`），
> 并对照自家已有的《前端UI视觉规范》《前端交互设计规范》逐条核对落地率。

## 0. 一句话诊断

**颜色与状态色的债已经还清了，但"排版、层级、密度"的债一分没还** —— 而这三样才是"观感"。
同时**页面没有分型**：项目详情被做成"数据库记录的编辑器"（12 个区块全平铺），工作台被做成"三层标题 + 两套计数"，
所以"用的人很难受"不是审美问题，是**信息架构没分类** + **视觉底座缺 token**。

## 1. 实测证据

### 1.1 项目详情页（客户点名的那张）

```
高 7411px ≈ 9 屏 · Card 14 张（首屏只装得下 5 张）· 表格 9 张 · 列合计 52 · Tag 45 · 按钮 13
区块：基本信息 | 客户与联系人 | 项目要求 | 时间与金额 | 成交信息 | 设计进度 | 设备清单 |
      节点计划 | 长周期采购 | 项目团队 | 资料包 | 操作记录        ← 12 个锚点胶囊 = 拿锚点条当地图
首屏内容：项目号 + 阶段 Tag + 一行灰字 + 7 段步骤条 + 12 胶囊 + 「基本信息」label:value 平铺（3 个空值 —）
```
截图里最刺眼的三件事：
1. **首屏没有任何"我该干什么"** —— 项目在质保期（该收质保金、有 24 条未读消息），但首屏只有静态字段；
2. **等权重平铺**：所有卡同款白底、同款标题字号，只靠 16px 灰缝区分 → 9 屏没有主次；
3. **空值占位**：`客户产品类型 —`、`要求节拍 —`、`要求产能 —`、联系人表「职务/微信/邮箱」三列全空 —— 空字段和关键字段抢同一份注意力。

### 1.3 台类页（采购/仓库/…）的共同病

```
仓库台：台条「仓库工作台 ⑦」→ 卡标题「仓库」+ 副标题「库存 4 种 · 缺货 1」→ 3 张数字卡(4/2/1)
        → 页签「待办(7) 库存(5) 领料单2张 出入库流水 库位(1)」→ 内嵌「生成领料单」卡
        → 小标题「◎ 验收（货到了就验：合格/不合格）」→ 又一行长说明 → 表格
```
1. **同一指标两套计数且互相矛盾**：卡说「库存 4 种 · 缺货 1」，页签说「库存 (5)」；
2. **标题重复三层**（台条名 / 卡标题 / 小标题），每层都在解释"这屏是干什么的"；
3. **把内部文档口径写给一线用户**：`先查仓库 → 缺的进池 → 攒一攒合并下单（00 卷 §3.1⑩）` —— **21 个文件**出现"卷/§"字样，`type="secondary"` 长说明句 **189 处**；
4. **列宽失控**：仓库台「预计到货」列被截成 `2026-10-0…`（日期截断=信息丢失，不是省略号美学）。

## 2. 页面分型：5 类原型 + 每类的 UI/UX 契约

> 原则：**同类页必须同壳同密度同范式**；不同类页不许互相借布局（详情页借列表的平铺 = 今天的病）。

| 型 | 页面 | 目的 | 首屏必须给（≤1 屏） | 布局契约 | 禁止 |
|---|---|---|---|---|---|
| **A 台账列表** | 项目列表 / 供应商 / 备件 / 领料单 | 找到那一条 | ①筛选 ②计数 ③表 | 单卡；表 `size=small`；列 ≤7 + 详情进抽屉；筛选进 URL | 行内塞 3 个按钮；列宽截断数据 |
| **B 工作台**（角色台） | 采购/仓库/车间/商务/PM/工程/现场/发运/售后 | 今天先干哪件 | ①**一条**计数行 ②页签队列 ③表 | 台条(切台) + **一层**页签；计数只在一处出现；说明文字进 Tooltip | 数字卡与页签双份计数；三层标题；内部口径上屏 |
| **C 对象工作台** | **项目详情**（今后含设备详情） | 这个项目现在什么状况、下一步做什么 | ①阶段+下一步(可点) ②4~6 个关键数字 ③风险/待办 | 三段式（结论条 / 分组折叠 / 明细抽屉），见 §3 | 12 区块平铺；空值占位；整页只有一把"编辑" |
| **D 结构工作区** | 设备设计面（图纸树+BOM+程序） | 在结构上干活 | ①结构树 ②当前节点动作 | 左树右详情（或上树下表）；动作贴近对象 | 把 BOM/程序/图纸并排堆成 4 张卡（现状 22 列） |
| **E 移动作业页** | /m/* | 一屏完成一个动作 | ①清单 ②勾选 ③吸底主按钮 | 灰底白卡；触控 ≥44；状态用左侧 4px 色条 | PC-only 入口（AGENTS 已定）；与 PC 不同名的动作 |

## 3. 项目详情页重构（P1 样板，方案具体到块）

### 3.1 新信息架构：三段式

```
┌ ① 结论条（固定，不滚走）────────────────────────────────────────┐
│ TX26001 E2E审计-整线   [质保]        面包屑：工作台 › 项目 › TX26001 │
│ ▶ 下一步：收取质保金（到期 2027-09-29，还剩 365 天）  [去登记回款]   │ ← NEXT_HINT 升级为可点动作
│ 设备 1 · 齐套 100% · 未收 ¥300,000 · 售后工单 2 · 未读 24            │ ← 关键数字（点击下钻到对应分组）
│ ⚠ 风险：交期已过 12 天未关单 / 长周期件 3 项在途                     │
├ ② 四条泳道（折叠，记住展开状态）──────────────────────────────────┤
│ ▸ 合同与商务   客户·联系人·成交条款·付款节点·回款      （原 basic+customer+deal+time 金额）│
│ ▸ 范围与团队   设备清单·项目团队·项目要求·资料包        （原 equipment+team+require+atts）  │
│ ▸ 执行进度     设计进度·节点计划·长周期采购·齐套率      （原 design+milestone+longlead）     │
│ ▸ 交付与售后   到货/发运/验收/质保/工单（只读摘要+跳转） │ ← 数据来自各台，详情回台里看        │
│ ▸ 操作记录（默认收起）                                                          │
├ ③ 明细 = 抽屉（点数字/行开 640px 抽屉，不跳页）──────────────────┤
└──────────────────────────────────────────────────────────────┘
```

**为什么这样分**：四条泳道正好对应业务主线 `成交 → 范围 → 执行 → 交付`（00 卷），用户的心智模型是"这个单子走到哪了"，不是"数据库第 7 张表"。

### 3.2 12 区块归并映射（不删信息，只改层级）

| 现在 | 去 | 处理 |
|---|---|---|
| 基本信息 / 时间与金额 / 成交信息 | 泳道①合同与商务 | 合并成一组；`label:value` 一行 ≤3 字段；**空值不渲染**（只在"应有而缺"时显示灰字提示） |
| 客户与联系人 | 泳道① | 客户 1 行 + 联系人表（列 7→4：角色/姓名/电话/操作，职务微信邮箱进抽屉） |
| 项目要求 | 泳道②范围与团队 | 4 个字段合并进"项目档案"；`旧线改造` 的 Switch 改文字（只读态不许用可交互控件外观） |
| 设备清单 / 项目团队 / 资料包 | 泳道② | 设备表列 9→6；资料包保留（附件是高频） |
| 设计进度 / 节点计划 / 长周期采购 / 齐套率 | 泳道③执行进度 | **节点计划升级为甘特式一行进度**（超期红）；齐套率从独立卡变成设备行的内联条 |
| （无） | 泳道④交付与售后 | **新增只读摘要**：到货/发运/验收/质保/工单，点它跳去对应台（数据同源，不在详情页复制逻辑） |
| 操作记录 | 底部收起 | 默认折叠，显示"最近 1 条 + 共 N 条" |

### 3.3 交互契约（UX）

1. **下一步必须可点**：`NEXT_HINT` 文案已有，改成 `[去成交登记] / [去立项] / [进入设计面] / [去登记回款]` 主按钮 —— 这是"数字驱动待办"原则在详情页的落地。
2. **就地编辑 + 分组保存**：现在每张卡各自 `save()`（13 个按钮散落），改为 `EditableField`（已有件）就地改 + 组头一个"保存本组"，脏组标黄点。
3. **面包屑**（交互规范 §1.1 早就要求，替代散落的「← 返回项目」）：结构位置用面包屑；**来路仍用 `?from=` 返回口**（docs/11 已做）——两者语义不同，都要。
4. **锚点条 12 胶囊 → 泳道 4 段**：胶囊数量本身就是"平铺"的症状。
5. **权限两级表达保持**（规范 §4）：无 `project:amount` 时金额显示 `—` + Tooltip，而不是整块消失。

## 4. 视觉底座（P0，先做——它决定"观感"的上限，而且可脚本化）

1. **补 token 刻度**（规范 §1.2/§1.4，一次改 `main.tsx`）：`fontSize 12/13/14/16/20/24`、`controlHeight 28/32`、Table/Card/Modal 组件级密度；**禁 `fontSize:10`**。
2. **等宽编号落地**（规范 §3.1，零落地的那条）：`theme/tokens.ts` 加 `MONO`，新增 `<Num>`/`<CodeNo>` 轻组件，全站图号/单号/日期/数量统一走它（可 grep 脚本替换 + 棘轮护栏）。
3. **inline style 848 → ≤300**：抽 5 个轻组件吃掉高频组合：`Stack`(间距) / `FieldGrid`(label:value 三列) / `Muted`(次要文字) / `NumCell`(右对齐等宽数字) / `Row2`(两行单元格：主+副)。
4. **文案改写规则**：内部口径（"00 卷 §3.1⑩"、"货到了就验：合格/不合格"）**从用户可见文案里删掉**，改成 `Tooltip` 或卡头 `?` 帮助抽屉；`type="secondary"` 长句 ≤30 字。
5. **状态三形态约束**（规范 §3.3）：Tag 只用于"当前状态"；列表行用左侧 4px 色条；文字色用于历史/归档。

> 全部**不引新依赖**（AGENTS 铁律：不加 CSS 框架/动效库），只做 token + 5 个轻组件。

### 13.2 修法：一处作用域 CSS，不给每个按钮加 size

`MobileLayout` 根容器加 `className="m-shell"`，`styles.css` 里按作用域统一抬升：
```
.m-shell .ant-btn { min-height: 40px }   .m-shell .ant-btn-sm { min-height: 38px }
.m-shell .ant-btn-primary / -lg { min-height: 44px }
.m-shell .ant-radio-button-wrapper { min-height: 44px }   ← 验收「合格/不合格」是拇指活
.m-shell .ant-list-item { min-height: 48px }   .m-shell .ant-tabs-tab { padding 10px }
.m-actionbar { position: sticky; bottom: 0 }   .m-actionbar .ant-btn { flex:1; min-height:48px }
```
> 为什么这样做：给每个页面各写 `size="large"` 一定会漏（10 个移动页 × 几十个按钮），作用域 CSS 一处生效、新页面自动继承。

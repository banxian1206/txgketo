## 2. ★★ 核心发现：同一个「要几个」，五个通道五种答案

测试用的 BOM 树（刻意构造 `qty>1` 的多级结构）：

```
总装图 TX26001-01A-00-00-00-00   qty=1
  └─ body 主体组件 (自制件)       qty=2
       ├─ cust 定制底板           qty=3   → 工艺改判【定制件】  真实需求 3×2×1 = 6
       ├─ out  外协罩壳           qty=1   → 工艺改判【外协件】  真实需求 1×2×1 = 2（直发现场）
       ├─ BOM 标准件 轴承          qty=4                        真实需求 4×2   = 8
       └─ BOM 原材料 方通          qty=5                        真实需求 5×2   = 10
```

**实测结果**（✅=与真实需求一致）：

| 物料 | 真实需求 | ①发布进池<br>`release_demand` | ②手动补跑<br>`equipment_demand` | ③排产<br>`manufacturing` | ④齐套率<br>`kitting` | ⑤领料<br>`generate_issue` |
|---|---|---|---|---|---|---|
| 定制底板（图纸·定制件） | **6** | **6** ✅ | **18** ❌ 平方 | — | **3** ❌ 少一半 | — |
| 外协罩壳（图纸·外协件） | **2** | **2** ✅ | **2**（但重复进池）❌ | — | **1** ❌ 少一半 | — |
| 轴承（BOM 标准件） | **8** | **8** ✅ | **8** ✅ | — | **4** ❌ 少一半 | **4** ❌ 少一半 |
| 方通（BOM 原材料） | **10** | **10** ✅ | **10** ✅ | — | **5** ❌ 少一半 | **10** ✅ |
| body 主体组件（自制件） | **2** | — | — | **2** ✅ | **2** ✅ | — |

**四个不同的错法，根因各不相同：**

| 通道 | 代码 | 错在哪 |
|---|---|---|
| ② `equipment_demand` **图纸分支** | `float(d.qty) * cum.get(d.drawing_no, 1.0)` | `cum[X]` 已经 = `X.qty × cum[parent]`（含自身），**又乘一次 → qty²**。定制底板 3 → 3×6=18。`release_demand`/`manufacturing` 都只写 `cum[X]`，是对的 |
| ④ `kitting` | `need = _qty(d.qty) or 1`（图纸）、`_qty(b.qty) or 1`（BOM行） | **完全不乘父级累计倍数** → 一律少一半（本例父 qty=2） |
| ⑤ `generate_issue` **标准件分支** | `need[child] += _qty(b.qty)` | **完全不乘** → 少一半 |
| ⑤ `generate_issue` **原材料分支** | `qty = b.qty * parent.qty` | **只乘直接父件一层** → 本例（两级树）恰好对；**三级及以上必然少领** |

> ★ 为什么 `qty=1` 时全都看不出问题：`1² = 1`，`1 × 任何数 = 任何数`。
> 现实里绝大多数图纸 qty=1，所以这四个错法**潜伏至今**。一旦有 `qty>1` 的组件（非标设备里非常常见：一套 2 个工位、4 个夹爪），**采购超买 3 倍 / 齐套率虚高 / 车间少领一半料**同时发生。

**齐套率虚高的实际后果**（实测）：`kitting` 返回 `rate=1.0, arrived=5/5, qty 15/15`，而真实总量应为 `2+6+2+8+10 = 28`。**显示 100% 齐套，实际只到了一半多** → 装配按它开工会停线。

## 3. ★★ 净需求缺一项抵扣：四种场景会重复进池

### 3.1 根因（一句话）

`bom_demand._cover` 的抵扣只有两项：**当前库存** + **`OPEN_STATUS` 里的在跑需求**。
**完全没有「已完成的采购需求量」这一项。**

```python
OPEN_STATUS = ("待采购", "在途", "已下单", "待入库", "部分到货", "不合格")
#              ↑ 不含 现场待验收 / 现场已验收 / 已入库
cover = max(stock, 0.0) + open_qty
```

于是**货一旦离开库存，系统就认为「从来没买过」**。离开库存有三条路：直发现场、领料出库、验收合格还没入库。三条路都已实证。

### 3.2 隔离实证（每个机制一个独立干净项目）

| 场景 | 项目 | 实证数据 | 结果 |
|---|---|---|---|
| **ISO-A 直发件完成后** | TX26001 | 定制底板发布进池 **6**（正确）→ 下单直发 → 现场清点「齐」→ 需求 `现场已验收`、库存 `0`（直发从不入库）→ 手动补跑：`need_qty=18, covered_qty=0, created=1` **新增 qty=18** | ❌ 一次多买 **18**（真实 6，已买 6 → 共 24，**4 倍**）<br>★ 同时命中 qty² 平方 bug |
| **ISO-B 验收合格未入库** | TX26002 | 轴承发布进池 **8**（正确）→ 下单 → 验收合格**不入库** → 需求 `待入库`、`qty_received=8`、库存 `0` → 手动补跑：`need_qty=8, covered_qty=0, created=1` **新增 qty=8** | ❌ 完全重复一倍<br>机制：`qty_received` 含 pending → `_open_qty` 的 `remaining = 8−8 = 0`；货又还没入库 → **两头都不覆盖** |
| **ISO-C 已入库+已领走** | TX26003 | 板材发布进池 **10**（正确）→ 下单 → 验收入库（库存 10）→ 领料领走 5（★ 领料只要了 5，本该 10）→ 库存剩 5 → 手动补跑：`need_qty=10, covered_qty=5, created=1` **新增 qty=5** | ❌ 又买 5<br>共买 15，真实只需 10 |
| **主 e2e B2 综合** | TX26001 | 发布进池后**立刻**手动补跑，一次新增 **4 条**：定制底板 ×12、外协罩壳 ×2、方通 ×10、轴承 ×4 | ❌ 违反 AGENTS §8.1「幂等，重复点不会重复进池」 |

### 3.3 为什么"幂等"承诺会失效

AGENTS §8.1 写的是：*"设备设计面「生成采购需求（进池）」= 已冻结的 BOM 展开 − 库存 − 在跑需求（**幂等，重复点不会重复进池**）"*

幂等成立的**隐含前提**是：货要么在库存里，要么在跑。这个前提在三种情况下都不成立（§3.2）。
**换句话说：幂等只在「刚发布、还没开始执行」时成立；一旦进入执行期，每点一次就多买一批。**

### 3.4 连带后果：领料少领 → 库存残留 → 少买

主 e2e B2 里轴承新增 **4**（不是 8），因为：
`generate_issue` 只领了 4（§2 标准件分支不乘）→ 库存剩 4 → `cover=4` → `residual = 8−4 = 4`。
**两个 bug 相互抵消了一半**，导致数字看起来"没那么离谱"，实际是：车间少领 4 个（会停工等料），采购又多买 4 个。

### 3.5 缺料行静默跳过（实测）

```
第二张领料单 MI26005：板材 需 5.0，shortage=True，location=None
  → 备料 HTTP 200「已备料」
  → 领走 HTTP 200「已领走」
  → 行 qty_issued = 0.0        ★ 一个都没发
  → 审计日志：「领料出库 MI26005：1 种物料，领料人 车间 李四」   ★ 日志说谎
  → 齐套率：板材 ready=True, state="已入库"                    ★ 而实际库存 = 0
```

`hand_over_issue` 里 `if not ln.location_id: continue` → 不扣库存、不写流水、不写 `qty_issued`，整单照样置「已领走」，审计日志按 `len(lines)` 报数。
齐套率又用 `qty_required`（不是 `qty_issued`）判"已领到车间" → **三处一起骗人**，只有装配时发现没料。

## 8. 对采购域重构的影响

1. **§2 的五通道口径必须统一，且优先级高于建表**。建 `purchase_order` / `purchase_order_line` 解决的是"单据结构"，但如果 `qty` 本身算错，单行数量照样错。→ **重构方案已加入「第 0 期：抽 `services/bom_math.py` 统一数量口径」**（见 `docs/08` V2）。
2. **`_cover` 必须增加第三项抵扣**：「已完成的采购需求量」。这是四种重复进池场景的共同根因，且不解决它，拆单功能（一条需求多张单）会让问题更严重 —— 拆单后 `qty_ordered` 语义更复杂。
3. **拆单的实证依据已经拿到**：ISO-A/B/C 都是"一条需求只能属于一张单"导致的（`purchase_request.po_no` 单值 + `merge_order` 覆盖 `qty`）。B1 探针直接实测：下 60 后 `qty` 被改成 60，再下 40 → `400 当前状态是「在途」，不能合并下单`，**40 个蒸发**。
4. **静默跳过与超锁必须一起修**（§5.5），否则修一个暴露另一个。
5. **e2e 脚本本身要重建**：`/tmp/txgk_e2e.py` + `/tmp/txgk_isolate.py` 已验证可跑（0 中断），建议提升为 `backend/scripts/e2e_baseline.py` 与 `backend/scripts/probe_bom_math.py`，作为重构的**回归基线**（重构前先记录现状，重构后逐条转绿）。

## 2. ★ 本轮新发现

### N11 [中] 审批留档的 `round_no` 错位 —— 看不出「第几轮被退回」

**根因**：`services/purchase_order.py:176` 退回分支**先加 round、再写留档**：

```python
if action == "退回":
    po.status = PO_RETURNED
    po.round = int(po.round or 1) + 1          # ← 先 +1
...
session.add(PurchaseApproval(
    round_no=po.round,                          # ← 用的是加完之后的 round
    ...))
```

**实测**（`/tmp/txgk_round.py` R1）：一张单走完「提交 → 第 1 轮被退回 → 重提 → 经理通过 → 总监通过」：

```
留档 3 条：[(round=2, level=1, '退回', '第1轮退回'),
            (round=2, level=1, '通过'),
            (round=2, level=2, '通过')]
终态 已批准 round=2
     ★ round_no 集合 = {2}   ← 三行全在第 2 轮，第 1 轮的退回被记到了第 2 轮
```

**后果**：审批时间轴上**「第 1 轮被退过」这个事实消失了** —— 三条记录都挂在 round 2 下，
`退回` 和它引发的 `重提通过` 混在同一轮里，分不清因果。08 §3.3 承诺的"多轮多级全部留档"只做到了一半（记录都在，但轮次归属错）。

**修法**：写留档用**退回前**的 round，写完再 `po.round += 1`：
```python
record_round = int(po.round or 1)
... PurchaseApproval(round_no=record_round, ...)
po.round = record_round + 1
```

### N12 [P0·严重] 拆单后到货**记到错误的单行** → 供应商绩效污染 + 作废被堵 + 对账错乱

**根因**：`api/routes/initiation.py:1225` `_bump_line_on_receipt()` 用「该需求的**最新一行**」定位到货该记到哪：

```python
line = session.scalar(
    select(PurchaseOrderLine)
    .where(PurchaseOrderLine.request_id == row.id)
    .order_by(PurchaseOrderLine.id.desc())      # ★ 「最新一行」，不是「这批货实际来自哪张单」
)
```

**为什么错**：验收接口是**按「采购需求」粒度**的 ——
`POST /projects/{p}/purchase-requests/{id}/inspect`，入参 `AcceptanceIn` 只有 `receipt_date / qty / result / qty_ok / qty_rejected / note`，**没有 `po_id` / `po_line_id`**。
拆单之前这是对的（一条需求只有一张单，取最新一行 = 取那唯一一行）；
**拆单之后一条需求对应多张单，系统无从知道这批货是谁送的，只能猜 —— 而它猜"最后一行"。**

**实测**（`/tmp/txgk_round.py` R2）：需求 `方通×100` 拆给 甲60 + 乙40，两张都审批通过，然后**只让甲那批 60 到货入库**：

| 采购单 | 供应商 | 订购 | 行 `received_qty` | 行状态 | 单头 | `actual_arrive_date` | `delay_days` |
|---|---|---|---|---|---|---|---|
| PO26017 | **甲钢材（真送货 60）** | 60 | **NULL** | 在途 | **已批准** | **NULL** | **NULL** |
| PO26018 | 乙标准件（**一件没送**） | 40 | **60** ❌超 50% | **已入库** | **执行中** | 09-28 | **-10** |

列表接口因此给出完全相反的呈现：
```
PO26018  status=已完成   po_status=执行中    ← 从未发货的单看起来"已完成"
PO26017  status=在途     po_status=已批准    ← 真交货的单看起来"还没到"
```

**五重后果**：

1. **供应商绩效被污染**：乙钢材被记成"提前 10 天交了 60 件"（实际一件未送），甲钢材（真实履约方）**零记录**。三期-C 的准时率/合格率打分从此拿错数据 —— 而这条链刚刚在 N1 里被修好，现在被这个 bug 从上游污染。
2. **作废出口被堵**（客户口径#16）：想作废未到货的乙单 →
   `400 当前状态是「执行中」，不能作废（已有到货的请走「整批退货关闭」）`
   —— 可乙根本没到货，却被逼去走"整批退货"。这正是 AGENTS §8.1 记的教训：*"任何『往前不能退』的硬拦都会造出永久死单"*。
3. **行级超额**：`received_qty=60 > qty=40`，一条单行收货量超过它的订购量 50%，`assert_no_over_order` 的口径被绕过。
4. **重复采购风险**：甲单在采购员眼里"还没到"（`status=在途`）→ 可能再下一单或误催货。
5. **对账/退换货错位**：`goods_receipt.po_line_id` 指向乙的行，后续按行协商换货会找错供应商。

**独立确认的第二处同源缺陷**（同一根因，不同函数）：

```python
# void_purchase_order（initiation.py:2911）
for ln in lines:
    if ln.request_id and _request_receipts(session, ln.request_id):   # ★ 查【整条需求】的到货单
        raise 400 "这张单已经有到货单，不能作废"
```
应按**本单行**过滤（`GoodsReceipt.po_line_id == ln.id`，该列已存在）。
本轮这个守卫在更前面的单头状态检查就被拦住了，所以尚未单独暴露 —— 但修好 N12 后**它会立刻变成下一个可见故障**。

**★ 为什么基线 111 项全绿没抓到**：
`b_split` 只测**拆单**（不下货到货），`b_partial_ok`/分批到货只测**到货**（不拆单）——
两条路径各自通过，**它们的交叉点从未被测过**。这正是我上轮报告 §4 说的失效模式（功能写了但没有路径触发它）的又一次复现。

**修法（两层）**：

| 层 | 做法 |
|---|---|
| **根本** | 验收接口接受 `po_line_id`（或 `po_no`）：仓库收货时看的是供应商送货单，本来就对应某一张 PO —— 让仓库指定，与 00 卷「OCR 结果永远只作候选，必须人工确认」同一哲学：**系统不该猜实物归属** |
| **过渡**（若暂不改接口） | `_bump_line_on_receipt` 改为按「未收满 + 状态为在途/部分到货 的行」按 qty 缺口分摊，并保证不会让任何一行 `received_qty > qty`；`void_purchase_order` 的守卫改成按 `po_line_id` 过滤 |

> ⚠ 这条我要认领一部分责任：`docs/08 §3.5` 写了"`goods_receipt` 加 `po_id` + `po_line_id`"，但**没写验收时如何确定这批货来自哪张单**。列建好了、写入点靠猜补上，是我方案的缺口。

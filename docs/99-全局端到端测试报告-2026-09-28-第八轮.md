## 3. 本轮新发现的 5 个问题

### M-04 [P1] 权限封堵把**设计师拦在自己任务之外**，且护栏零覆盖

**根因**：`PATCH /tasks/{task_id}` 这轮加上了 `Depends(require_permission("project:edit"))`（`routes/tasks.py:380`），
但**任务负责人根本没有 `project:edit`**：

```
mech_manager  → design:audit, design:edit, project:view, std:view
craft_manager → design:edit, project:view, std:edit, std:view
mech1/elec1/prog1/craft1 → design:edit, project:view, std:view
```

**实测**（用任务**本人**账号改**自己名下**任务的状态）：

```
craft_manager  PATCH /tasks/2 {status:进行中} → 403 {"detail":"没有权限：project:edit"}
craft_manager  PATCH /tasks/4 {status:进行中} → 403
craft_manager  PATCH /tasks/6 {status:进行中} → 403   （三条都是「待开始」）
mech_manager   PATCH /tasks/1 …               → 403
```

**前端会直接撞上去**：`features/task/Page.tsx:90` 的 `updateTask(id, { status })` 就是「开始」/「完成」两个链接
（`Page.tsx:236–250`），渲染条件只有 `task_type !== '采购' && status !== '已完成'`，**没有任何 `hasPerm` 门槛**
（同页的「拆分派工」反而有 `isLead` 门槛）→ 每个设计师都看得到、点了就吃红叉。
后果：**S2 设计的「开工/完成」这一步对干活的人不可用**（评审发布能自动置完成，但手动开工/推进没路）。

**为什么没被拦下**：`grep` 证据——
`scripts/e2e_baseline.py` 里**没有任何 `PATCH /tasks` 调用**；`frontend/e2e/ui.mjs` 里**没有「开工/完成」的点击**。
这条接口路径**两套护栏都没覆盖**，所以加门禁时没人发现它把人锁在外面。

> 修法方向（未实施）：门禁应按"能不能动这张任务"判，而不是扁平要求 `project:edit` ——
> 负责人本人 / 其经理（同专业 `POSITION_LEAD`）/ 总监 / `project:edit` 任一即可；
> 同时给 `PATCH /tasks/{id}` 补一条 e2e 断言（正控：设计师能改自己任务；反控：他人不能）。

### M-03 [P2] 建单时库存=0 的领料行，**货到以后永远备不出来**

**根因链**（三处叠加）：
1. `generate_issue`（`routes/warehouse.py`）**只在该库位"当时有可用量"时**才写 `location_id`，否则留 `NULL`；
2. `pick`：`if not ln.location_id: ln.shortage = True; continue` —— 无库位的行**永远跳过**；
3. `hand-over`：`if not ln.location_id: pending.append(...)` —— 同样跳过；
4. `IssueActionIn.location_id` 这个入参**声明了但 pick/hand-over 都没读**（全文件只有 `inbound` 用它）。

**实测**：

```
零库存下 generate-issue → 行 YL-FT-0001 需20.0 location_id=NULL shortage=True
POST /warehouse/inbound 把 20 个补到「主库位」→ 库存确实 20.0/占用 0.0
POST /warehouse/issues/{id}/pick               → 400「库位可用量为 0，无法备料：YL-FT-0001（先补货再备料）」
POST /warehouse/issues/{id}/pick {location_id} → 400 同上（入参被忽略，实测备料量仍 0.000）
POST /warehouse/issues/{id}/hand-over          → 400「要先备料才能领走」
领料单状态停在「待备料」，无任何接口可推进、可作废
```

⚠ 那句报错还是**错的**：库位里明明有 20，提示说"可用量为 0"（因为该行的库位是 NULL，它查的根本不是那个库位）。

**同族的契约缺口**：`ISSUE_STATUS` 含 `"已取消"`，但全仓**没有任何接口能把领料单置成「已取消」**
（只在别处的过滤条件里被读到一次）——即"作废口"在枚举里承诺了、实现里没有。
这正是 AGENTS §8.1 记过的教训：**"没有取消/作废口 → 造出永久死单据"**。
所以 N24 的修复只覆盖了 `0 < 库存 < 需求`，**没覆盖 `库存 = 0`**（缺料最常见的形态就是没货）。

> 修法方向（未实施）：`pick`/`hand-over` 采纳 `location_id`（无库位时用入库库位回填，并允许人工指定）；
> 或给领料单补一个「作废」口（把未备量释放回需求池），并让报错文案说清"这一行没绑库位"。

### M-02 [P2] `PATCH /projects` 改 `pm_id` 不同步项目角色

```
改前： project.pm_id=18   project_member(项目经理)=[18]        ← 一致
pm1   PATCH /projects/TX26001 {"pm_id": 8} → 200
改后： project.pm_id=8    project_member(项目经理)=[18]        ← 两个真相
```
`pm_id` **不在** `SALES_OWNED_FIELDS` 内（注释明确写"执行类不在内——项目管理仍可改"），所以这条路径是被预期使用的。
而 AGENTS §8.1 记的是：*"`project.pm_id` 必须与项目角色「项目经理」同步（任命/解绑时写），所有'通知项目经理'的分支靠它定位"*。
`POST /users/{id}/handover` 做了同步、立项流程也做了同步（基线有断言：`project.pm_id 与项目角色「项目经理」同步（pm_id=18）` ✅），
**唯独通用 PATCH 这条路径漏了** → 换项目经理若走项目详情页，团队角色不会跟着换，通知发给新 pm_id、而团队里挂的还是旧人。

### M-01 [P2] N21 的兜底只修了采购链，**评审链原样保留**

采购链这次改成了"按单据归属部门找审批人"（正确解），设计链没跟上。

## 5. 总评与建议

2. **优先级建议**：**M-04（P1，正在阻断设计流程 + 零覆盖）→ M-03（P2，永久死单）→ M-01（P2，N21 的同类未修）→ M-02（P2，数据两个真相）→ M-05（P3）**。
3. **最小护栏补法**（配合上面每条，防止再溜）：
   - `PATCH /tasks/{id}`：**正控**"任务负责人能改自己任务状态" + **反控**"别人不能"（现在只有反控）；
   - 领料单：把"零库存建单 → 补货 → 备得出"写成一条 e2e（当前 N24 只测了 `0<库存<需求`）；
   - 把 `e2e:api` 那 4 条休眠断言改成**自建靶**（自己造辅料需求 / 自己造装配完成设备），不依赖残留数据；

## 7. 补充（2026-09-28 · 按 §4「休眠护栏」自评落地）

§4 里我自己批得最狠的一条是：**"休眠的护栏永远绿 = 没有"** —— `e2e:api` 有 5 条断言靠"扫库碰运气"，
数据不合就 `check(id, true, '...跳过', 'SKIP')`，**把 FAIL 悄悄换成了 SKIP**。现已全部改成**自建靶**：

| 断言 | 原来 | 现在（自建靶） |
|---|---|---|
| `P-02` 无项目（辅料）需求验收路由 | 扫 `warehouse/workbench.incoming` 找 `project_no` 为 NULL 的 | 自己 `manual-request`（**不带 project_no**）→ `merge-order`（公司仓库）→ 审批到在途 → 拿它验收 |
| `P-05` 验收门禁 | 扫项目找"线索/成交待立项/执行中" | 自己**新建一个商机**（线索）→ 申请验收应 400「调试还没完成」 |
| `R5-01/02` ×3 装车硬拦·补勾·锁死 | 扫 `to-ship` 找"装配完成且不在未完成批次" | 自己**造一台装配完成的设备**（挑有零件的设备 → 开始装配 → 装配完成）再走批次 |

**另外发现并治掉 4 条同类**（`P-07` / `R2-01` / `RCPT-售后报修` / `O3A-预计到货` —— 它们只在"库里一点数据都没有"时才跳，
平时因为有数据所以看不出来）：把 `true, '...跳过', 'SKIP'` 一律改成**明确失败** —— 基线跑完本来就该有项目/供应商/物料，缺了就是真问题。

**结果**：复位后**单独**跑 `e2e:api` → **PASS 15 / FAIL 0 / SKIP 0**，**不再依赖任何残留数据、也不再依赖"先跑 UI 套件"**。

**新增「护栏的护栏」**：`backend/tests/test_no_sleeping_assertions.py`（3 条，注入反例能红）——
① 禁止 `check(..., true, ..., 'SKIP')` 假绿；② `api.mjs` 里**不许出现带引号的 `'SKIP'`**（休眠就是没测）；
③ 三个自建靶的关键动作必须在（防止有人"清理"掉造数逻辑又退回扫库）。

## 2. 本轮新发现（3 个，均轻微）

### N18 [P2] 前端只认「退货重采」，`现场缺件` 的溯源被吞

后端**已经**给补采需求回了溯源字段：
```json
{"id":25, "source":"现场缺件", "origin_po_no":"PO26024", "source_release_no":null}
{"id":29, "source":"现场缺件", "origin_po_no":"PO26026", ...}
```
但 `frontend/src/features/purchase/Page.tsx:320-335`：
```tsx
v === '退货重采' ? (<><Tag color="orange">退货重采</Tag>{r.origin_po_no && <>原 {r.origin_po_no}</>}</>)
                 : (<><Tag>{v}</Tag>{r.source_release_no && <>…}</>)   // ← else 只读 source_release_no
```
→ `现场缺件` 走 else 分支：有默认灰标签（不是完全不可见），但**「原 PO26026」不显示**（因为 `source_release_no` 为 null）。

**后果**：N16 的"最后一公里"没走完 —— 采购员在池里看到 3~4 条灰灰的「现场缺件」需求，**不知道各自对应哪张单、哪批货缺的**，而这信息后端有。同一条信息在仓库侧「退货重采」上是橙色高亮 + 带溯源的。
**修法**：`Page.tsx` 把判断从 `v === '退货重采'` 改成"补采类来源集合"（含 `现场缺件`），或在 else 分支也渲染 `r.origin_po_no`。约 3 行。`PurchaseOrderDrawer.tsx:482` 同。

### N17 [P3] `REQUEST_SOURCES` 是死代码且早已漂移

```python
# models/initiation.py:64
REQUEST_SOURCES = ("常规", "长周期", "退货重采")
```
- **全库仅此一处定义，零引用**（`grep -rn REQUEST_SOURCES app/ scripts/ tests/` → 只命中定义行）→ 无任何校验作用
- 实际在用的 source 值有 7~8 个：`手工`(27条) / `现场缺件`(4条) / `退货重采`(1条) / `设计发布` / `工艺发布` / `常规` / `长周期` / `退货重采`，其中 `SOURCE_DESIGN_RELEASE`、`SOURCE_CRAFT_RELEASE`、`SOURCE_MANUAL` 三个常量**本来就不在词表里**（早于本次改动）
- 新增 `SOURCE_SITE_SHORTAGE = "现场缺件"` 时同样没同步 → 属既有漂移的延续，**不影响运行时**
- `tests/test_status_contract.py` 只管 `*_STATUS`，**不覆盖 `source` 维度**

**修法**：要么让 `REQUEST_SOURCES` 真正收集全部 `SOURCE_*` 并被 `test_status_contract.py` 断言（推荐，一条断言就能挡住以后每次漂移），要么删掉这个误导性常量。

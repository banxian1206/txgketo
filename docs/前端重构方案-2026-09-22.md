# 前端 Web + 移动端重构方案

> 日期：2026-09-22 ｜ 状态：**待拍板**（§8 有 4 个需要决策的点）
> 依据：① 代码量化侦察（本文 §1）② 同日 E2E UI 测试 22 项问题（`99-E2E测试报告-2026-09-22-前端UI.md`）
> 前提约束（AGENTS §3/§6）：**React 18 + TS + Vite + AntD 5 技术栈不变；不得擅自新增依赖**——凡新依赖必须先在 AGENTS §3 补决策，默认走零依赖方案。

## 1. 现状诊断（先看数字）

### 1.1 规模

| 指标 | 现状 | 问题 |
|---|---|---|
| 总代码量 | **21,932 行** TS/TSX（27 个 PC 页 + 10 个移动页 + 21 个组件） | 无测试护栏（frontend 零测试） |
| `api/client.ts` | **3,175 行 / 198 个函数**，类型+常量+接口函数混装 | 任何人改任何功能都要碰这一个文件，冲突与误伤高发 |
| 巨石页面 | `EquipmentDesign` 1,452 行 · `ProjectDetailPage` 1,347 · `PurchaseWorkbench` 901 · `Users` 884 · `Warehouse` 753 | 单文件承载 5~8 个业务卡片，review/修改都在百行级别 diff |
| Modal / Table | **60 个 Modal、88 个 Table** | 全部手搓，无统一基座 |
| `destroyOnClose` | 45 处 | 直接对应测试 P-03（预填失效）、P-16（antd 弃用警告） |
| `Form.useForm` | 42 处 + 169 处 `errMsg(e)` 手写 try/catch | 对应 P-09（validateFields reject 未捕获） |
| localStorage | 5 个 key 散落（`txgk_token/user/name` + `IMPERSONATE_*`），36 处直接读写 | 登录态/身份伪装/权限判断各读各的，`AppLayout` 每次进页面才刷新 profile → 权限状态会 stale |
| 路由 | 全部静态 import，**无 code splitting** | 首屏加载全站代码 |
| `window.prompt` | 2 处（PC `Warehouse` + M `IssuesM` 各一份） | 对应 P-12 |

### 1.2 最大的结构性问题：**双端双实现**

同一业务在 PC 和移动端**各写一遍**，靠人肉保持同步：

| 模块 | PC | 移动 | 现状 |
|---|---|---|---|
| 现场 Site | 341 行 | **445 行** | ⚠️ **移动比 PC 还大** —— 因为勘测/日报/问题/申请调试的**创建入口只写在移动端**（测试 P-04），PC 端只剩只读列表 |
| 发运 Shipping | 604 | 251 | 双实现，清单勾选逻辑两份 |
| 仓库 Warehouse | 753 | 224 | 双实现 |
| 装配 Assembly | 394 | 226 | 双实现 |
| 售后 Service | 353 | 164 | 双实现 |

**后果已被上轮测试证实**：5 个模块只要漏同步一处，就是"PC 找不到入口"（P-04）、"两端行为不一致"这类问题；而且同一段校验/提交代码在两处各修一遍。

### 1.3 测试 22 项问题中的「架构性根因」

| 测试问题 | 根因 | 靠修 bug 能根除吗 |
|---|---|---|
| P-03 弹窗预填失效（通用） | 45 处 `destroyOnClose` Modal 各写各的 `setFieldsValue` 时序 | ❌ 下一个 Modal 还会犯 → 需统一基座 |
| P-04 PC 现场无创建入口 | 双端双实现漏同步 | ❌ → 需共享业务组件 |
| P-09 空提交抛未捕获异常 | 42 处 `validateFields` 无统一 catch | ❌ → 需统一提交封装 |
| P-12 原生 prompt | 无表单基座，图省事 | ❌ → 同上 |
| P-13 项目号手填 Input | 无共享字段组件（`SelectProject` 这种东西不存在） | ❌ → 需业务字段组件库 |
| P-16 antd 弃用刷屏 | 45 处属性没有集中治理 | 一次性清理可根除 |
| P-01/P-02/P-05~P-08 | **后端逻辑问题，与前端架构无关** | 与本次重构并行走后端修复 |

**结论：重构要解决的不是"代码不好看"，而是让 P-03/P-04/P-09/P-12/P-13 这一类问题在结构上不可能复发。**

## 2. 目标与原则

### 2.1 目标（可验收）

1. **一份业务逻辑，两端共用**：每个业务动作（验收/入库/清点/报修…）只有**一份**组件+一份数据 hook，PC 与移动只是两个薄壳 → 从结构上消灭"PC 有移动没有"
2. **新增一个业务卡片的成本**：从现在"抄 Modal+Table+try/catch 约 200 行"降到 **"调用基座 + 写字段，约 50 行"**
3. **上轮测试的 5 项架构性问题（P-03/04/09/12/13）+ P-16 全部根除**，且有 E2E 回归防止复发
4. **首屏按路由分包**，单页只加载自己的代码
5. **移动端具备 03 卷要求的离线能力前置**（拍照先存本地、动作可排队），为 Capacitor 打包铺路

### 2.2 原则（红线）

1. **绞杀者式渐进重构，不推倒重来** —— 每一阶段结束系统都是可交付状态，可整体回滚
2. **业务规则零改动** —— 编号、状态机、权限语义、接口契约都在后端；前端重构只动"组织方式"，不动"业务含义"
3. **不顺手改 UI/文案** —— 重构 diff 与"交互改动"严格分离（视觉应零变化，改视觉另立需求），否则无法回归
4. **每阶段必过三关**：`npx tsc --noEmit` + `npm run build` + 全量 E2E 重跑全绿
5. **依赖不新增**，除非先在 AGENTS §3 补决策（§7 给了决策表）

## 3. 分阶段方案

### 阶段一：打地基（约 3~5 天，页面零变化）

**做什么（纯结构调整，用户看不出任何变化）：**

| # | 事项 | 说明 |
|---|---|---|
| 1.1 | **E2E 脚本入库当护栏** | 把 `/tmp/e2e/*.mjs` 收进仓库 `e2e/`（登录、25 路由冒烟、9 个关键动作链），配 `npm run e2e`；**这是后续所有重构的前提，没有护栏不动刀** |
| 1.2 | **拆 `api/client.ts`** | 按域拆：`api/{http,auth,project,design,review,change,purchase,warehouse,manufacturing,assembly,shipping,site,acceptance,service,notify,user,library}.ts` + `api/types.ts`；`http.ts` 集中拦截器：**401 跳登录、403 统一"无权限"文案、5xx 友好提示**（根除 P-06 那种裸露 `Request failed with status code 500`） |
| 1.3 | **三个基座封装**（零依赖，纯封装 antd） | ① `hooks/useSubmit.ts`：统一 `validateFields` + catch + message，根除 P-09；② `components/AppModal.tsx`：**统一"打开即挂载、预填生效、关闭销毁"的时序**，根除 P-03，45 处 Modal 逐页替换；③ `hooks/useRequest.ts`：loading/error/data 三态小 hook（自写 ~40 行） |
| 1.4 | **登录态与权限收口** | `contexts/AuthContext.tsx`：单一 storage key、`<AuthContext>` 供全站、`usePerm()` 替代散落的 `JSON.parse(localStorage.txgk_user)`；`hasPerm` 从 context 读，登录/登出/伪装一处更新 → 根除权限 stale |
| 1.5 | **业务字段组件**（先建 4 个） | `<SelectProject>` `<SelectEquipment>` `<SelectSupplier>` `<InputLocation>`（库位下拉，根除 P-11/P-13 手填）——后续所有表单只准用这些 |
| 1.6 | **antd 弃用治理** | 45 处 `destroyOnClose`→`destroyOnHidden`、`addonAfter`→`Space.Compact`（根除 P-16 控制台刷屏） |
| 1.7 | **巨石页第一刀（只拆不改）** | `EquipmentDesign` 拆成 `components/design/{DrawingsTree, BomStdPanel, BomMaterialPanel, ProgramsPanel, SubmitPanel, PurchasePanel}`；`ProjectDetailPage` 同理按 6 个锚点区块拆 |

**验收**：`tsc + build + e2e` 全绿；浏览器逐页截图与重构前**像素级一致**；console 无 antd 警告。

### 阶段二：双端合一（约 1~2 周，本次重构的核心）

**目标结构：每个业务域三层，PC/M 只是壳。**

```
src/
  app/                    # 壳与全局：App.tsx 路由、AppLayout(PC)、MobileLayout(M)、AuthContext、providers
  api/                    # 阶段一已拆好的按域 client + types + http
  features/               # ★ 业务按域垂直切分（一个域 = hook + 组件 + 两个薄壳）
    warehouse/            # 例：仓库域
      hooks.ts            #   useWarehouseBoard() 数据 + useInspect()/useStore() 动作（唯一一份）
      components/         #   InspectModal / StoreModal / IssueTable（唯一一份，PC/M 共用）
      Page.tsx            #   PC 壳：Table 布局
      MobilePage.tsx      #   M 壳：List + 大按钮，只拼装同一批组件
    site/                 #   ★ 创建入口（勘测/日报/问题/调试）做成共享组件 → PC、M 都挂 → 根除 P-04
    shipping/ purchase/ design/ manufacturing/ assembly/ acceptance/
    service/ tasks/ review/ change/ admin/(users·library·numbering) / workbench/ project/
  components/             # 跨域通用：AppModal、useSubmit、SelectProject…、MfgPhotoPicker（本就共享，保留）
  contexts/  hooks/  utils/
```

**关键动作：**

| # | 事项 | 消掉哪个问题 |
|---|---|---|
| 2.1 | **建 `features/` 骨架，先迁 2 个试点域**（仓库、现场——问题最集中） | 试点验证模式，不一次全迁 |
| 2.2 | **现场域共享化**：把 `SiteM` 里的勘测/日报/问题/申请调试 4 个表单抽成 `features/site/components/*`，**PC `Site.tsx` 挂上同一批按钮** | **P-04**（PC 无创建入口） |
| 2.3 | **共享动作 Modal**：验收/入库/清点/装车/报修…全部走 `AppModal` + `useSubmit` | **P-03、P-09、P-12**（prompt 换 Modal） |
| 2.4 | **字段组件全覆盖**：项目/设备/供应商/库位/物料搜索 5 类字段全站替换手填 | **P-11、P-13** |
| 2.5 | **数据 hook 抽离**：`useXxxBoard()` 同时供 PC Table 与 M List 用，双端数据口径强制一致 | 双端数字不一致类隐患 |
| 2.6 | **逐域迁移**（每迁一域过一次三关）：仓库→现场→发运→装配→售后→制造→采购→设计→项目→管理 | 每步可交付可回滚 |
| 2.7 | **移动端壳保留 `/m` 路由与 820px 登录分流**（03 卷同构原则），只换内部实现 | 不动用户习惯 |

**验收（新增）**：E2E 脚本为每个业务动作出 **PC + 移动双视口两份用例**，全部通过；5 个原双实现模块的 PC/M 页面各自 diff 后行数应大幅下降（M 壳目标 <80 行/页）。

### 阶段三：性能与移动强化（约 3~5 天，可与业务并行排期）

| # | 事项 | 说明 |
|---|---|---|
| 3.1 | **路由级 code splitting** | `React.lazy` + `Suspense`，按 feature 分包（React 已有能力，零依赖） |
| 3.2 | **离线队列（03 卷硬需求）** | `hooks/useOfflineMutation.ts`：写操作进 IndexedDB 队列（含重试、状态回显"待同步"）；**照片先落本地再补传**——这是 Capacitor 打包的前置条件 |
| 3.3 | **PWA 补齐** | 已有 `manifest.webmanifest`，补 service worker（App Shell 缓存 + 队列同步脚本）；SW 是标准 API 非依赖 |
| 3.4 | **移动动线规范落文件** | 把"清单+勾选+拍照、大按钮、必填红标"写成 `features/*/MobilePage` 检查清单，后续新页面照抄 |
| 3.5 | **（打包就绪验证）Capacitor** | 到 03 卷要求打包 APK 时再引入——**属新依赖，需 AGENTS §3 补决策**；因阶段二已同构，届时只加壳不改业务 |

## 7. 需要你拍板的 4 个决策

| # | 决策 | 默认方案（零新依赖，推荐先跑） | 可选升级（要动 AGENTS §3 加决策） |
|---|---|---|---|
| 1 | 服务端数据缓存/重取 | 自写 `useRequest`（~40 行，三态够用） | `@tanstack/react-query`（省掉大量手动 loading/刷新，但+1 依赖） |
| 2 | 全局状态 | React Context（auth/权限/通知已够 30 人规模） | `zustand`（样板更少，+1 依赖；**不建议现阶段上**，AGENTS 明说 30 人规模别过度设计） |
| 3 | E2E 回归转正 | 脚本放 `e2e/`，用本机已装 Playwright | `playwright` 进 `devDependencies` + npm script（团队其他人能一键跑；+1 dev 依赖） |
| 4 | 单元测试 | 暂只对 `hooks/`、`features/*/hooks.ts` 写纯逻辑测试 | `vitest` 入 devDependencies（+1 dev 依赖） |

**我的建议**：决策 1、2 走默认零依赖；决策 3 建议升级（护栏值得一个 dev 依赖）；决策 4 等阶段二抽完 hook 再定。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 重构期间业务还在改，冲突不断 | 阶段一尽量短平快；阶段二**按域迁移**，一次只动一个域，冲突面最小 |
| 双端合一是最大手术，怕改坏 | 试点先行（仓库+现场）→ E2E 双视口护栏 → 逐域推广；任何一域回归失败即 revert 该域 |
| 视觉被"顺手优化"导致无法回归 | 原则 2.2-3：重构 PR 里出现视觉 diff 即打回 |
| 离线队列做浅了（只存不冲突处理） | 本期只承诺"拍照暂存 + 动作排队 + 失败重试"；字段级冲突留给真机试点后再补 |
| 后端 6 项问题未修，E2E 会红 | 重构开工前先修测试报告里的 P-01/P-02（阻断项），否则护栏本身跑不绿 |

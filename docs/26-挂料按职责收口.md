# 26 · 挂料按职责收口：品类「谁能选」

日期：2026-10-07。状态：**已落地**（分类数据 + API 收口 + 两个选择器 + 8 条护栏）。

## 1. 客户口径（原话）

> 「作为机械设计师，他不会去选择原材料，只会选择那些商选件（比如马达、电机）。
>   原材料是属于工艺去选择的。所以，我们是不是可以分个类，
>   把哪些东西可以让他选、哪些东西不可以让他选，对不对？」
>
> 「第一个仓库耗材，这里只给采购。」「第二个（其他外购）先不管吧，隐藏吧。」
> 「这几个没办法定的，就都能看得到吧？」
> 「写错兜底允许加提示，后台踢出去吧……但是我在这个标准里面去买的时候，照样能买。
>   这是我手动下单的，我能选择到的。但是这个东西又不能让机械、电气、工艺他们去选。」

★ 关键：这里的「踢出去」是**从设计面/材料 BOM 的选择器里踢掉**，**不是**从标准库删掉 ——
采购下单时照样能买到。

## 2. 机制：`std_category.select_by`

品类多一列，4 个取值：

| 值 | 谁能在**挂料选择器**里看到 |
|---|---|
| `设计` | 机械 / 电气 / 程序（设计 BOM 的商选件） |
| `工艺` | 工艺员（材料 BOM 的原材料） |
| `采购` | **对设计/工艺隐藏**；采购侧本来就全量，所以这一档 = "只给采购" |
| `皆可` | 谁都能看到（定不了的先放这里） |

★ **默认是「皆可」不是「设计」** —— 将来 ERP 再导入新品类，宁可谁都能看到，
也不能因为没配归属就**静默把料藏起来**（那会让人以为"这个件不存在"）。

## 3. 19 个类别的归属（客户逐条确认）

| 归属 | 类别 | 物料数 |
|---|---|---:|
| **工艺** | 原材料 YL | 4,702 |
| **采购** | 车间仓库耗材 HC · 其他外购 QT | 3,849 |
| **皆可** | 组件 ZJ · 半成品类 BCP · 管路附件 GLF | 375 |
| **设计** | 传动 CD · 动力 DL · 电气 DQ · 气动 QD · 导轨 DGL · 轴承 ZC · 紧固 JJ · 五金 WJ · 仪表 YQYB · 通用 TYLJ · 模具 MJ · 标准化 BZH · TCL | 19,654 |

★ 归属是**数据不是代码** —— 改一个品类只改 `CATEGORY_SELECT_BY` 一行（或将来在标准库页上点），
不动业务代码。`scripts/seed.py` **每次重应用**它，所以 `e2e:clean` + `seed` 之后分类不会丢。

## 4. 过滤规则（`routes/library.py::_apply_pick_for`）

| `pick_for` | 允许的归属 | 实测 total |
|---|---|---:|
| `design` | 设计 + 皆可 | 20,029 |
| `process` | 工艺 + 皆可 | 5,077 |
| `purchase` / 不传 | **不过滤** | 28,580 |

★ **`purchase` 与不传都是全量** —— 它**不是** `in_([采购, 皆可])`。
  这条最容易写反，写反了采购就买不到原材料，而且**没人会发现**（护栏专门钉住它）。

实测收口（用 `eng_director` 账号逐项验）：

|---|---:|---:|---:|---:|---:|
| 机械/电气（design） | **0** | **0** | **0** | 2,570 | 5,827 |
| 工艺（process） | 4,702 | 0 | 0 | **0** | **0** |

## 5. 前端：两个选择器**各查各的**

以前设计 BOM 与材料 BOM **共用同一个 `items` 列表**（`Page.tsx::searchItems`）——
一个列表没法服务两种职责。现在：

- 设计 BOM 挂标准件 → `pick_for=design`
- 材料 BOM 挂原材料 → `pick_for=process`（独立 `matItems` 状态 + 打开时按工艺职责加载）
- **兜底**：选择器下方「显示全部物料（含工艺 / 采购职责的）」复选框 ——
  跨职责能选（客户同意「允许 + 提示」，不硬拦：现实里设计确实会直接指定型材）。

## 6. 护栏（8 条，均注入反例自证能红）

`tests/test_category_select_by.py`：

1. 4 个取值是契约（且列宽 `String(8)` 放得下）
2. **默认必须是「皆可」不是「设计」**
3. 归属表与客户确认一致（YL→工艺、HC/QT→采购、ZJ/BCP/GLF→皆可、13 个→设计）
4. **19 个类别一个不少**（含 ERP 导入进来的 12 个）
5. 迁移里的落值与归属表不漂移
6. ★ **`purchase` 不是过滤条件**（真比 SQL：不传/purchase → 语句原样；design → 加了 `std_class` 收口）
7. `/items` 与 `/items/page` **两个入口都要**收口（少一个就是漏）
8. 前端确实是**两个独立选择器** + 有「显示全部物料」兜底

## 7. 已知边界

1. **只按品类（类别）划分，不按物料** —— 同一个品类里如果混了不同职责的件，只能整类归一个。
   客户口径就是按类分的，先这样。
2. **选择器的搜索是「前 N 条」**（老接口 `limit` 语义）—— 收口后候选变少，
   但若某个品类里符合职责的件排在很后面，仍需输入关键词才找得到。
   （这属于"选择器本身要重做"的范畴，见 docs/17 的标准库查找类样板。）
3. 采购侧**不做「只看我能买的」过滤** —— 客户明确要"照样能买"，所以采购看到的是全量。
